# riseup: Riseup.net email as a provider for a third-party Android client (state on 2026-10-16)

- [R1|high|confirmed] Riseup has one mail endpoint, mail.riseup.net. The names imap., smtp. and pop.riseup.net are CNAMEs to it. It has three A records (198.252.153.70, .170, .171) and no AAAA record, so it is IPv4 only. Ports: IMAP 993 (implicit TLS) and 143 (STARTTLS), POP3 995 (implicit TLS) and 110 (STARTTLS), submission 465 (implicit TLS) and 587 (STARTTLS). Port 4190 (ManageSieve) is closed. — Live probe on 2026-10-16. On port 143 the server advertises STARTTLS and LOGINDISABLED before TLS. On port 587 EHLO advertises STARTTLS and no AUTH before TLS. Port 25 gave no answer from the probe network, which may be a local block, so that result is not conclusive. Riseup docs say: 'For security reasons, we no longer support SSL' (they mean SSLv3; implicit TLS on 993/465 works). Front-end hosts answer as fews01/03/04-sea.riseup.net.
- [R2|high|confirmed] Riseup publishes RFC 6186 SRV records and a Mozilla-format autoconfig file. Thunderbird's ISPDB has no riseup.net entry. — SRV: _imaps._tcp -> mail.riseup.net:993, _imap._tcp -> 143, _submissions._tcp -> 465, _submission._tcp -> 587, _pop3s._tcp -> 995, _pop3._tcp -> 110. There is no _sieve SRV record. https://autoconfig.riseup.net/mail/config-v1.1.xml gives IMAP mail.riseup.net:993 SSL, SMTP mail.riseup.net:465 SSL, username %EMAILADDRESS%, authentication password-cleartext. https://autoconfig.thunderbird.net/v1.1/riseup.net returns 404, and riseup.net/.well-known/autoconfig returns 404. The riseup.net zone is DNSSEC-signed (DS algorithm 14).
- [R3|high|confirmed] The only SASL mechanisms are PLAIN and LOGIN on IMAP, SMTP and POP3. There is no SCRAM-*, no CRAM-MD5, no OAUTHBEARER and no XOAUTH2. IMAP also offers SASL-IR, so a client can authenticate in one round trip. — IMAP pre-auth (2026-10-16): 'IMAP4rev1 SASL-IR LOGIN-REFERRALS ID ENABLE IDLE LITERAL+ AUTH=PLAIN AUTH=LOGIN'. SMTP: 'AUTH PLAIN LOGIN'. POP3 CAPA: 'TOP UIDL RESP-CODES PIPELINING AUTH-RESP-CODE USER SASL PLAIN LOGIN'. Riseup tells users not to enable 'secure passwords' or 'secure authentication', because these 'require that the email server keep a cleartext copy of your password'.
- [R4|high|corrected] Mail at rest is encrypted per user with the TREES Dovecot plugin. The plugin must get the cleartext password at each IMAP login. For this reason password-based PLAIN/LOGIN is part of the design: SCRAM or OAuth cannot work without a redesign, and every login runs an argon2 key derivation on the server. — TREES README: '1. On IMAP log in, the user's cleartext password is passed to the plugin. 2. The plugin creates an argon2 digest... used as a symmetric secret to decrypt a libsodium secretbox... Curve25519 private key... decrypt each individual message'. New mail is encrypted on arrival with the public key. The recommended 'Interactive' cost is opslimit 4 and 32 MB. The README also says 'indexes should be disabled (otherwise, headers of incoming email are cached in cleartext)'. Riseup's own page: 'Encryption of incoming email is automatic, and only when you login does the mail become decrypted... This takes place on the server'.

The README (the repo moved to 0xacab.org/liberate/trees) has the login, argon2, secretbox and Curve25519 steps, the Interactive cost of opslimit 4 and 32 MB, and the advice that 'indexes should be disabled'. - [R8|high|confirmed] TLS facts: the server accepts TLS 1.3 (TLS_AES_256_GCM_SHA384) and TLS 1.2. It has only an ECDSA P-256 leaf certificate. The leaf is CN=mail.riseup.net with SAN imap/mail/pop/smtp.riseup.net, issued by Let's Encrypt YE1 and valid 2026-08-18 to 2026-11-16. The served chain is leaf <- YE1 <- ISRG Root YE (cross-signed by X2) <- ISRG Root X2 (cross-signed by ISRG Root X1). There is no OCSP stapling. — SPKI SHA-256 values (base64): leaf QCsLQOzQ7vHZCvFdzClVpwj3tQQZ/XNyuH9zps1uLKY= (the same leaf is on 993 and 465); YE1 brzvtCELCIZUo4sD/qPX0ccRtPsd3DY6RfmxpOU9oB4=; Root YE sCkq5UWXjg+7mKu9lMhhYF5bGLsy7VI/UNW3tccdR7w=; ISRG Root X2 diGVwiVYbubAI3RW4hB9xU8e/CH2GnkuvVFZE8zmgzI=. - [R9|high|confirmed] Pinning the leaf or the intermediate certificate will break. Riseup renews about every 60 days with a new key each time, and the intermediate changes often (E6 -> E8 -> YE2 -> YE1 in 16 months). Since 2021 Riseup tells clients not to pin fingerprints. The CAA record allows only letsencrypt.org. — crt.sh issuance dates for mail.riseup.net: 2025-06-24 (E6), 2025-08-23, 2025-10-22, 2025-12-21, 2026-02-19, 2026-04-20 (E8), 2026-06-19 (YE2), 2026-08-18 (YE1). The last three leaves have three different SPKIs. Riseup's signed notice: 'As of Sept 17, 2021 Riseup no longer publishes signed certificate fingerprints... If you were pinning against the fingerprint, you will need to change to use a different mechanism, such as DANE TLSA records, or specifying a list of certificate authorities to trust'. TLSA records exist only for _25._tcp.mx1.riseup.net and not for ports 993, 465 or 587, so a client cannot use DANE. Let's Encrypt plans: the classic profile issues 64-day certificates from 2027-02-10 and 45-day certificates from 2028-02-16.

## Missed facts
- Android Network Security Config allows an 'expiration' attribute only on <pin-set>. <trust-anchors> and <domain-config> have no expiration. To make an expiring 'only ISRG CAs for *.riseup.net' policy, use <pin-set expiration=...> with the SPKI pins of ISRG Root X1, X2, YE and YR, on top of the system trust anchors. A trust-anchors override with custom roots cannot expire. — WHY: The recommended TLS decision B cannot be built the way the report says. It must use a pin-set on the root SPKIs, which keeps the fall-back-on-expiry behaviour.
- NSC domain rules also apply to raw IMAP/SMTP SSLSockets. AOSP RootTrustManager.checkServerTrusted(chain, authType, Socket) takes the hostname from session.getPeerHost() and selects the domain config. For Tor, open the SOCKS socket to the unresolved onion, then wrap it with SSLSocketFactory.createSocket(sock, "mail.riseup.net", 993, true). SNI, hostname verification and the riseup.net pin-set then all work with the standard verifier. — WHY: The onion TLS option (B) needs no custom HostnameVerifier, which is less code and less risk. It is still unverified that the onion's 993 serves the mail.riseup.net certificate.
- Personally encrypted storage (TREES) is on by default only for accounts created since March 2017. Older accounts may have opted in or may not have it. — WHY: It changes what the app tells users: the 'wipe on alternate-email reset' warning and the argon2 login cost apply only to encrypted accounts. The client cannot find out from the protocol which kind of account it has.
- Server-side spam filing needs a folder named exactly 'Spam', and the statistical filter is opt-in in account.riseup.net Spam settings. — WHY: The app must never delete or rename 'Spam' (case-sensitive) and must not create a 'Junk' folder for Riseup. 'Not spam' trains the filter only if the user has turned it on.
- The live pre-auth capability string matches Dovecot 2.3's hardcoded banner order exactly, not the 2.4 order. In Dovecot 2.3, NOTIFY appears only with mailbox_list_index=yes. — WHY: Riseup is probably still on Dovecot 2.3, so expect no IMAP4rev2, no UTF8=ACCEPT and no METADATA after login. The NOTIFY evidence also suggests indexes are not fully off, which makes QRESYNC more likely to be useful. Both points are inferences.
- Let's Encrypt certificates no longer carry an OCSP URL; the leaf has only a CRL distribution point. Revocation therefore works through CRLs only, and Android does not check CRLs for app sockets by default. — WHY: 'No OCSP stapling' is expected, not a misconfiguration. The CA-scope pin is the practical way to harden trust. Do not add OCSP code.
- Dovecot hashes the keepalive phase on the username when the client IP is private (10/8 and similar). Riseup's front-end to back-end hop uses 10.0.1.x. — WHY: With several Riseup accounts on one phone, the 2-minute keepalives probably arrive at different times, so radio wakeups add up. One connection per device stays the lowest-cost option. This is an inference.
- On Android 15+ targets, dataSync foreground services may run only 6 h in 24 h. Thunderbird for Android/K-9 declare PushService as 'dataSync|specialUse', and FairEmail uses 'specialUse'. AOSP gives Doze network access to processes at FOREGROUND_SERVICE state or higher. — WHY: A persistent IDLE connection for Riseup needs a specialUse foreground service, not dataSync, plus a Play-policy declaration. This is the main push and battery design choice the Riseup report leaves out.
- Riseup does not rewrite Message-ID. A client-generated Message-ID can leak a local hostname (seen: '@verito.mail-host-address-is-not-set'). — WHY: This confirms that the client must generate Message-ID itself (random@riseup.net). For the same reason it should not send an IMAP ID with device or app details.
- Riseup's own docs do not agree on the login name (onion and clients pages use the bare 'joe_hill'; KB and autoconfig use the full address). The server accepts both, and rejects a wrong domain. — WHY: Supports the login-name decision: send the full address, and retry once with the bare name.

## Implications
- Authentication: for Riseup, use only AUTHENTICATE PLAIN with SASL-IR (base64 of UTF-8) over TLS or the onion. Do not use IMAP LOGIN quoting, because Riseup reports that special characters in passwords break some clients. Do not build OAuth or SCRAM paths for Riseup (R3, R4). The password is also the key that decrypts the mailbox. Store it only encrypted with a hardware-backed Android Keystore key, never write it to logs, and never send it on a clearnet connection without TLS.
- Connection economy: every login runs argon2 on the server (R4), and the server throttles (R15). Keep one long-lived IMAP connection that does sync and IDLE, keep at most 2 concurrent connections, and reconnect only on network change or error. Do not open short connections for each action.
- Push: Dovecot keeps IDLE open indefinitely and sends its own keepalives (R13). The client therefore does not need NOOP or re-IDLE timers if it sees '* OK Still here'. Measure the real keepalive interval at runtime. If no keepalive arrives, fall back to re-issuing IDLE about every 25 minutes. The server's 2-minute default will wake the radio. The client cannot change that interval, so one connection is the lowest battery cost available.
- Sync: decide from the capability list at runtime and never hardcode the 2022 list (R11). Use QRESYNC/CONDSTORE when they are advertised, handle NOMODSEQ, and if HIGHESTMODSEQ goes backward (TREES may disable persistent indexes, R4), fall back to UID FETCH FLAGS. Use COMPRESS=DEFLATE through java.util.zip; no library is needed. Run body search locally, because every server-side search must decrypt each message.
- Folders: map folders through SPECIAL-USE (Spam = \Junk). Let the user choose the Archive folder, because it may have no \Archive flag (R12). Show the server's automatic deletion rules in the UI (Trash 21 days, Spam 7 days). 'Not spam' must MOVE the message to INBOX, which trains the filter (R20).
- Quota: read it with GETQUOTAROOT INBOX if QUOTA is advertised, and label the value as approximate (R18).
- Sending: check that the full encoded message is at most 25,600,000 bytes (R14). APPEND the sent copy to Sent yourself (no BURL). Do not request DSN. Treat 4xx replies as throttling and retry from a persistent outbox with exponential backoff (R15). Identities are the account address plus aliases that the user types in, because there is no alias API (R17).
- Header hygiene: Riseup removes the IP and EHLO and appears to remove User-Agent, but it keeps Date and Message-ID (R23). The client should send EHLO '[127.0.0.1]', write Date in UTC (+0000), use a random UUID@riseup.net Message-ID, and send no User-Agent or X-Mailer.
- TLS trust: do not pin the leaf or the intermediate (R9). Riseup's CAA allows only Let's Encrypt. Limit trust for *.riseup.net to the ISRG roots (X1, X2, and later YE/YR) through Network Security Config, with an expiration date so the app falls back to system trust if Riseup changes CA (R9, R10).
- Tor: with the onion host, the client can keep TLS on 993/465 and validate the certificate against the name 'mail.riseup.net' instead of the .onion name. This removes the warnings Riseup describes and adds a second layer of integrity (R16). Ship the onion address from the signed list and let the user override it, because addresses change (September 2026). Use 587 when the connection goes through Tor exits.
- Settings with no protocol: filters, vacation, spam allow-list, aliases and forwarding are available only as web pages. Open account.riseup.net (or its onion) in the browser instead of building UI for them (R19).
- OpenPGP key discovery for riseup.net addresses cannot use WKD (R21). Use Autocrypt headers and manual import, and offer keys.openpgp.org VKS lookup as an opt-in.
- Data safety: Riseup keeps no backups, and a reset through the alternate email wipes the mailbox (R22). If UIDVALIDITY changes or most messages disappear at once, keep the local copies and ask the user before deleting them. Offer a local export.
- Account setup: put a built-in Riseup profile in the app (mail.riseup.net, 993/465, full address as login). The autoconfig file and RFC 6186 SRV records can serve as a cross-check (R2). The network stack must work over IPv4 only (R1).

## Decisions
### How should the app support Tor and Riseup's onion service?
- A. No Tor support: + Simplest. No extra code and no battery cost from Tor. / - Gives up Riseup's strongest privacy feature. No way around censorship.
- B. Optional SOCKS5 proxy to Orbot (127.0.0.1:9050) with the onion host preset: + Uses only java.net.Proxy, so no library is needed. Orbot runs Tor. Works the same for Gmail through exits. / - The user must install and run Orbot. Battery and latency depend on Orbot, and IDLE over Tor is slower.
- C. Embed a Tor client (Arti or tor-android): + Works out of the box in one app. / - A large native dependency that goes against the minimal-library rule. More attack surface, a larger APK, and more battery use.
REC: B: an opt-in per-account 'Use Tor (Orbot)' switch that selects the onion host automatically for Riseup.
### On the onion, should the app use plaintext ports (143/25, as Riseup documents) or TLS ports (993/465)?
- A. Plaintext 143/25 as in Riseup's docs: + Matches Riseup's guide. Tor already gives end-to-end encryption to the onion. / - No second layer of protection, and the password crosses the server's internal path in clear. It is also unverified whether the onion's 143 accepts LOGIN without STARTTLS.
- B. TLS on 993/465, with the certificate validated for the name mail.riseup.net: + Defense in depth with full chain validation and no certificate warnings. / - A small custom HostnameVerifier is needed. It is unverified that the onion serves the same certificate (the Riseup text implies that it does).
REC: B, with fallback to A only if the TLS handshake on the onion fails.
### Which TLS trust policy should apply to Riseup hosts?
- A. System CA store only: + Zero maintenance. Never breaks when certificates rotate. / - Any CA in the store that is compromised or forced to cooperate can issue a certificate the app accepts.
- B. Limit trust to ISRG roots (X1, X2, YE, YR) for *.riseup.net in Network Security Config, with an expiration date: + Matches Riseup's CAA record and Riseup's own advice to 'specify a list of CAs'. Survives the 60-day key and intermediate rotation. / - Breaks if Riseup moves away from Let's Encrypt before the pin expires. The root list needs updates in app releases.
- C. Pin the leaf or intermediate SPKI: + Strongest in theory. / - Breaks about every 60 days (R9). Riseup explicitly tells clients not to do this.
REC: B, with an expiration about 12 months ahead and renewal in each app release.
### Which login-name format should the app send to Riseup?
- A. Full address (user@riseup.net): + Same as autoconfig, K-9 KB and Delta Chat (tested in 2024). One field for the user. / - Some Riseup help pages show the bare username, which can confuse users.
- B. Bare username: + Matches most of Riseup's help pages. / - The app must split the address, and that adds an edge case for users who log in with an alias.
REC: A. If the first auth fails, retry once with the bare username.
### How should the app receive new mail for folders other than INBOX (Riseup filters can deliver to other folders)?
- A. IDLE on INBOX only, and STATUS-poll the other folders when the app opens or a push arrives: + One connection, lowest battery use, simplest code. / - Mail that a filter moves to another folder does not trigger a notification right away.
- B. NOTIFY (RFC 5465) on one connection for the chosen folders, with IDLE as fallback: + One connection with notifications for many folders. / - More parser code. NOTIFY is advertised only in the 2022 data, and Gmail does not support it, so the app needs two code paths.
- C. One IDLE connection per watched folder: + Simple logic. / - Multiplies the argon2 logins, the keepalive radio wakeups and the risk of connection limits.
REC: A for version 1, and B later behind the capability check.
### Should the app offer key lookup on keys.openpgp.org for Riseup contacts, given that WKD is not available?
- A. Autocrypt headers and manual import only: + No extra network calls and no metadata leak to a keyserver. / - The app finds fewer keys.
- B. Opt-in VKS lookup on keys.openpgp.org, through Tor if Tor is on: + Finds keys whose owners verified their email address. / - Each lookup tells the keyserver which contacts the user writes to.
REC: A as the default, and B as an opt-in per lookup.

## Open questions
- What is the current post-auth IMAP CAPABILITY list? The latest public evidence is from 2022, and the 2026-10-06 maintenance may have upgraded Dovecot. Check it on the user's first login and log only the capability string.
- Does Riseup keep persistent Dovecot indexes? The TREES README says to disable them. If they are disabled, HIGHESTMODSEQ may reset between sessions or the server may answer NOMODSEQ, and QRESYNC will not help.
- What are Riseup's actual imap_idle_notify_interval, connection limit per user and IP, and SMTP rate limits? None are published. Measure them at runtime.
- Does account.riseup.net now offer a mail-specific service password? The docs disagree (R5). The user can check the Passwords page in the account manager.
- Over Tor, does the onion's port 143 allow LOGIN without STARTTLS, and does its port 993 serve the mail.riseup.net certificate? This was not probed, because no Tor client was available and installing one was out of scope.
- Is the removal of User-Agent and X-Mailer deliberate server policy? It is inferred from 22 messages and not documented.
- Does submission check that the header From matches the envelope sender and the registered aliases, or only the envelope sender?
- Does Riseup save submitted mail to Sent on the server? It is assumed not; check on first send that no duplicate appears.
- Did the 2026-03-30 'expiring certificate authority' incident involve the public Let's Encrypt chain or an internal CA? This affects how strict the trust policy can be.

## Verifier decision feedback
Most recommendations still hold. Three need a change.

1. TLS trust (keep B, change the build). NSC cannot set an expiration on trust-anchors. Keep the system anchors and add a <pin-set expiration="~12 months"> for riseup.net (includeSubdomains) with the SPKI pins of ISRG Root X1, X2, YE and YR. Do not use a trust-anchors override. Do not pin the leaf or intermediate: there were three different leaf SPKIs in 4 months, and the intermediates went E8 -> YE2 -> YE1.

2. Push (keep 'one long-lived IDLE connection', drop 'no timers needed'). Dovecot's '* OK Still here' keeps the NAT mapping open, but the client still needs a watchdog to detect a dead TCP path: reconnect if no keepalive arrives in about 2.5 x the observed interval, or by about 29 minutes when the interval is 0. Run the connection in a specialUse foreground service (dataSync is limited to 6 h a day on Android 15+). Reconnect on ConnectivityManager network callbacks.

3. Tor onion TLS (keep B, simpler build). Wrap the SOCKS socket with createSocket(sock, "mail.riseup.net", port, true). The standard hostname check and NSC then apply, so no custom HostnameVerifier is needed. Still unverified: whether the onion's 993/465 serves the same certificate. Fall back to plaintext 143/587 only after an explicit user choice.

These hold as stated:
- PLAIN or SASL-IR auth only.
- Full address as the login name, with one retry using the bare name.
- Orbot SOCKS switch, off by default.
- Autocrypt by default; VKS lookup only as an opt-in.
- Polling the other folders with STATUS in version 1.
- Linking out to account.riseup.net for filters, aliases and vacation.
- APPEND to Sent; no DSN.
- The 25,600,000-byte size limit.

Folder handling needs two additions: never rename or delete 'Spam', and use LIST, not LSUB, because Riseup notes that unsubscribed folders are hidden. Label the 'wipe on reset' and argon2 notes as applying to encrypted-storage accounts (all accounts since March 2017).
