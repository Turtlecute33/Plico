# android-push: Android 14-17 platform rules for near-real-time new-mail notifications without FCM and without a server (IMAP IDLE in a foreground service), with minimal battery use. Facts current to 2026-10-16. Android 17 (API 37) has been stable since 2026-06-16. Android 17 QPR2 is in beta.

- [G1|high|confirmed] FairEmail declares its IMAP push service (ServiceSynchronize) and its send service (ServiceSend) as foregroundServiceType="specialUse". The Play, F-Droid and GitHub flavors all do this. The PROPERTY_SPECIAL_USE_FGS_SUBTYPE text says the other types do not fit, or cannot be used on Android 15 because of time limits or the boot-start block. — Subtype text (abridged): 'A foreground service is required to keep a continuous connection to email servers to listen for push messages via IMAP IDLE, for which there is no Firebase Cloud Messaging integration. Other foreground service types do not fit this use case, or can't be used on Android 15 because there are time limits or auto-starting on boot is not allowed. Using the Android work manager isn't an option either.' Permissions: FOREGROUND_SERVICE, FOREGROUND_SERVICE_SPECIAL_USE, SCHEDULE_EXACT_ALARM, WAKE_LOCK, REQUEST_IGNORE_BATTERY_OPTIMIZATIONS, RECEIVE_BOOT_COMPLETED, POST_NOTIFICATIONS. ReceiverAutoStart (exported=true) handles BOOT_COMPLETED (priority 1000), MY_PACKAGE_REPLACED and SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED. The F-Droid and GitHub flavors use dataSync only for ServiceExternal (third-party automation) and mediaPlayback for TTS. Checked at commit 190e477 (2026-10-16).
- [G2|high|confirmed] FairEmail keepalive: the default interval is 15 min per account. It auto-tunes down in 2-min steps after 3 failures, to a floor of 9 min, and locks the interval after 3 successes. The alarm is setExactAndAllowWhileIdle when exact alarms are allowed, otherwise setAndAllowWhileIdle (RTC_WAKEUP, PendingIntent to the FGS). The wakelock is released while waiting. Kernel TCP keepalive (via JNI) is off by default. — Constants: EntityAccount.DEFAULT_KEEP_ALIVE_INTERVAL=15; ServiceSynchronize TUNE_KEEP_ALIVE_INTERVAL_MIN=9, _STEP=2. The keepalive alarm is brought forward to the OAuth access-token expiry. AlarmManagerCompatEx falls back exact→inexact→set() on SecurityException. EmailService: setKeepAlive(false) by default. - [G7|high|confirmed] dataSync cannot host a persistent push connection. For targetSdk 35+, all dataSync FGS together may run 6 h per 24 h. Then onTimeout() is called, and the app must stop within seconds or get RemoteServiceException. No new dataSync FGS can start until the user brings the app to the foreground. dataSync also cannot start from BOOT_COMPLETED. — The 6 h budget is shared across all dataSync services and resets when the user brings the app to the foreground. Trying to start after the budget is used throws ForegroundServiceStartNotAllowedException 'Time limit already exhausted for foreground service type dataSync'. mediaProcessing has the same limit.
- [G8|high|confirmed] specialUse covers 'any valid foreground service use cases that aren't covered by the other foreground service types'. It needs FOREGROUND_SERVICE_SPECIAL_USE plus a <property android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE>. It has no runtime prerequisites and no time limit. Play reviews the free-form use case.
- [G9|high|confirmed] remoteMessaging means 'Transfer text messages from one device to another ... continuity ... when they switch devices' (Play: 'Relay text communication to another device'). connectedDevice means interaction with external Bluetooth/NFC/IR/USB/network devices and needs e.g. CHANGE_NETWORK_STATE or BT/UWB runtime permissions. shortService lasts about 3 minutes and cannot be sticky. None of them describes IMAP push.
- [G10|high|confirmed] BOOT_COMPLETED rule (targetSdk 35+): the docs list dataSync, camera, mediaPlayback, phoneCall, mediaProjection and microphone as blocked. AOSP enforces an allowlist instead: only connectedDevice, health, remoteMessaging, systemExempted, specialUse and location may start from BOOT_COMPLETED. Every other type throws ForegroundServiceStartNotAllowedException. — ActiveServices change ID FGS_BOOT_COMPLETED_RESTRICTIONS=296558535, @EnabledSince(VANILLA_ICE_CREAM), @Overridable. ActivityManagerConstants DEFAULT_FGS_BOOT_COMPLETED_ALLOWLIST. Read from the AOSP main branch; shipped builds and DeviceConfig can differ.
- [G11|high|confirmed] Exemptions that let an app start an FGS from the background (Android 12+). Relevant ones: ACTION_BOOT_COMPLETED, LOCKED_BOOT_COMPLETED or MY_PACKAGE_REPLACED received; an exact alarm fires for a user-requested action; the user interacts with the app's notification; 'The user turns off battery optimizations for your app'. Since targetSdk 35, SYSTEM_ALERT_WINDOW counts only while an overlay window is visible. — The setExactAndAllowWhileIdle javadoc: 'Alarms scheduled via this API will be allowed to start a foreground service even if the app is in the background.' AOSP gives inexact while-idle alarms a temp-allowlist WITHOUT the FGS-start capability (mOptsWithoutFgs).
- [G12|medium|confirmed] Google Play FGS policy: apps targeting 14+ must declare each FGS type in Play Console App content. The declaration needs a functionality description, the user impact if the task is deferred or interrupted, and a video link. Use must be user-perceptible, stoppable by the user, and impossible to defer without harming the user. specialUse is allowed 'in limited scenarios' and is reviewed. No email- or IMAP-specific wording exists. — The 2026 preview policy only removes geofencing as an FGS use case (effective 2027-01-27). FairEmail (Play flavor) and Thunderbird ship specialUse for IMAP IDLE on Play. This is precedent, not a guarantee.
- [G13|high|confirmed] Since 2026-08-31, new Play apps and updates must target API 36 (Android 16); extensions run to 2026-11-01. Every Play build is therefore subject to the API 35 rules (dataSync timeout, BOOT_COMPLETED allowlist).
- [G14|high|confirmed] Android 16 (all apps): JobScheduler, WorkManager and DownloadManager jobs that run alongside an FGS, or that started while the app was on top, now count against runtime quotas. Active-bucket apps also get a (generous) quota. No new FGS-type limit was added in 16.
- [G15|high|confirmed] Android 17 (API 37, stable 2026-06-16) adds no FGS-type, FGS-timeout, alarm or Doze change. Relevant changes: app memory limits for all apps (kill reason 'MemoryLimiter:AnonSwap'). For targetSdk 37: ACCESS_LOCAL_NETWORK runtime permission for LAN hosts, Certificate Transparency on by default, and ECH. Android 17 QPR2 (beta, 2026-10-09): self-broadcasts no longer raise process importance or prevent freezing; Google says not to use them as a timer or keep-alive.
- [G16|high|confirmed] A process with an FGS keeps network access in Doze, in Battery Saver, and under the Android 15+ background-network firewall. AOSP allows network for procState <= BOUND_FOREGROUND_SERVICE (FGS=4, BFGS=5). Background blocking starts at TOP_SLEEPING (12). Google's power table lists 'App process is running a foreground service: Network — No restrictions'. — Android 15 (all apps): 'apps that start a network request outside of a valid process lifecycle receive an exception', with FGS or WorkManager as the recommended fix. AOSP enables FIREWALL_CHAIN_BACKGROUND at init, with a 2-5 s grace delay. Low Power Standby (device feature) allows only TOP or allowlisted apps.
- [G17|high|confirmed] In Doze, partial wakelocks are honored for apps whose procState <= BOUND_FOREGROUND_SERVICE (so an FGS app) or that are on the Doze allowlist. Other apps' wakelocks are disabled. A running FGS does NOT keep the CPU awake: the device still suspends with the screen off. — PowerManagerService.setWakeLockDisabledStateLocked. Docs: 'When the user leaves their Android-powered device idle, it quickly goes into the suspend state'. A wake lock is needed only if suspending during FGS work would hurt the user.
- [G18|high|confirmed] Handler.postDelayed, Thread.sleep, Object.wait and System.nanoTime all run on the uptimeMillis clock, which 'stops when the system enters deep sleep'. So coroutine delay(), Handler timers and socket read timeouts do not fire while the CPU is suspended, even inside an FGS. Only *_WAKEUP AlarmManager alarms wake the device. Incoming packets also wake it, which is why IDLE push works. — SystemClock javadoc; Handler javadoc: 'Time spent in deep sleep will add an additional delay to execution.' Signal PR: a 55 s sleep-based keepalive fired hours late after the screen went off. Reasoned, not doc-confirmed: Linux TCP keepalive timers are not wake sources, so kernel keepalive does not protect NAT state during suspend.
- [G19|high|confirmed] AOSP alarm quotas: per-hour standby-bucket quotas are Active 720, Working 10, Frequent 2, Rare 1, and Restricted 1 per day. setExactAndAllowWhileIdle with exact-alarm permission is exempt from bucket quotas and limited to 72 per hour in Doze. setAndAllowWhileIdle (inexact, targetSdk 31+) is downgraded to the COMPAT class: 7 per hour in Doze and still subject to bucket quotas. — AlarmManagerService: DEFAULT_APP_STANDBY_QUOTAS, DEFAULT_ALLOW_WHILE_IDLE_QUOTA=72, DEFAULT_ALLOW_WHILE_IDLE_COMPAT_QUOTA=7 (both per 1 h window). isExemptFromAppStandby() covers only FLAG_ALLOW_WHILE_IDLE or UNRESTRICTED. The 'once per nine minutes' figure on the Doze page is legacy wording that matches the COMPAT quota. Google's power table: 'While-idle alarms: Limited to 7 per hour' under Doze.
- [G20|high|confirmed] Apps on the user's battery-optimization allowlist get FLAG_ALLOW_WHILE_IDLE_UNRESTRICTED on their alarms ('allow these alarms to go off as normal even while idle, with no timing restrictions'). They are also exempt from SCHEDULE_EXACT_ALARM and their standby bucket is pinned to EXEMPTED. One user grant therefore removes every alarm, bucket and FGS-restart limit. — AlarmManagerService: isUidPowerSaveUserExempt → UNRESTRICTED; isExemptFromExactAlarmPermissionNoLock → isAppOnWhitelist. The Android 14 docs confirm 'Apps on the power allowlist' are always allowed to call setExact and setExactAndAllowWhileIdle. AppStandbyController.getAppMinBucket → EXEMPTED for power-allowlisted packages. The old Doze page still says regular alarms don't fire for exempt apps; that conflicts with current AOSP, so use setExactAndAllowWhileIdle anyway.
- [G21|high|confirmed] Exact alarms: SCHEDULE_EXACT_ALARM is not pre-granted to fresh installs targeting API 33+ on Android 14+. When it is revoked, the app is stopped and all exact alarms are cancelled. USE_EXACT_ALARM is auto-granted, but Play allows it only for alarm/timer and calendar apps, so an email app does not qualify. setExact with an OnAlarmListener needs no permission but is deferred in Doze; listener-based allow-while-idle alarms are @SystemApi.
- [G22|high|confirmed] A running FGS does not keep an app in the Active standby bucket. FOREGROUND_SERVICE_START raises the bucket only on the app's first-ever use, for 30 min. A seen notification raises it to WORKING_SET. Google's table says FGS apps' alarms follow standby-bucket limits. — AppStandbyController: 'Only elevate bucket if this is the first usage of the app'; DEFAULT_INITIAL_FOREGROUND_SERVICE_START_TIMEOUT=30 min; DEFAULT_NOTIFICATION_SEEN_PROMOTED_BUCKET=WORKING_SET.

- [G24|high|confirmed] Android vitals 'excessive partial wake locks': a session is excessive when wakelocks total 2 h or more in 24 h. - [G26|medium|confirmed] Keepalive energy cost (published data): on 3G-era networks, keepalives every 5 min or less used more than 17% of a 1350 mAh battery per day, and 30-min timers less than 2%. LTE (2012): RRC tail 11.576 s at 1060 mW base power, promotion 260 ms at 1210 mW. That is ~12.6 J per wake as an upper bound. Later measurements show much lower LTE tail power. — Derived upper-bound estimate (not measured), 5000 mAh × 3.87 V ≈ 69.7 kJ: 2-min wakes (720/day) ≈ 13%/day; 9-min ≈ 2.9%; 15-min ≈ 1.7%; 28-min ≈ 0.9%. Wi-Fi and modern C-DRX/5G RRC_INACTIVE cost much less. Use these only to rank options, not as absolute figures.
- [G27|high|confirmed] TCP keepalive on Android: Socket.setKeepAlive uses the kernel default (7200 s). android.system.OsConstants exposes SO_KEEPALIVE, TCP_NODELAY and TCP_USER_TIMEOUT, but not TCP_KEEPIDLE, KEEPINTVL or KEEPCNT (Os.setsockoptInt is public). Hardware keepalive offload for TCP sockets (ConnectivityManager.createSocketKeepalive(Network, Socket, ...)) is @SystemApi with PACKET_KEEPALIVE_OFFLOAD. Only the IPsec NAT-T UDP variant is public.
- [G28|medium|confirmed] IMAP: RFC 2177 and RFC 9051 tell clients to end IDLE and send it again at least every 29 min. A server autologout timer, if any, MUST be at least 30 min. - [G31|high|confirmed] Notification styles for email: Android docs say conversation notifications (MessagingStyle plus long-lived shortcut) are for real-time chats, and 'Users don't have that expectation with emails'. - [G32|high|confirmed] Lock screen: VISIBILITY_PRIVATE shows only the icon and content title, and setPublicVersion() supplies a redacted alternative. VISIBILITY_SECRET hides everything. User channel settings always win. POST_NOTIFICATIONS (13+): if denied, the FGS shows only in the Task Manager, not the drawer. — Android 14 lets users dismiss ongoing (FGS) notifications, except on the lock screen and via Clear all. - [G33|high|confirmed] Notification actions: every PendingIntent needs an explicit mutability flag (API 31+). The RemoteInput reply action must be FLAG_MUTABLE and, for targetSdk 34+, must use an explicit intent, or creating it throws. Notification trampolines are banned (API 31+): content taps must open an Activity PendingIntent directly. - [G34|high|confirmed] Restart edge cases: on Android 15, force-stop cancels all of the app's PendingIntents (alarms), and push stays off until the user opens the app. A START_STICKY restart after process death can throw ForegroundServiceStartNotAllowedException on Android 14 (Thunderbird #7416). App hibernation (12+, after months unused) resets permissions and stops background alarms, jobs and push. Notification interaction counts as use; alarms do not.
- [G35|high|confirmed] Network callbacks: registerDefaultNetworkCallback tracks the single default network. onLost means it lost default status. onCapabilitiesChanged and onLinkPropertiesChanged follow onAvailable (8.0+). Do not call synchronous ConnectivityManager queries inside callbacks. Callback count is capped per app. NET_CAPABILITY_VALIDATED is the system's best guess of real internet access.

## Missed facts
- Dovecot aligns its 'Still here' IDLE keepalives by client. imap_keepalive_interval_msecs() shortens the first interval by (time + hash(public client IP)) mod interval. It falls back to a hash of the username only for private or unknown IPs. So every IDLE connection from one phone to the same Dovecot server fires in the same second: all folders and all Riseup accounts on that phone. Dovecot also resets its idle-disconnect timer on each keepalive, so it allows IDLE forever. — WHY: The report's '720 wakes/day per account' is wrong for several Riseup accounts or folders. The cost is about 720 wakes/day per server per phone, if the interval is the 2-min default. This lowers the cost of option D5-A. It also means the client can piggy-back its refresh on server keepalives with zero extra alarm wakes.
- For a battery-allowlisted app, AOSP sets FLAG_ALLOW_WHILE_IDLE_UNRESTRICTED on EVERY alarm it sets. This includes the public setExact(type, t, tag, OnAlarmListener, Handler), which needs no permission. Such an alarm fires on time in Doze without SCHEDULE_EXACT_ALARM, a PendingIntent or a BroadcastReceiver, as long as the FGS process is alive. — WHY: In the D2-A path, an in-process listener alarm can replace the AlarmReceiver and the exact-alarm permission. This is less manifest and less code. The source is AOSP main only, so test it on OEM builds. Keep the PendingIntent path for the D2-B and D2-C fallback, and take a wakelock in onAlarm.
- The BOOT_COMPLETED type check runs only if the aconfig flag fgsBootCompleted is on AND the FGS start reason recorded is REASON_BOOT_COMPLETED. It tests (type & allowlist) != 0. — WHY: specialUse is safe in all cases. An app whose start is attributed to another exemption (for example the battery allowlist) may not hit the check at all. Do not rely on this; it only explains device differences seen in tests.
- Task Manager 'Stop' kills the app, but alarms and jobs stay scheduled. A keepalive or backoff alarm that targets the FGS would restart push after the user stopped it. — WHY: Play requires that an FGS 'can be terminated or stopped by the user'. At start, check ApplicationExitInfo REASON_USER_REQUESTED and stay stopped, or show a choice. Do not silently restart.
- Play's FGS criteria also say the service must 'run only for as long as necessary to complete the task'. Google's 2026-03 battery-enforcement post recommends FCM over socket connections for remote-messaging use cases. — WHY: This raises Play review risk for a permanent specialUse FGS plus the battery-exemption prompt (D3-B). The specialUse text and video must explain why the IMAP push task is continuous and why FCM is technically impossible.
- Thunderbird passes FOREGROUND_SERVICE_TYPE_DATA_SYNC to startForeground on API 29-33. FairEmail calls 2-arg startForeground on all versions. — WHY: The design note 'On API < 34 … Thunderbird and FairEmail ship this way' is half wrong. With minSdk 34 (D4-A) it does not matter.
- From Android 16, jobs of battery-unrestricted apps are no longer exempt from job runtime quotas ('Prior to Android 16 there was no execution limit when … the user unrestricted the app battery'). — WHY: The D2-A 'removes every limit' claim does not cover jobs. This supports D8-A (in-process actions) over a WorkManager path.
- The Riseup IMAP certificate chain is Let's Encrypt YE1 → ISRG Root YE → ISRG Root X2 → cross-signed by ISRG Root X1. The leaf is valid only to 2026-11-16, and its SAN covers imap/mail/pop/smtp.riseup.net. imap.riseup.net and mail.riseup.net resolve to different IPs but give the same banner and capabilities. — WHY: Leaf or intermediate pinning will break often with short-lived LE certificates. Use the platform trust store, and CT (default for targetSdk 37). If you pin, pin only to ISRG roots.

## Implications
- Short version: use one specialUse FGS that holds one IMAP IDLE connection per account (INBOX only). Ask the user once to disable battery optimization. Drive every timer from a single coalesced ELAPSED_REALTIME_WAKEUP alarm (setExactAndAllowWhileIdle). Hold a partial wakelock only while bytes are being processed. Reconnect on network-callback events, with alarm-driven backoff. This is the FairEmail/Thunderbird pattern, cut down to its minimum. [G1,G4,G5,G7,G10,G20]
- FGS type: specialUse only. dataSync stops after 6 h/24 h and cannot start at boot (G7,G10). remoteMessaging and connectedDevice describe other use cases and invite a Play rejection (G9). shortService lasts about 3 min (G9). On API < 34, call ServiceCompat.startForeground without a type (or with 0); Thunderbird and FairEmail ship this way. [G1,G4,G6,G8]
- Manifest (core): INTERNET, ACCESS_NETWORK_STATE, POST_NOTIFICATIONS, FOREGROUND_SERVICE, FOREGROUND_SERVICE_SPECIAL_USE, RECEIVE_BOOT_COMPLETED, WAKE_LOCK, plus REQUEST_IGNORE_BATTERY_OPTIMIZATIONS and/or SCHEDULE_EXACT_ALARM per decision D2. Do NOT declare USE_EXACT_ALARM (Play-ineligible), FOREGROUND_SERVICE_DATA_SYNC, SYSTEM_ALERT_WINDOW or ACCESS_LOCAL_NETWORK (Riseup and Gmail are public hosts). [G21,G15]
- Manifest components: <service android:name=".push.PushService" android:exported="false" android:foregroundServiceType="specialUse"> with <property android:name="android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE" android:value="Keeps a user-enabled IMAP IDLE connection to the user's own mail servers to show new-mail notifications in real time; the servers offer no FCM; dataSync has a 6 h limit and cannot start at boot"/>. Add <receiver .push.StartReceiver exported=false enabled=false> for BOOT_COMPLETED, MY_PACKAGE_REPLACED and, if used, android.app.action.SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED; enable it by code only while push is on (Thunderbird pattern). Add <receiver .push.AlarmReceiver exported=false> and <receiver .notify.ActionReceiver exported=false>. [G4,G10,G33]
- Do not use LOCKED_BOOT_COMPLETED. Credentials and the mail DB belong in credential-encrypted storage, so connect only after the first unlock (BOOT_COMPLETED). [G11]
- Power grant hierarchy. The user battery-optimization exemption gives unrestricted alarms in Doze, exemption from the exact-alarm permission, the EXEMPTED bucket, and background FGS restart (G20,G11). SCHEDULE_EXACT_ALARM gives 72 while-idle alarms/h, bucket exemption, and FGS start from the alarm, but no bucket pinning for other work (G19,G21). With neither, setAndAllowWhileIdle gets 7/h in Doze and bucket quotas (Rare = 1/h), so a 15-min keepalive WILL slip and connections die. Show a clear 'push degraded' state in that case, as Thunderbird does with ALARM_PERMISSION_MISSING (G5,G19,G22).
- Never rely on coroutine delay(), Handler, Thread.sleep or socket SO_TIMEOUT for keepalive or dead-peer detection while the screen is off. They run on uptime and freeze in suspend (G18). Kernel TCP keepalive also gives no protection during suspend, and TCP keepalive offload is system-only (G27). The single source of client-initiated timing is AlarmManager *_WAKEUP. Keep coroutine delays only for in-session timeouts while a wakelock is held.
- Wakelock policy: release before blocking on the IDLE read (Thunderbird pattern, G5). Take a timeout-bounded partial wakelock (for example 30-60 s) when the read returns or an alarm fires. Release in finally after the notification is posted or IDLE is re-armed. Budget target: under 10 min/day, far below the 2 h/24 h vitals threshold that counts FGS wakelocks (G24).
- Keepalive policy (server-aware plus adaptive). (1) Measure server-initiated untagged traffic during IDLE (for example Dovecot 'OK Still here' every 2 min). If the server talks every ≤5 min, the NAT stays fresh, so set the client alarm to about 25 min: one DONE/IDLE cycle for the RFC 29-min rule, plus a liveness check that lastServerByteAt (elapsedRealtime) is within 2× the server cadence. (2) If the server is silent (expected for Gmail, unverified), start at 15 min per account and per transport (Wi-Fi vs cellular). After 2-3 refreshes that find the socket dead, with no network change in between, lower by 2 min, floor 9 min. Lock the value after 3 successes, unlock on a later failure, and re-learn on network change (FairEmail-style, G2). (3) Ceiling 28 min (G28). (4) Coalesce all accounts into one alarm and refresh every connection due within the next ~3 min in the same wake, so they share one radio tail (Thunderbird BackendIdleRefreshManager, G5,G26).
- Network identity for learned intervals: key by transport type plus a hash of the default network's LinkProperties (DNS servers, IPv6 /64 prefix, interface). Never read Wi-Fi SSID/BSSID (needs location permission; privacy). Store only the hash, locally. [G35]
- Refresh step: DONE, wait for the tagged OK, IDLE, wait for '+'. Use a short in-session timeout (about 20 s) under the wakelock. Set TCP_USER_TIMEOUT (OsConstants, public) on the socket to about 20-30 s so writes on a dead path fail fast instead of after minutes of retransmits. If the refresh fails, reconnect. [G27]
- Reconnect algorithm: event-driven first. registerDefaultNetworkCallback once inside the FGS. On onAvailable(new default network), on onCapabilitiesChanged gaining VALIDATED, or on onBlockedStatusChanged(false), reconnect after a 2 s debounce and reset the backoff. Do not hard-require VALIDATED, since VPNs and captive portals break it (FairEmail note). On onLost or no default network, close sockets, cancel the alarm and wait. Error classes: AUTHENTICATIONFAILED or a TLS/certificate error means no automatic retry; post an actionable notification (security and lockout safety). IOException, BYE or [UNAVAILABLE] means backoff: 1 immediate retry, then 5 s and 20 s in-process under a ≤30 s wakelock, then alarm-driven 2, 5, 15, 30, 60 min (cap), each with ±20% jitter. Reset on success or network change. Refresh the OAuth token (Gmail) at the keepalive wake that comes just before expiry, as FairEmail does. [G3,G35]
- Single long-lived FGS: start it from foreground UI, BOOT_COMPLETED, MY_PACKAGE_REPLACED, the exact-alarm or AlarmReceiver path, or a notification action. Signal the running engine in-process (Kotlin Flow/Channel); never use self-broadcasts (Android 17 QPR2, G15). Catch ForegroundServiceStartNotAllowedException on START_STICKY restarts (G34). Implement onTimeout() defensively even though specialUse has no timeout.
- FGS notification: its own channel at IMPORTANCE_LOW (not MIN, which triggers the system warning, G32). Silent, no badge. Content shows a privacy-neutral status ('Connected to 2 accounts') with no addresses. Expect that users may dismiss it (Android 14+) or deny POST_NOTIFICATIONS; push keeps running in both cases. [G32]
- New-mail notifications: one channel per account (users can set sound and lock-screen policy per account). Per message, a BigTextStyle child (sender, subject, snippet only if the user allows it). One InboxStyle summary per account group with GROUP_ALERT_SUMMARY, so a burst makes one sound (also avoids the Android 15+ cooldown and 16 auto-grouping surprises). setOnlyAlertOnce on updates. No MessagingStyle or conversation shortcuts (Google says email is not a conversation). [G31]
- Lock screen default: VISIBILITY_PRIVATE with setPublicVersion('N new messages — <account label>'), with no sender or subject. Offer a per-account switch to SECRET. Use category CATEGORY_EMAIL and Person/sender only in the private version. [G32]
- Notification actions (Archive, Delete, Mark read, Reply): ActionReceiver exported=false uses goAsync() and hands the job to the already-running push engine. That process is FGS, so it has network in Doze (G16). Finish within 10 s and fall back to a WorkManager expedited job if the engine is not running. Remember Android 16 job quotas also apply while an FGS runs (G14). Reply uses FLAG_MUTABLE with an explicit component; all other actions use FLAG_IMMUTABLE. Content taps open the Activity directly (no trampoline). [G33]
- Riseup (Dovecot): if 'OK Still here' arrives every 2 min, the radio and CPU wake about 720 times a day per account no matter what the client does. The upper-bound estimate is about 13%/day on LTE-era figures (G26,G28). Only the server admin can change this. The client can choose push (accept the cost) or periodic polling (see decision D5).
- Distribution split: the Play flavor needs the specialUse declaration with video, an exemption justification (IMAP IDLE to third-party servers; FCM technically impossible), and vitals wakelock hygiene. The F-Droid flavor uses the same code. Keep one manifest and use no Google libraries (no Play Services, no Firebase) in both builds. [G12,G23,G24,G36]
- Hibernation: offer IntentCompat.createManageUnusedAppRestrictionsIntent only if the user rarely opens the app. Notification taps already count as usage. [G34]

## Decisions
### D1: Which foreground service type should the push service declare?
- A) specialUse only: + Only type with no time limit that is still allowed from BOOT_COMPLETED. Same choice as FairEmail (Play and F-Droid) and Delta Chat FOSS. Simplest manifest. / - Play needs a free-form justification and a video, reviewed by hand. On API < 34 the type is unknown, but shipping apps show it works.
- B) dataSync|specialUse (Thunderbird style: dataSync on API 29-33, specialUse on 34+): + Exact type semantics on old Android versions. / - More code and a second permission. Gives nothing on 34+. Pointless if minSdk is 34.
- C) remoteMessaging or connectedDevice: + No specialUse review text. / - Neither describes IMAP push (G9), so Play rejection or removal is likely. Not honest to the user.
REC: A
### D2: How should the app get timely keepalive wakeups in Doze?
- A) Ask the user to disable battery optimization (direct prompt; declares REQUEST_IGNORE_BATTERY_OPTIMIZATIONS): + One grant removes every limit: unrestricted alarms, no exact-alarm permission needed, EXEMPTED bucket, background FGS restart, wakelocks and network in Doze (G20,G23). Fewest permissions. / - Play may question it: email is not named, though 'can't use FCM due to technical dependency' fits. Some users distrust the prompt.
- B) Exact-alarm permission only (SCHEDULE_EXACT_ALARM; Thunderbird style): + Lower Play risk. 72 while-idle alarms/h. Bucket-exempt alarms. Alarm can start the FGS. / - Denied by default on 14+, so the user must go to Settings. Revocation stops the app. No protection for non-alarm restarts or bucket decay.
- C) A with B as fallback (FairEmail style): + Most robust across OEMs and user choices. / - Two permissions and two flows to explain. Slightly more code.
- D) Neither (inexact setAndAllowWhileIdle only): + No special permission. / - 7 alarms/h in Doze plus bucket quotas (Rare = 1/h), so connections silently die. Fails the near-real-time requirement.
REC: A for the F-Droid build. C if you also publish on Play, where A is shown first and B is offered only if the user declines A.
### D3: Where will the app be distributed?
- A) F-Droid / direct APK only: + No Play declarations, video or vitals enforcement. Battery prompt needs no justification. Fits the privacy-first goal. / - Smaller audience. Google developer verification starts covering more install sources from 2027 (G36).
- B) Play + F-Droid (same code, no Google libraries): + Wider reach. Precedent from FairEmail and Thunderbird shows specialUse IMAP push is accepted. / - Review risk for specialUse and the battery exemption. Must keep wakelocks well under 2 h/24 h (G24). Must target API 36 now (G13).
REC: B with one manifest. If you want zero policy friction, start with A and add Play later.
### D4: What minSdk should the app use?
- A) minSdk 34 (Android 14): + specialUse exists natively, no version branches for FGS types or exact alarms, smallest code. Matches 'modern'. / - Excludes Android 12-13 devices.
- B) minSdk 31 (Android 12): + Wider device reach. Still has exact-alarm, PendingIntent-mutability and FGS-restriction semantics. / - Version branches for startForeground type, POST_NOTIFICATIONS (33) and the exact-alarm default.
- C) minSdk 26-29: + Maximum reach. / - Much more compatibility code. Contradicts the elegance goal.
REC: A, or B if you need Android 12/13 users.
### D5: For Riseup, if the server sends 'OK Still here' every 2 min (Dovecot default), what should the app do?
- A) Always keep push (instant mail, accept the battery cost): + Fastest notifications. Simplest. / - About 720 server-initiated wakes/day per account. Upper-bound estimate about 13%/day on cellular (G26).
- B) Auto-switch that account to periodic polling (e.g., 15 min) when server keepalive ≤3 min (FairEmail auto-optimize): + Large battery saving. Automatic. / - Up to 15 min delay. Silently changes behaviour.
- C) Per-account toggle 'Instant (more battery) / Every N min', defaulting to Instant on Wi-Fi and polling on cellular: + User keeps control. Cellular is where the cost is. / - One more setting. Needs a transport-change hook (already exists for reconnect).
- D) Ask Riseup to raise or disable imap_idle_notify_interval: + Fixes it for everyone. / - Outside your control. Unknown answer.
REC: C, and also try D. First measure the real interval with your own account (see open questions).
### D6: Which notification layout should new mail use?
- A) Per-message BigTextStyle children + InboxStyle summary per account (GROUP_ALERT_SUMMARY): + Google's documented email pattern. Per-message actions. One sound per burst. / - A little more code than a single notification.
- B) One InboxStyle notification per account, updated in place: + Minimal code. No group logic. / - No per-message actions. Weak on many messages.
- C) MessagingStyle conversations: + Rich chat-like UI. / - Google says email is not a conversation (G31). Needs long-lived shortcuts. Over-engineered.
REC: A
### D7: What should the lock screen show by default?
- A) VISIBILITY_PRIVATE + public version 'N new messages · <account label>': + No sender or subject leak. Still useful. User can relax it per channel. / - Less information at a glance.
- B) VISIBILITY_SECRET: + Maximum privacy. / - Users may miss mail. Feels broken to some.
- C) VISIBILITY_PUBLIC: + Most convenient. / - Leaks sender and subject on a locked phone.
REC: A as the default, with a per-account option for B.
### D8: How should notification actions run?
- A) goAsync() receiver → in-process push engine (already FGS, has network in Doze), WorkManager expedited only as fallback: + Fastest. No job quota. Minimal code. / - Must finish in under 10 s or hand off.
- B) Always WorkManager expedited work: + Uniform. Survives process death. / - Android 16 job quotas apply even while the FGS runs (G14). Extra dependency path. Slower.
REC: A

## Open questions
- Riseup after login: is the imap_idle_notify_interval really 2 min, and do NOTIFY, QRESYNC or COMPRESS appear in post-login CAPABILITY? Only you can measure this, with your own account: log in by hand, SELECT INBOX, IDLE, and time the '* OK Still here' lines. I did not log in, per the task rules.
- Gmail: how long does it allow an IDLE to run before closing it (10 min or about 29 min; reports conflict), and does it send any untagged keepalive during IDLE? This sets the starting keepalive value and needs a measurement with your account.
- What are the real NAT idle timeouts of your carrier (CGNAT) and your home router today? The only cellular survey is from 2011. The adaptive algorithm handles this, but a quick measurement would set better defaults.
- Will Play review accept a new app's specialUse IMAP-IDLE declaration together with the battery-exemption prompt in 2026? FairEmail and Thunderbird are precedent, but reviews are manual and inconsistent.
- Several findings come from the AOSP main branch: alarm quotas 72/7 per hour, the unrestricted allowlist path, the BOOT_COMPLETED allowlist, FGS wakelocks in Doze. Shipped Pixel/OEM builds and DeviceConfig flags can differ, and OEM battery managers (Samsung, Xiaomi) may still kill the FGS. These need device tests on your own phones.
- Android 17 QPR2 (stable expected December 2026) and Android 18 previews could change background rules. Re-check the behavior-change pages before release.
- No primary source was found for current 5G NR (RRC_INACTIVE) keepalive energy. The battery percentages here are upper-bound estimates from 2011-2012 measurements and should be checked with Battery Historian / Perfetto on target devices.

## Verifier decision feedback
D1 (specialUse only) holds. AOSP and docs confirm that it is the only fitting type with no time limit that is allowed from BOOT_COMPLETED. D2 holds: A for F-Droid, C for Play. Two changes. First, in path A, an in-process OnAlarmListener setExact can replace the AlarmReceiver, because AOSP gives allowlisted apps UNRESTRICTED alarms. Second, A does not remove Android 16 job quotas. Note that Thunderbird gets onto Play with SCHEDULE_EXACT_ALARM only and no battery prompt; that is the lower-risk Play path. D3 holds, but Play risk is higher than the report says: the 'runs only as long as necessary' criterion, and the 2026 battery post that pushes FCM for remote messaging. D4-A holds, and it removes the Thunderbird DATA_SYNC branch question. D5 needs a fix: Dovecot keepalives are phase-aligned per client IP, so the cost is about 720 wakes/day per phone per server, not per account. C plus measurement is still right. Change the keepalive policy (1). On Dovecot, do not use a separate ~25-min client alarm. Re-arm one dead-peer alarm on every byte from the server, at about 2.5x the measured server cadence; it fires only if the server goes silent. Do the DONE/IDLE refresh (optional on Dovecot, which allows IDLE forever) during a server-keepalive wake. This gives dead-peer detection in about 5 min with zero extra wakes. For Gmail (silent server, cut-off unknown), the adaptive 15→9 min alarm policy still holds. D6, D7 and D8 hold. For D8, skip the WorkManager fallback where you can, because Android 16 quotas apply even to battery-unrestricted apps. Add one rule: after a Task Manager Stop (REASON_USER_REQUESTED), do not let surviving alarms restart push without the user. The reconnect trigger also works on onBlockedStatusChanged(false), which comes after onAvailable on API 29+ (Delta Chat pattern). Small fixes elsewhere: FairEmail auto-optimize is off by default and its code threshold is 9 min, and the 2025 gateway study tested 23 devices.
