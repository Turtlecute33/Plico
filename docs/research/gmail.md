# gmail: Gmail as an IMAP/SMTP provider for a third-party Android client (auth, endpoints, capabilities, Gmail extensions, feature emulation, IDLE, SMTP, 2025-2026 changes), status 2026-10-16

- [G1|high|confirmed] Password-only access ("less secure apps") is fully gone for IMAP, SMTP, POP, CalDAV and CardDAV. The only accepted credentials are OAuth 2.0 and app passwords. — Consumer accounts lost the LSA toggle on 2022-05-30 (secondary source). For Workspace, the Workspace Updates blog moved the final cut-off several times: 2024-09-30, then a pause, then 2025-03-14, then 2025-05-01 (update dated 2025-04-29). The Admin Help page (updated 2026-10-13) still shows 2025-03-14. It says: "You will no longer use a password for access (with the exception of app passwords)." One secondary blog says Workspace also blocks app passwords. Google's own pages contradict this blog.
- [G2|medium|confirmed] App passwords still work in 2026. They need 2-Step Verification. They are not available when 2SV uses only security keys, on some work or school accounts, or with Advanced Protection. Google revokes them when the account password changes. I found no official Google announcement that deprecates them. — Google says: "App passwords aren't recommended and are unnecessary in most cases." Advanced Protection blocks app passwords and revokes existing ones on enrolment. An isync-devel log from 2024-12-19 shows a working IMAP login on a consumer account with an app password. Blogs that claim a 2026 phase-out (getmailbird, mailtester) give no Google source. 'No deprecation' rests on absence of evidence, so I rate it medium.
- [G3|high|confirmed] Consumer Gmail: IMAP is always on since January 2025, and users cannot turn it off. Workspace: admins can still turn POP and IMAP off. They can also limit IMAP to an allowlist of OAuth client IDs ("OAuth mail clients only").
- [G4|high|confirmed] SASL mechanisms (live probe 2026-10-16). imap.gmail.com:993 before login shows AUTH=XOAUTH2, AUTH=PLAIN, AUTH=PLAIN-CLIENTTOKEN, AUTH=OAUTHBEARER and SASL-IR. smtp.gmail.com on 465, and on 587 after STARTTLS, shows AUTH LOGIN PLAIN XOAUTH2 PLAIN-CLIENTTOKEN OAUTHBEARER XOAUTH. On 587, EHLO before STARTTLS shows no AUTH. — XOAUTH2 initial response = base64("user=" email ^A "auth=Bearer " token ^A ^A). With SASL-IR the login takes one round trip. On failure, the server sends a base64 JSON challenge {status, schemes, scope}. The client must answer it with an empty response. The scope for IMAP, SMTP and POP is https://mail.google.com/ (gmail.imap_admin is only for Workspace domain-wide delegation). The legacy OAuth1 AUTH=XOAUTH no longer shows in the IMAP pre-auth list (an older gist still lists it). SMTP still shows XOAUTH. OAUTHBEARER (RFC 7628) is an alternative to XOAUTH2.
- [G5|medium|corrected] https://mail.google.com/ is a RESTRICTED scope. To ship it publicly, the app needs restricted-scope verification. Google requires a CASA security assessment for apps that can access the data "from or through a third-party server". The assessment repeats every 12 months. — All Gmail read and modify scopes are restricted (readonly, compose, insert, modify, metadata, settings.basic, settings.sharing). Only gmail.send is 'sensitive', and IMAP cannot use it. Google charges no fee, but the assessor does: FairEmail's FAQ quoted $15k-75k per year. Google estimates about 6 weeks for verification, plus the assessment. Whether a client that runs only on the device is exempt is disputed. Google's text ties the assessment to servers, and Kanmail's developer reported no audit. But Thunderbird for Android and K-9 completed CASA Tier 2, and FairEmail's developer says Google stopped treating his app as a 'local client' when it used browser OAuth.

- [G6|high|confirmed] An app for personal use can use its own OAuth client ID with https://mail.google.com/ and skip verification. Set it to External and publish it 'In production'. Users click through the 'unverified app' screen. Unverified apps have a 100-new-user cap for the lifetime of the project, and nobody can reset it. — Google: "If the app is for your personal use (fewer than 100 users), you and your limited number of users can continue using the app without going through verification (users will be allowed to click through 'unverified app' warning screens during sign-in)." With Testing status: at most 100 listed test users, and "Authorizations by a test user will expire seven days from the time of consent". A refresh token with a 7-day life is unusable for a mail client. A mutt-users post from 2025-06-08 shows exactly this problem. One unverified report says Publish needs a homepage URL, a privacy-policy URL and an authorized domain.
- [G7|high|confirmed] A production refresh token stops working when: the user revokes it; it is unused for 6 months; the password changes and the token has Gmail scopes; the account has more than 100 live refresh tokens for one client ID (Google drops the oldest without warning); a time-based grant expires; or an admin restricts the service. — The access token lives about 1 hour. The client must handle invalid_grant: show a re-auth prompt and do not retry in a loop. Revocation endpoint (from the discovery document): https://oauth2.googleapis.com/revoke. Call it when the user removes the account.
- [G8|high|confirmed] An IMAP session that logged in with OAuth lasts only as long as the access token, usually about 1 hour. Then Gmail closes the TCP connection. A session that logged in with a password or app password lasts up to about 24 hours. A POP session lasts up to about 7 days. — Verbatim: "If you authenticated the session using OAuth credentials, it lasts approximately the validity period of the access token used (usually 1 hour)." Gmail sends a 'session expired' message and then disconnects. IMAP cannot authenticate again on an open connection, so the client must reconnect with a fresh token. Page updated 2026-09-15.
- [G9|medium|confirmed] Android redirect options for Google OAuth. Custom URI scheme: since 2023-10-02, new Android clients cannot use it by default, but you can turn it on under 'Advanced Settings'. The current Google doc (updated 2026-10-15) says "Custom URI schemes are no longer supported on Android and Chrome apps". Loopback: blocked for Android, iOS and Chrome client types since 2022 and still allowed for the Desktop type. OOB: gone. Embedded WebView: blocked (disallowed_useragent). Device flow: does not allow Gmail scopes. — Loopback: new clients blocked from 2022-03-14 and all clients from 2022-10-21. OOB: fully deprecated by 2023-01-31. WebView: final block on 2023-07-24, so use Custom Tabs or the system browser. Three FOSS apps still use package-name custom schemes with AppAuth and Google: Thunderbird Android `${APPLICATION_ID}:/oauth2redirect`, FairEmail `eu.faircode.email:/`, and DAVx5 `${packageName}:/oauth2/redirect`. Their client IDs are older. I could not confirm that a client ID created in Oct 2026 can still turn on custom schemes. App Links (https redirect) need a Web-type client, a client secret and a hosted assetlinks.json. This is from my own knowledge and is not verified for Google; FairEmail uses App Links plus a jump page for other providers. AppAuth-Android: the last tag is 0.11.1 and the last commit is 2026-03-22.
- [G10|medium|corrected] PKCE: Google's discovery document lists code_challenge_methods_supported = [plain, S256], so use S256. Android-type clients send no client_secret. Google's preferred Android path is the Google Identity Services AuthorizationClient (play-services-auth). It needs Google Play services. It gives 1-hour access tokens on the device, and refresh tokens only through a serverAuthCode exchanged on a backend. — The AuthorizationClient docs (updated 2025-10-27) do not mention restricted scopes. The docs show no way to get a refresh token without a backend. Because of the Play services dependency, this path does not work on de-Googled ROMs.

- [G11|medium|confirmed] Advanced Protection allows only verified third-party apps to read Gmail data. It also blocks app passwords. So a personal unverified client ID, and app passwords, will not work on Advanced Protection accounts. — A K-9 forum thread (older) reports that K-9's OAuth was blocked under Advanced Protection while Thunderbird desktop was allowed.
- [G12|high|confirmed] Endpoints. imap.gmail.com:993 uses implicit TLS, and port 143 is closed. pop.gmail.com:995. smtp.gmail.com:465 uses implicit TLS and 587 uses STARTTLS. Thunderbird also maps imap/smtp.googlemail.com. The hosts answer over IPv6.
- [G13|high|confirmed] TLS (live probe). imap.gmail.com negotiates TLS 1.3 (TLS_AES_256_GCM_SHA384) and TLS 1.2. It STILL accepts TLS 1.0 and 1.1 when the client offers them. The client must therefore enforce a minimum of TLS 1.2 or 1.3 itself. Chain: GTS Root R1 -> WR2 -> CN=imap.gmail.com.
- [G14|high|confirmed] IMAP capabilities before login (live): IMAP4rev1 UNSELECT IDLE NAMESPACE QUOTA ID XLIST CHILDREN X-GM-EXT-1 XYZZY SASL-IR AUTH=XOAUTH2 AUTH=PLAIN AUTH=PLAIN-CLIENTTOKEN AUTH=OAUTHBEARER. The greeting and the ID response echo the client's public IP ('Gimap ready for requests from <IP>', remote-host).
- [G15|medium|confirmed] Capabilities after login (from logs, 2024): IMAP4rev1 UNSELECT IDLE NAMESPACE QUOTA ID XLIST CHILDREN X-GM-EXT-1 UIDPLUS COMPRESS=DEFLATE ENABLE MOVE CONDSTORE ESEARCH UTF8=ACCEPT LIST-EXTENDED LIST-STATUS LITERAL- SPECIAL-USE APPENDLIMIT=35651584. QRESYNC, NOTIFY, IMAP4rev2, OBJECTID, SORT, THREAD and METADATA are NOT advertised. — Requested items: IDLE yes, CONDSTORE yes, QRESYNC NO, COMPRESS=DEFLATE yes, SPECIAL-USE yes (Google: the attributes are in every LIST reply even without the capability), UIDPLUS yes, MOVE yes, ENABLE yes, UTF8=ACCEPT yes, ID yes, NAMESPACE yes (("" "/")) NIL NIL, LIST-EXTENDED yes, ESEARCH yes, NOTIFY NO, X-GM-EXT-1 yes, XLIST advertised but deprecated since 2013. I could not log in to re-check this list in 2026.
- [G16|high|corrected] Gmail IMAP extensions (X-GM-EXT-1). X-GM-LABELS: FETCH, STORE +/- and SEARCH; system labels such as \Inbox \Sent \Drafts \Important; values in modified UTF-7. X-GM-MSGID: 64-bit, the same as the Gmail API id in decimal, fetchable and searchable. X-GM-THRID: the thread id, fetchable and searchable. X-GM-RAW: full Gmail web search syntax in SEARCH and UID SEARCH. Labels act as folders (CREATE, RENAME, DELETE). System labels have the prefix [Gmail] or [GoogleMail]. — Google 'strongly recommend[s]' that clients send IMAP ID with a contact address. This is optional and is a privacy trade-off. Folder names change with the Gmail display language (e.g. Spanish '[Gmail]/Todos'). Find special folders by their attributes (\All \Drafts \Important \Sent \Junk \Flagged \Trash), never by name.
  >> VERIFY corrected: The alternative system prefix is '[Google Mail]' with a space, as seen on UK and German accounts, not '[GoogleMail]'. The doc's own list of system labels is \Inbox \Sent \Important \Drafts \Junk \Flagged \Trash. Google says X-GM-LABELS values are "encoded in UTF-7 as appropriate". All other points are confirmed: X-GM-MSGID is a 64-bit unsigned decimal of the web/API hex id; X-GM-THRID can be fetched and searched; X-GM-RAW is "interpreted in the same manner as in the Gmail web interface"; and the IMAP ID 'strongly recommend' quote with a contact address is accurate. | evidence: imap-extensions doc (updated 2026-09-15), quoted directly. - [G17|medium|confirmed] X-GM-RAW accepts these operators: category:primary|social|promotions|updates|forums|reservations|purchases, is:important, is:starred, is:unread, in:snoozed, label:, has:userlabels, list:, deliveredto:, rfc822msgid:, in:anywhere, older_than/newer_than and others. - [G18|medium|confirmed] Mapping Gmail features to IMAP. [Gmail]/All Mail (\All) holds everything except Spam and Trash. Archive = remove the \Inbox label: UID STORE -X-GM-LABELS (\Inbox), or MOVE from INBOX to All Mail. With default settings, delete or expunge in a label folder removes only that label. To trash reliably, MOVE to the \Trash folder; this removes all labels. To delete forever, set \Deleted and EXPUNGE inside Trash. Spam = MOVE to \Junk. Star = \Flagged ([Gmail]/Starred). Important = [Gmail]/Important, or the \Important label. — Gmail help: "Don't save deleted messages on the server". Messages deleted in IMAP stay in All Mail. Trash and Spam empty themselves after 30 days. FairEmail (FAQ 153) reports that the web settings for Auto-Expunge and 'expunged from the last visible folder' no longer work reliably. FairEmail therefore moves to Trash and then expunges. Quirk: STORE -FLAGS (\Flagged) cannot remove a star that was set in the web UI. Sources disagree on whether All Mail includes Drafts and Sent: secondary sources say yes, FairEmail FAQ 195 says no.
- [G19|medium|confirmed] Snoozed messages are not visible over IMAP: there is no Snoozed folder, and third-party apps cannot set snooze. Categories (tabs) are not folders. A client can only read them through X-GM-RAW searches, or after a Gmail filter copies them to a real label. Scheduled send has no IMAP or SMTP mechanism. Undo send must be a delay in the client. — FairEmail: "Third party apps do not have access to the Gmail snoozed messages folder." I could not confirm that the Gmail API supports snooze or scheduled send either (medium).
- [G20|high|confirmed] Conversations: X-GM-THRID gives Gmail's own threading. UID SEARCH X-GM-THRID <id> in All Mail returns the whole thread, including your own replies.
- [G21|medium|confirmed] Send-as. smtp.gmail.com replaces the From address with the logged-in account's address, unless From is a verified 'Send mail as' address in that account's Gmail settings. You use the same credential (OAuth token or app password) for every alias. The limit is 99 addresses. From January 2027, Gmail stops supporting Send-as for third-party (non-Google) addresses, and also ends Gmailify and POP fetch. Gmail addresses and Workspace aliases are not affected. — Gmailify and POP fetch were first announced (Oct 2025) to end in January 2026. If Gmail sends a custom-domain alias through its own servers, it can add a Sender: header, which shows as 'on behalf of' (secondary source).
- [G22|high|confirmed] Gmail saves a copy of every message sent through smtp.gmail.com in Sent automatically. Google says: "Don't save sent messages on the server." A client that APPENDs to Sent creates a duplicate. Drafts: APPEND to \Drafts (UIDPLUS returns APPENDUID). After sending, the client must delete the draft itself.

- [G25|medium|confirmed] Bandwidth: IMAP download 2,500 MB/day, IMAP upload 500 MB/day, POP download 1,250 MB/day. When an account goes over, Google suspends it, usually for 1 hour and up to 24 hours. This page covers Workspace. Google does not publish separate consumer limits.

- [G27|high|confirmed] Gmail web settings that affect IMAP: per-label 'Show in IMAP', the IMAP folder size limit, and the delete or expunge behaviour. Google suggests syncing only folders with 10,000 emails or fewer.

## Missed facts
- Google's OAuth 2.0 Policies (Google APIs ToS) say: "You must choose the client type that best matches the platform." A Desktop-type client inside an Android app breaks this written policy. Also, Desktop clients send a (non-confidential) client_secret to the token endpoint. — WHY: Redirect option C (Desktop client + loopback on Android) is a policy breach, not a 'grey area'. It must not be the recommended fallback.
- The GIS AuthorizationClient gives a fresh 1-hour access token with no user interaction on every authorize() call after the first consent. It needs no refresh token and no backend. It offers revokeAccess(), and it requires play-services-auth. — WHY: It removes the main 'needs a backend' objection to option B. B becomes a serverless and possibly simpler path on devices with Play services: no token storage, no PKCE code, no redirect handling. It still fails on de-Googled ROMs.
- Google API Console Help still documents the Android client Advanced setting that "enables custom URI schemes for your Android client" and is "disabled by default on Android". The native-app doc says custom schemes are 'no longer supported on Android'. — WHY: Option A may still be possible for a new client, but the docs conflict. Test it in the Console before writing OAuth code.
- FairEmail also offers a 'Gmail (Android)' path. It gets tokens from the Android AccountManager for a Google account already on the device, in addition to browser OAuth. Google Family Link accounts under 13 get '[ALERT] IMAP access is not allowed for this account.' — WHY: This is another OAuth source with no redirect at all, for devices with Play services. Family Link accounts cannot use any IMAP client.
- MailKit's official IMAP IDLE example (imap.gmail.com) says Gmail seems to drop idle connections after about 10 minutes, so it idles for only 9 minutes. — WHY: This is evidence for a Gmail-specific starting re-IDLE interval near 9-10 min instead of 15 min. The 15 -> 9 adaptive plan could lose push for the first cycles on every new network.
- Google documents only SASL XOAUTH2 for Gmail. OAUTHBEARER is advertised but not documented. — WHY: Implement XOAUTH2 only. It is one mechanism, matches the docs, and keeps the code small.
- After ENABLE UTF8=ACCEPT, Gmail sends mailbox names as UTF-8 and treats '&' as a normal character (reproduced against Gmail in go-imap issue #20). Google's doc still says X-GM-LABELS are 'encoded in UTF-7 as appropriate'. Behaviour of labels in UTF-8 mode is not verified. — WHY: The design step 'no modified-UTF-7 codec needed' is probably right for LIST and SELECT. Check X-GM-LABELS in a live test before you drop the decoder.
- Android 15+: a dataSync FGS is limited to 6 hours in every 24 hours and cannot start from BOOT_COMPLETED. FairEmail keeps IMAP IDLE in a specialUse FGS with a PROPERTY_SPECIAL_USE_FGS_SUBTYPE explanation. FairEmail says other types do not fit, or have time limits or boot limits. — WHY: This decides how the push service is declared. Use specialUse with a justification, not dataSync, or push will stop after 6 hours a day.
- Workspace admins can block 'unconfigured third-party apps' or mark Gmail as a restricted service through App Access Control. OAuth then fails with admin_policy_enforced, even for a personal client ID. — WHY: A personal unverified client may be blocked on a Workspace account even when IMAP is on. Show a clear error and offer the app-password fallback if the admin allows it.
- imap.gmail.com sends GTS Root R1 cross-signed by GlobalSign Root CA in its chain. — WHY: If you pin, pin the SPKI of GTS Root R1 (and maybe the GlobalSign root), never a certificate hash. The system trust store is the simpler, safer default.

## Implications
- Use only implicit TLS: IMAP 993 and SMTP 465 (RFC 8314). Set the TLS protocols explicitly to TLSv1.3 and TLSv1.2, because Gmail still accepts TLS 1.0 and 1.1 (G13). Do not use cleartext ports.
- Pick OAuth or app password with battery in mind. Gmail closes an OAuth IMAP connection about every 60 min (G8), so plan one reconnect with a fresh token per hour. Refresh the token proactively at about 55 min, in the same wake-up as a re-IDLE, so no messages are missed. App-password sessions last about 24 h, so they need fewer reconnects.
- Keep the OAuth code small. Use PKCE S256 + Custom Tabs + a package-name redirect, with one HTTPS POST to oauth2.googleapis.com/token. This is about 150 lines with androidx.browser only, and avoids AppAuth and Play services. Store the refresh token encrypted with an Android Keystore key. Call /revoke when the user removes the account. Treat invalid_grant as 're-auth needed' (password change, 6 months unused, more than 100 tokens).
- Always use SASL-IR with XOAUTH2 or OAUTHBEARER (one round trip). On failure, answer the base64 JSON challenge with an empty line.
- On every connection: CAPABILITY, then AUTHENTICATE, then COMPRESS DEFLATE, then ENABLE UTF8=ACCEPT CONDSTORE. Folder names then arrive as UTF-8, and no modified-UTF-7 codec is needed. Find special folders by SPECIAL-USE attributes, never by name, because names change with the display language (Italian accounts have Italian folder names).
- Use a Gmail-native sync model. Sync [Gmail]/All Mail plus \Junk, \Trash and \Drafts. Store each message once, keyed by X-GM-MSGID. Derive Inbox, Sent, Starred, Important and user labels from X-GM-LABELS, and threads from X-GM-THRID. This avoids downloading one message in several folders, and archive or label actions become label edits.
- Gmail has no QRESYNC: detect changes with CONDSTORE (FETCH ... CHANGEDSINCE). Detect expunges with UID SEARCH or ESEARCH (RETURN ALL) and compare the UID sets. One LIST ... RETURN (SPECIAL-USE STATUS (UIDNEXT UNSEEN HIGHESTMODSEQ)) call checks all labels in one round trip.
- Push: IDLE watches only one mailbox per connection, and the account has about 15 connections in total (G24). Use ONE IDLE connection, on INBOX by default (or All Mail for users whose filters skip the inbox). When EXISTS arrives, fetch only the new UIDs with X-GM-LABELS. For per-category notifications, run UID SEARCH X-GM-RAW "category:primary" UID <new>.
- Make the re-IDLE interval adaptive, as FairEmail does: start at 15 min and step down to 9 min after silent drops. Note that the OAuth reconnect at about 60 min also refreshes the connection.
- Email actions on Gmail. Archive: UID STORE -X-GM-LABELS (\Inbox). Delete: UID MOVE to \Trash. Delete forever: in Trash, set \Deleted and EXPUNGE. Spam: MOVE to \Junk. Star: \Flagged. Important: +X-GM-LABELS (\Important). Label: +/-X-GM-LABELS. Do not depend on the user's web expunge settings.
- Send: never APPEND to Sent on Gmail (G22). After a successful send, delete the server draft. Implement undo send as a short local hold before SMTP. Implement scheduled send and snooze locally (WorkManager or AlarmManager, plus an archive and a later re-label). These work only when the device is on and online, and the UI must say so.
- Send-as: load the verified aliases from user input, because IMAP cannot read Gmail settings. Use the same Gmail credential for each alias. Warn that Gmail stops Send-as for non-Google addresses in January 2027. Send Riseup identities through Riseup's own SMTP, not through Gmail.
- SMTP privacy: send EHLO '[127.0.0.1]' (or a fixed neutral name) so that the LAN IP or device hostname does not go into Received. Tell the user that Gmail still records their public IP in every message sent from the app (G30). Hiding it needs a VPN or Tor. Generate the Message-ID as <random>@<sender domain>. Write Date in UTC (+0000) to hide the timezone.
- Do not send the IMAP ID command, or send only a generic name. Google 'recommends' ID with a contact address, but this exposes more data than needed.
- Keep Gmail-specific code behind a capability check: X-GM-EXT-1 present means the Gmail code path. Riseup (Dovecot) then uses the standard code path with no Gmail logic.
- Contacts: Google CardDAV needs a second OAuth scope (carddav) and vCard 3.0. Treat it as optional or out of scope for v1, to keep the code small.
- Do not pin certificates to a leaf. If you pin at all, pin only the Google Trust Services roots, and accept that Google can change them.

## Decisions
### Which authentication method for Gmail?
- A) OAuth only (own client ID, PKCE, Custom Tabs): + Google's preferred method. The token covers mail only, the user can revoke it per app, and it dies on a password change. Needs no 2SV setup and does not bypass 2SV. Works with Advanced Protection only if the app is verified. / - Needs a Google Cloud project. Gmail force-reconnects every hour (more radio wake-ups). The redirect setup is fragile for new Android clients (G9). Unverified-app warning screen.
- B) App password only: + The simplest code (AUTH PLAIN). IMAP sessions last about 24 h, so the least battery. No Google Cloud project, no Play services, no browser. / - Needs 2SV. Not available with Advanced Protection or with security-key-only 2SV, and maybe not on Workspace. Google discourages it. It bypasses 2SV and also unlocks CalDAV, so it has more power than needed. Google could deprecate it in the future.
- C) OAuth by default + app password as an advanced fallback: + Works on the most accounts and devices. The user chooses between security and battery. / - Two code paths (still small: about 150 lines for OAuth plus 1 line for AUTH PLAIN).
REC: C. Both paths are small. Default to OAuth. Offer app passwords for accounts or devices where OAuth setup fails.
### Who owns the OAuth client ID (distribution model)?
- A) Personal use: your own Google Cloud project, published 'In production', unverified: + Allowed by Google for fewer than 100 users. Refresh tokens do not expire after 7 days. No verification and no CASA. / - Warning screen at consent. Lifetime cap of 100 users. Does not work with Advanced Protection.
- B) Bring-your-own client ID: each user pastes their own client ID (as aerc, mutt or DAVx5 custom ID do): + Can be distributed publicly with no verification. Each user stays under the personal-use exception. / - Hard setup for normal users. Android-type clients are tied to the package name and signing-certificate SHA-1.
- C) Public app with restricted-scope verification (+ CASA if Google requires it): + No warning screen. No user cap. Advanced Protection users can use it. / - Weeks of review, a demo video and a privacy policy. CASA is possibly yearly and costs money (Thunderbird did CASA Tier 2). Google can revoke access.
REC: A now (personal app). Design the config so that B is a settings field, and do not plan for C.
### Which Android redirect or token mechanism for Google OAuth?
- A) Android-type client + custom scheme '<package>:/oauth2redirect' (Thunderbird, FairEmail and DAVx5 pattern): + No Play services and no server. Proven in FOSS apps. / - Google now says custom schemes are 'no longer supported on Android'. A new 2026 client may not be able to turn it on. Must be tested first.
- B) Google Identity Services AuthorizationClient (Play services): + Google's official path. Gives silent 1-hour access tokens. / - Proprietary Play services dependency, which fails on de-Googled ROMs. Refresh tokens need a backend. Restricted-scope support is undocumented.
- C) Desktop-type client + loopback http://127.0.0.1:port in the app: + Google still supports loopback for Desktop clients. No Play services. / - Google deprecated loopback for mobile. Using a Desktop client on Android is a policy grey area, and another app can listen on the port.
- D) Web-type client + App Link (https) redirect: + Verified ownership of the redirect. / - Needs a hosted assetlinks.json (hosting, which you do not want) and an embedded client secret.
REC: Test A first with a newly created client ID. If Google rejects it, choose between C (no Google dependency) and B (official). I recommend C for a privacy-first personal app, with the risk written down.
### Which mailbox does the single IDLE connection watch?
- A) INBOX only: + Fewest false wake-ups. Matches what users expect from notifications. / - Misses mail that filters send past the inbox.
- B) [Gmail]/All Mail: + Catches all new mail with every label (not Spam). / - Also wakes on your own sent messages and on draft saves from other devices, so more battery and more fetches.
- C) INBOX IDLE + one LIST-STATUS sweep of chosen labels on each wake-up: + One connection. Catches labels with some delay. / - Label mail is not instant.
REC: A by default, with C for user-picked labels. Offer B as a toggle.
### Which notifications for Gmail categories?
- A) Every new INBOX message: + No extra command. / - Promotions and Social are noisy.
- B) Primary only by default (X-GM-RAW category check on new UIDs): + Same behaviour as the Gmail app. One small extra SEARCH per arrival. / - Gmail-only code path.
- C) A toggle for each category: + Most control. / - More settings UI.
REC: C, with Primary on and the others off by default.
### Re-IDLE (keep-alive) interval
- A) Fixed 9 min: + Survives most NAT and server timeouts. / - About 160 radio wake-ups a day.
- B) Fixed 24 min (Thunderbird default): + Fewest wake-ups. / - Risk of silent drops and late mail on some networks.
- C) Adaptive 15 -> 9 min (FairEmail): + Balances latency and battery for each network. / - Some more logic.
REC: C.
### Gmail features with no protocol support (snooze, scheduled send, undo send)
- A) Implement them locally: + Feature parity in the app. / - They work only while the phone is on. Snooze is not visible in Gmail web.
- B) Undo send only (local delay); leave out snooze and scheduled send: + Minimal code. / - Less parity.
REC: B for v1. Add local scheduled send later if you want it.
### Google contacts (CardDAV)
- A) Skip; use the device's or the app's local contacts: + No extra scope and no extra protocol code. / - No sync of Google contacts.
- B) Read-only CardDAV with the extra OAuth scope: + Address autocomplete from Google. / - A second scope and consent. vCard 3.0 parser. No app-password path.
REC: A for v1.
### Sender privacy on Gmail SMTP
- A) Neutral EHLO + UTC Date + Message-ID with the sender's domain, and a notice that the public IP is visible: + Removes the leaks the client can control. No extra infrastructure. / - The public IP still leaks.
- B) A also, plus optional SOCKS proxy or Tor (Orbot) for SMTP: + Hides the public IP. / - More code. Google may challenge logins from Tor.
REC: A by default. B is optional and can come later.

## Open questions
- Can a Google Android OAuth client created in Oct 2026 still turn on 'custom URI scheme' in Advanced Settings? The current docs say custom schemes are no longer supported on Android. Only a real test with a new client ID can answer this.
- What is Gmail's real IDLE timeout in 2026? Does Gmail send any untagged keep-alive during IDLE? Does IDLE report flag or label changes made by other clients (FETCH)? Answering this needs an authenticated test, which I did not do.
- Does a label-only change (X-GM-LABELS) increase MODSEQ in [Gmail]/All Mail? Does LIST-STATUS accept HIGHESTMODSEQ on Gmail?
- Is the capability list after login unchanged in 2026? I verified only the list before login.
- Does UID SEARCH X-GM-RAW "in:snoozed" work in All Mail?
- After January 2027, will smtp.gmail.com still accept a verified third-party Send-as address in From, or will it rewrite it?
- Is the user's Gmail account a consumer @gmail.com account or a Workspace account? For Workspace, the admin can turn IMAP off, limit OAuth to allowlisted client IDs, or block app passwords.
- Does a purely on-device public client need CASA for restricted-scope verification? Google's text and the experience of real apps disagree. This matters only if the app is ever published.
- Do the Workspace bandwidth limits (2,500 MB down and 500 MB up per day) also apply to consumer accounts?
- Exact Gmail behaviour for a missing or malformed Message-ID and Date: the evidence is only from forums. Test this with Show original on test messages.

## Verifier decision feedback
Auth (C: OAuth by default, app password as fallback): still valid. Use XOAUTH2 only, because it is the only mechanism Google documents.

Client-ID ownership (A personal unverified in production, B bring-your-own as a settings field): still valid. The 100-user lifetime cap, the 7-day Testing expiry and the CASA rules are all confirmed. Note that BYO Android-type clients need the app's package name and signing SHA-1, and the custom-scheme question applies to them too.

Redirect mechanism: the recommendation must change.
- Option C (Desktop client + loopback) breaks Google's written OAuth policy ("choose the client type that best matches the platform"). It also needs an embedded client_secret. Drop it as the preferred fallback.
- Option B's main con is wrong. AuthorizationClient.authorize() returns fresh access tokens silently each session with no backend and no refresh token. Its real costs are Play services and undocumented restricted-scope support.
- API Console Help still documents the Android 'Enable custom URI scheme' toggle, so A may still work.
- New order: test A (Android client + package-name custom scheme + PKCE S256 + Custom Tabs) with a new client first. If A fails, use B on devices with Play services and the app password on de-Googled devices.

IDLE target (INBOX plus a LIST-STATUS sweep, All Mail as a toggle) and categories (Primary on through X-GM-RAW): still valid.

Re-IDLE interval: an adaptive interval still makes sense. The MailKit evidence (Gmail drops IDLE after about 10 min) suggests starting Gmail at about 9-10 min. Raise it only after stable cycles, instead of starting at 15 and stepping down. Do the hourly OAuth reconnect and token refresh in the same wake-up.

Push service: declare it as a specialUse FGS with a subtype justification, as FairEmail does. Do not use dataSync, which is limited to 6 hours a day on Android 15+.

Snooze and scheduled send (local only, v1 = undo send), CardDAV (skip in v1) and SMTP privacy (neutral EHLO, UTC Date, own Message-ID, notice that the public IP is visible): still valid.

Send-as: Gmail may already restrict new third-party Send-as setups during Q3-Q4 2026. Tell users that adding a non-Google alias may fail now, not only from January 2027.

Design note on UTF8=ACCEPT: it is probably safe for folder names. Keep the X-GM-LABELS encoding check on the live-test list before you remove the modified-UTF-7 decoder.
