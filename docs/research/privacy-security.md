# privacy-security: Privacy and security feature set for a privacy-first Android email client (Kotlin 2.4 / Compose M3 / AGP 9) for Riseup and Gmail, balanced against usability. Survey of FairEmail, Thunderbird for Android, Delta Chat, Proton Mail, Tuta and Apple Mail Privacy Protection, with live pre-auth probes (2026-10-16) and Android 16/17 platform facts.

- [G1|high|confirmed] FairEmail detects tracking images with a size and host heuristic and replaces them with an icon. This is on by default. — HtmlHelper.isTrackingPixel(): width*height <= 25 px (TRACKING_PIXEL_SURFACE), inline style max-width or max-height <= 1px, or class 'cloudmagic-smart-beacon'. TRACKING_HOSTS = www.google-analytics.com. Optional downloaded Disconnect lists add tracker hosts (FAQ 159); 'Content' category hosts are not flagged. The pref disable_tracking defaults to true. It also removes duplicate tracking-image URLs.
- [G2|high|confirmed] The FairEmail original-message WebView turns off JS, file access, cookies and Privacy Sandbox attribution. Safe Browsing and WebView metrics are turned off in the manifest. Backups are excluded with data extraction rules. — WebViewEx: setJavaScriptEnabled(false), setAllowFileAccess(false), setAllowContentAccess(true) (default kept), CookieManager.setAcceptCookie(false), setAttributionRegistrationBehavior(DISABLED), setSafeBrowsingEnabled(pref), setBlockNetworkLoads(!show_images), setAlgorithmicDarkeningAllowed(dark). Manifest: android.webkit.WebView.MetricsOptOut=true, android.webkit.WebView.EnableSafeBrowsing=false. It sets allowBackup=true, but data_extraction_rules.xml excludes file, database, sharedpref, external and root for both cloud-backup and device-transfer, and fullBackupContent=false. Note: it sets mixed content to ALWAYS_ALLOW.
- [G3|high|confirmed] FairEmail strips tracking parameters and unwraps known redirect wrappers before it opens a link. — UriHelper.sanitize(): it unwraps *.safelinks.protection.outlook.com ?url=, Trend Micro clicktime ?url=, www.google.com/amp/, www.google.* ?url=, Mandrill /track/click?p= (base64 JSON), *.awstrack.me path, urldefense.com/v3/__<url>__, generic ?redirect= and base64 ?redirectUrl=, and the Brave debounce list. It strips utm_* plus a list: gclid, gclsrc, dclid, _ga, fbclid, igshid, msclkid, mc_cid, mc_eid, yclid, twclid, gbraid, wbraid, _hsenc, __hssc, __hstc, __hsfp, hsCtaTracking, ml_subscriber, vero_id, oly_*, awt_*, icid, ef_id, s_cid, and others. The AdGuard URL-tracking filter list is optional (FAQ 200). FAQ 118 says the basic option removes UTM parameters. Note: Gmail web wrappers use q= (see G19). FairEmail handles url= for www.google.* only.
- [G4|high|confirmed] FairEmail does not connect to third-party services by default. All sub-processors (favicons, BIMI, Gravatar, Libravatar, DeepL, LanguageTool, VirusTotal, ipinfo, spam blocklists, Bugsnag, LLMs) are opt-in. — PRIVACY.md: 'The services of all sub-processors are disabled by default.' Gravatar and Libravatar send MD5 hashes of email addresses. BIMI and favicons send the sender domain.
- [G5|high|confirmed] FairEmail transport: optional TLS hardening (TLS 1.2+ with a cipher blocklist, or TLS 1.3 only with 'strict'). Certificate Transparency is always on through Android 16+ in non-Play builds. DNSSEC and DANE use MiniDNS. In-app proxy support was removed. — EmailService: SSL_PROTOCOL_BLACKLIST = SSLv2, SSLv3, TLSv1, TLSv1.1. The strict mode also removes TLSv1.2 and RSA/CBC-SHA suites. FAQ 201: since 1.2326, CT 'as provided by Android 16 and later is always enabled in non Play Store builds'. FAQ 202: DANE needs Android 8+, GitHub build only. FAQ 199: proxy support was removed because 'it is not possible to let an app proxy DNS requests'. The FAQ recommends VPN-based apps (Orbot VPN) and says private DNS must be turned off for .onion. G37 contradicts the DNS claim for SOCKS5 with unresolved addresses.
- [G6|high|confirmed] FairEmail shows authentication and transport indicators. A red or orange stripe means DKIM, SPF or DMARC failed. The shield is green only if DMARC passes and SPF or DKIM passes. Optional client-side DKIM and MX checks cost battery and data. — FAQ 92 and 94: it relies on the receiving server's Authentication-Results. Native DKIM verification is a debug option ('will increase both data and battery usage'). The MX-record check 'will slow down synchronization significantly'. It also warns when the Reply-To domain differs from the From domain. FAQ 176 adds a TLS shield computed from the 'Received' headers.
- [G7|high|confirmed] With biometric lock on, FairEmail notifications show no content and the app is hidden from Recents. FairEmail relies on Android file-based encryption for data at rest. — FAQ 113: lock after inactivity or screen-off. 'new message notifications will not show any content and FairEmail won't be visible on the Android recents screen'. FAQ 37: passwords are protected by device encryption. There is no app-level DB encryption.
- [G8|high|confirmed] Thunderbird for Android blocks remote pictures by default (ShowPictures.NEVER). Its message WebView has JS off and network loads blocked. HTML goes through a jsoup Safelist.relaxed cleaner. The app sets allowBackup=false and WebView MetricsOptOut. — ShowPictures enum: NEVER, ALWAYS, ONLY_FROM_CONTACTS. The default provider uses NEVER. MessageWebView: javaScriptEnabled=false, blockNetworkData(true) by default. A code comment warns: 'Images with content: URIs will not be blocked, nor will network images that are already in the WebView cache.' cid: parts are served by shouldInterceptRequest with Cache-Control no-store. BodyCleaner extends Safelist.relaxed with font, center, map, area, style tags and style/class/id attributes. It sets no CSP. app-common manifest: allowBackup=false. legacy/common manifest: android.webkit.WebView.MetricsOptOut. BiometricPrompt is used only to reveal server passwords in settings, not as an app lock.
- [G9|high|confirmed] Thunderbird for Android has 'Hide time zone', 'Hide user agent' and 'Incognito keyboard' privacy settings. All three are off by default. It uses EHLO ehlo.thunderbird.net, an uppercase-UUID Message-ID modeled on Apple Mail, random MIME boundaries, and an optional IMAP ID. — PrivacySettings.kt: PRIVACY_SETTINGS_DEFAULT_HIDE_TIME_ZONE=false, HIDE_USER_AGENT=false, INCOGNITO_KEYBOARD=false. MimeMessage.addSentDate() formats the Date in UTC when hideTimeZone is on. MessageIdGenerator: '<UUID-UPPERCASE@from-domain>', with the comment 'to match Apple Mail Message-ID format (for privacy)'. BoundaryGenerator: '----' + 30 base36 chars from SecureRandom. IncognitoKeyboard sets IME_FLAG_NO_PERSONALIZED_LEARNING. SmtpTransport: SMTP_HELLO_NAME='ehlo.thunderbird.net'. This changed from 127.0.0.1 in June 2025 'to increase compatibility' with servers that reject 127.0.0.1. RealImapConnection sends ID ('name','version') if the server advertises ID and the per-account sendClientInfo setting is on.
- [G10|high|confirmed] Delta Chat isolates its HTML WebView from the network. A process-wide fake proxy (0.0.0.0) is set with androidx.webkit ProxyController. Remote content, when allowed (Never/Once/Always), is fetched by the core through shouldInterceptRequest. That fetch uses the app's proxy settings and sends no User-Agent. — WebViewActivity.toggleFakeProxy(): ProxyConfig.Builder().removeImplicitRules().addProxyRule('0.0.0.0'). FullMsgActivity: JS off, PluginState OFF, setAllowContentAccess(false), setAllowFileAccess(false), setBlockNetworkLoads(!loadRemoteContent). interceptRequest() calls rpc.getHttpResponse(). Safe Browsing is off: 'this has privacy issues, eg. at least false positives are sent to the Safe Browsing Lookup API'. Core src/net/http.rs loads ProxyConfig for HTTP and comments 'By default we do not set User-Agent'.
- [G11|high|corrected] Chromium DNS prefetch can exfiltrate data from Android WebViews even when the official prefetch-off setting is used. Delta Chat's fixes came from the Cure53 finding XDC-03 (high severity). — Delta Chat blog (2023-05-22): 'XDC-03: Data Exfiltration via DNS Lookup on Android'. 'The official suggestion for disabling DNS-prefetch on Chromium does not work.' The fixes are deltachat-android #2539 and #2540 and core #4339. A similar WebKit leak was reported in Aug 2026 (mysk.blog). Implication: blockNetworkLoads plus a sanitizer is weaker than a sanitizer plus a dead proxy.
  >> VERIFY corrected: XDC-03 (High) is confirmed, and so is the quote that the official DNS-prefetch disabling 'does not work'. But the attack was shown in webxdc apps that have JavaScript ENABLED, not in a JS-off mail viewer. The fake-proxy fix (deltachat-android #2539) was also applied to the HTML mail viewer, and #2540 adds 'X-DNS-Prefetch-Control: off'. The 'dead proxy is stronger' implication is a sound defense-in-depth inference, but it was not demonstrated for JS-off WebViews. The mysk.blog WebKit item was not checked; it concerns WebKit/iOS, not Android WebView. | evidence: Delta Chat blog 2023-05-22, and the descriptions of PRs #2539 and #2540.
- [G12|high|corrected] Delta Chat core implements Autocrypt Level 1, RFC 9788 header protection, IMAP IDLE, and SOCKS5 and Shadowsocks proxies. With Orbot it uses socks5://127.0.0.1:9050, and per-account SOCKS credentials give Tor stream isolation. — standards.md lists RFC 9788 under metadata minimization and SOCKS5 (RFC 1928). Forum: Orbot VPN mode plus an in-app SOCKS proxy together break connections. Per-account socks5://user:pass@127.0.0.1:9050 isolates circuits because Tor's IsolateSOCKSAuth is on by default. Maintainers say some features (calls, webxdc realtime) ignore the proxy.
  >> VERIFY corrected: standards.md does list SOCKS5 (RFC 1928) plus Shadowsocks, IMAP IDLE, Autocrypt Level 1 and RFC 9788. But Delta Chat does NOT do per-account Tor isolation itself. A maintainer (Nov 2023) said Tor 'is not supported very well'. Per-account SOCKS credentials and per-account SocksPorts are user workarounds. The Tor man page confirms IsolateSOCKSAuth is 'On by default', so the technique works when the client sends distinct credentials. | evidence: forum.delta.chat thread 2799. tor.1.txt: 'IsolateSOCKSAuth ... On by default; you can disable it with NoIsolateSOCKSAuth'.
- [G13|high|corrected] Proton Mail 'Block email tracking' is on by default. It removes known trackers and proxies other remote images through Proton servers when mail arrives, so senders see every message as opened. Link-parameter cleaning is web-only. 'Confirm link URLs' is on by default on Android too. — Images are fetched server-side on arrival for non-E2EE mail, with a generic IP and geolocation. Proton itself says 'marketers see every email sent to a Proton Mail address as opened as soon as it's delivered'. The link confirmation shows the full URL and is presented as homograph protection. These features need a provider-side server.
  >> VERIFY corrected: Confirmed: 'Tracking protection is enabled by default'. Remote content is loaded through Proton servers on receipt, with a generic IP and location, for non-E2EE mail. Link-parameter cleaning is web-only. 'Confirm link URLs' is on by default on web, Android and iOS. Not found on the cited pages: the quote 'marketers see every email ... as opened as soon as it's delivered', and any homograph or full-URL framing. The link-confirmation page only says the user is asked to confirm before opening. | evidence: proton.me/support/email-tracker-protection; proton.me/support/link-confirmation ('The feature is enabled by default ... web, Android, and iOS').
- [G14|high|confirmed] Apple Mail Privacy Protection downloads remote content in the background when mail arrives, whether or not the user opens it. It routes the content through two relays run by different entities: one sees the IP, the other sees the content. — Apple legal page: 'routes all remote content downloaded by Mail through two separate relays operated by different entities'. With MPP off, the user can separately hide the IP and block all remote content (Mac guide). This is a server-dependent design.
- [G15|medium|corrected] Tuta blocks external content by default with 'Show', 'Always trust sender' and 'Always block sender'. It uses a strict CSP and a sanitizer. It warns when the technical sender differs from From or authentication fails. It matches reported phishing locally with hashes. — Some sources are older release notes. Tuta does not offer IMAP, so its model applies only to its own apps.
  >> VERIFY corrected: The cited release note is from 2020-04-15 (v3.71.3). It confirms local hash matching of reported phishing and authentication banners. It also says the technical-sender warning triangle was REPLACED by an info banner because it was shown too often. That page does not cover external-content blocking with Show / Always trust / Always block. Treat those as unverified here. | evidence: tuta.com/blog/release-email-phishing-protection (April 15, 2020).
- [G16|high|confirmed] A client cannot hide the user's IP when it loads remote content unless it uses a third-party network hop. Without a server, the only options are Tor or a VPN. — Every IP-hiding product found depends on infrastructure: Apple uses two relays (G14), Proton a server-side proxy (G13), and Gmail a proxy only inside its own UI. FairEmail FAQ 35 notes that the Gmail proxy fetches 'in real-time', so it does not hide open time. IMAP clients get the original image URLs. This is a reasoned conclusion from the cited designs.
- [G17|high|confirmed] Android WebView: shouldOverrideUrlLoading 'is not called for POST requests'. shouldInterceptRequest is not called for javascript:, blob: or file:///android_asset URLs, and on redirects it is called only for the first URL. — So an HTML form with method=POST can navigate without the app seeing it, and remote loads through the WebView network stack follow redirects without app checks. setBlockNetworkLoads(false) does not refetch until reload(), and needs the INTERNET permission.
- [G18|high|corrected] WebView privacy switches: the manifest meta-data android.webkit.WebView.MetricsOptOut=true opts out of diagnostics, and android.webkit.WebView.EnableSafeBrowsing=false turns off Safe Browsing app-wide. Safe Browsing checks URLs with Google. — Google recommends keeping Safe Browsing on. In a viewer that never navigates (content loaded with loadDataWithBaseURL, all link taps sent to the browser), Safe Browsing has nothing to check, and the user's browser runs its own check. Since Android 16 the default WebView User-Agent is reduced to 'Linux; Android 10; K' with no device model.
  >> VERIFY corrected: The manifest keys and Google's 'We recommend keeping Google Safe Browsing enabled' are confirmed. WRONG: the date of the UA reduction. The Android Developers blog now says 'Beginning in Android 17', and the Android 17 summary lists 'User-agent reduction for WebView' as 'Change (apps targeting 17+)'. So it applies to targetSdk 37, not Android 16 (the privacysandbox page is outdated). Also, Safe Browsing checks URLs served through shouldInterceptRequest too (WebViewClient note), so 'nothing to check' is not accurate once images are allowed. This supports turning it off. | evidence: android-developers.googleblog.com/2024/12/user-agent-reduction-on-android-webview.html (current text: 'Beginning in Android 17'). developer.android.com/about/versions/17/summary.
- [G19|high|corrected] WebView dark mode for apps targeting API 33+: use WebSettingsCompat.setAlgorithmicDarkeningAllowed(). It applies only when the content does not use prefers-color-scheme and the app theme is dark (isLightTheme=false). For API 32 and lower, use setForceDark. — prefers-color-scheme follows isLightTheme. FairEmail and Delta Chat use these APIs.
  >> VERIFY corrected: setAlgorithmicDarkeningAllowed applies to apps with targetSdkVersion >= 33, and prefers-color-scheme follows isLightTheme (confirmed). setForceDark is keyed on the app's targetSdk (<33), NOT on the device API level. It is a no-op for an app that targets 36/37 on every device, so drop the 'API 32 and lower use setForceDark' branch. | evidence: WebSettings.setForceDark: 'In apps with targetSdkVersion ≥ TIRAMISU this API is a no-op'.
- [G20|medium|corrected] The Gmail web UI wraps links as https://www.google.com/url?q=<dest>&source=gmail&ust=..&usg=.. (usg is a signature). Such wrapped links can appear in mail bodies composed or forwarded from Gmail. — The destination is in q= (Search-style links use url=). Changing q without a valid usg shows a Google 'Redirect Notice'. Reports from 2020 (HN) and July 2026 say URLs in sent bodies are rewritten.
  >> VERIFY corrected: The HN 2020 thread shows the rewrite in IMAP-delivered bodies, with source=gmail-imap ('google.com/url?q=<URL>&source=gmail-imap&ust=..&usg=..'). It happened only under special account setups (Apple Mail with the 'Google' account type, or Advanced Protection), and most commenters could not reproduce it. The claude-code issue cited is not a primary source. | evidence: news.ycombinator.com/item?id=24818024 (Oct 2020).

It warns again at click time. — Mozilla notes false positives from mailing lists that use click-tracking redirectors.

- [G22|medium|corrected] Gmail SMTP submission (smtp.gmail.com, ESMTPSA) adds a Received header with the sender's public IP, and the EHLO string can expose a LAN IP. Mail sent with the Gmail API shows 'by gmailapi.google.com with HTTPREST' and no client IP. — Privacy Guides forum (2026-08-06) reproduced this; one reply reports inconsistent results. A 2022 LKML doc patch says Gmail adds 'your private and public IPs'. On mailop, a Google employee said Google treats user IPs as PII; the number in the gmailapi Received line is likely a client/project token.
  >> VERIFY corrected: The Privacy Guides thread (2026-08-06) supports the SMTP public-IP Received header, and one reply says 'Some messages have Received: header, some not'. That thread does NOT mention the Gmail API. The gmailapi.google.com/HTTPREST statement comes only from a 2019 mailop post (Brandon Long). That post also says the numeric token is 'a unique token for the client of the API, ie the specific third party client', so the API path tags the sending app in the headers. Treat the API 'no IP' claim as 2019-dated. | evidence: Forum thread and the mailop archive msg08419 (2019-07-22).
- [G23|high|confirmed] Riseup does not put the sender's IP in outgoing mail, keeps no IP logs, and hides the user ID header. Stored mail is encrypted per user and unlocked with the account password. — riseup.net/en/email: 'your internet address (IP address) is not embedded in the email'. 'Riseup temporarily retains the ability to decrypt the user ID header'. 'Your e-mails are encrypted individually on our servers, and can only be unlocked and read using your password.' So the stored password has high value. Not verified: whether Riseup keeps the EHLO string in Received.
- [G24|high|confirmed] RFC 5321 says the EHLO argument MUST be a primary host name or, if the host has no name, an address literal. In a live probe, both smtp.gmail.com:465 and mail.riseup.net:465 answered 250 to 'EHLO [127.0.0.1]'. — FairEmail defaults to 'dummy.faircode.eu', with an option for '[127.0.0.1]' or '[IPv6:::1]', and falls back when the server answers 'syntactically invalid'. Thunderbird for Android uses ehlo.thunderbird.net (G9). App-specific EHLO names identify the client in Gmail's Received header.
- [G25|high|confirmed] Jakarta/Angus Mail default generators put a millisecond timestamp, a per-process counter and an object hashCode into MIME boundaries and Message-IDs. — UniqueValue: boundary '----=_Part_<counter>_<hash>.<currentTimeMillis>'. Message-ID '<hash.counter.currentTimeMillis@localaddress>'. FairEmail overrides the Message-ID with '<UUID@domain>' and adds an 'X-Correlation-ID' header (a client fingerprint).
- [G26|high|confirmed] RFC 5322: '+0000' means the local zone is UTC. '-0000' means the time contains no information about the local zone. The Message-ID right side SHOULD be a domain that guarantees uniqueness. Section 3.6.3 gives three ways to handle Bcc. — Bcc options: remove the Bcc line for all copies; send To/Cc a copy without Bcc and Bcc recipients a copy with Bcc; or send separate copies, one per Bcc recipient. '-0000' is the semantically correct 'hidden zone' marker, but it is rare in practice, so it can act as a fingerprint (inference).
- [G27|medium|corrected] Thunderbird desktop: the hidden pref mail.sanitize_date_header writes Date in UTC with seconds set to 00. Since about v110, Thunderbird desktop does not send User-Agent by default. — Sourced from the Send Later add-on changelog and a privacy hardening guide, not Mozilla documentation. Bug 1114475 covers the UA change.
  >> VERIFY corrected: mail.sanitize_date_header is real, and the comm-central source shows it: mailnews.js pref default false, and jsmime emits UTC with seconds = 0. WRONG: 'does not send User-Agent by default'. Bug 1114475 (fixed in 110) added a MINIMAL User-Agent: mailnews.js has sendUserAgent=true and useMinimalUserAgent=true, so Thunderbird desktop still sends a short UA by default. | evidence: comm-central mailnews/mailnews.js lines 24 and 36-41; mailnews/mime/jsmime/jsmime.mjs sanitizeDate (getUTC*, seconds = 0); Bugzilla 1114475 summary 'send a minimal User-Agent header, or no header at all'.
- [G28|high|confirmed] The Android photo picker redacts location metadata by default. MediaStore.getRedactedUri (API 31) gives EXIF-redacted URIs. ACCESS_MEDIA_LOCATION is needed for unredacted EXIF. A new extra, EXTRA_REQUEST_LOCATION_METADATA_ACCESS (SDK 37.1), lets an app request location, and the user decides. — Files that come from share intents (ACTION_SEND) or from the Storage Access Framework are not guaranteed to be redacted. The app must strip metadata itself (inference from the docs).
- [G29|high|confirmed] RFC 8098: an MUA MUST NOT send MDNs automatically if Disposition-Notification-To differs from Return-Path. The default should be to not send MDNs. Silently ignoring MDN requests is acceptable.
- [G30|medium|confirmed] One OpenPGP ciphertext sent to all recipients contains the key ID of every recipient, Bcc included. Thunderbird warns about this and does not send separate copies. — Mozilla bug 1671891: 'The encoding of an encrypted message contains the key ID of each message recipient.' Sending separate copies to Bcc recipients was discussed and not adopted. The Stanford BCC paper shows the exposure across clients.
- [G31|high|confirmed] RFC 8314 deprecates cleartext and prefers implicit TLS (IMAP 993, submission 465). MUAs MUST implement TLS 1.2+. A client that requires confidentiality MUST NOT do anything except capability discovery or STARTTLS before it has TLS. NO STARTTLS (USENIX Security 2021) found more than 40 STARTTLS bugs in clients and servers, including mobile.
- [G32|high|corrected] Live probe: mail.riseup.net (993/465) and imap.gmail.com (993) negotiate both TLS 1.3 and TLS 1.2 with ECDHE AEAD suites. Riseup uses Let's Encrypt (chain YE1 > ISRG Root YE > ISRG Root X2 > X1) and Gmail uses Google Trust Services (WR2 > GTS Root R1 > GlobalSign Root CA). — Riseup SAN: imap/mail/pop/smtp.riseup.net. crt.sh shows mail.riseup.net renewed about every 60 days (2026-02-19, 04-20, 06-19, 08-18), with a new key each time and intermediate changes E8 > YE2 > YE1. Leaf-key pinning or leaf TOFU would therefore break or warn about 6 times a year. TLS 1.1 could not be tested because the local OpenSSL refuses it.
  >> VERIFY corrected: TLS 1.3 and 1.2 with ECDHE AEAD on all four endpoints is confirmed. Riseup's chain mail.riseup.net < YE1 < Root YE < ISRG Root X2 < ISRG Root X1 is confirmed (leaf 2026-08-18 to 11-16). crt.sh shows about 60-day renewals: 2025-06-24 (E6), 08-23, 10-22, 12-21, 2026-02-19, 04-20 (E8), 06-19 (YE2), 08-18 (YE1). Gmail's chain DEPENDS ON THE CLIENT KEY TYPE: ECDSA-capable clients get imap.gmail.com < WE2 < GTS Root R4 < GlobalSign Root CA, and RSA-only clients get WR2 < GTS Root R1 < GlobalSign. A Gmail pin-set must include R4 (and R1). 'New key each time' was not re-checked. | evidence: live probe 2026-10-16: openssl s_client -tls1_2/-tls1_3 on all four endpoints; -showcerts default (ECDSA) vs -sigalgs RSA-only on imap.gmail.com; crt.sh JSON.
- [G33|high|confirmed] Live pre-auth capabilities. Riseup IMAP: IMAP4rev1 SASL-IR LOGIN-REFERRALS ID ENABLE IDLE LITERAL+ AUTH=PLAIN AUTH=LOGIN. - [G38|high|confirmed] SOCKS5 without DNS leaks is possible in-app on Android. libcore SocksSocketImpl sends the hostname (ATYP DOMAIN_NAME) when the target InetSocketAddress is unresolved. Delta Chat says its core does not leak DNS when SOCKS5 is set. .onion names must never be resolved locally.

## Missed facts
- Gmail IMAP/SMTP via XOAUTH2 needs the scope https://mail.google.com/, which Google classifies as RESTRICTED. gmail.send is SENSITIVE. Any public app with these scopes needs Google OAuth verification. An unverified app shows the 'unverified app' screen and is capped at 100 new users. The extra security assessment applies 'if you store restricted scope data on servers (or transmit)', so an on-device-only client avoids that but not verification. App passwords are the alternative: they need 2-Step Verification, are 'not recommended' by Google, and are unavailable with Advanced Protection. — WHY: It drives the Gmail auth design and the cost of distribution. It also changes the Gmail-API-send trade-off: verification is needed anyway for IMAP, and the API adds only a sensitive scope.
- Android's built-in SOCKS (libcore SocksSocketImpl) gets SOCKS5 username/password only from the process-global java.net.Authenticator, keyed by proxy host/port and not by account. Per-account credentials (for Tor IsolateSOCKSAuth isolation) therefore need a small hand-written RFC 1928/1929 handshake on a plain Socket to 127.0.0.1:9050. — WHY: The report's 'Orbot SOCKS, about 100 lines' plan with per-account isolation cannot use Proxy(Proxy.Type.SOCKS) as-is. A custom SOCKS5 client is still small and also guarantees remote DNS.
- Auto Backup: 'If there are no rules for a particular backup mode, such as if the <device-transfer> section is missing, that mode is fully enabled for all content'. — WHY: The report recommends OMITTING <cross-platform-transfer>. The safer and simpler rule is to write explicit exclude-all rules in every section, including <cross-platform-transfer platform="ios">, plus allowBackup=false.
- WebView UA reduction ships with Android 17 and only for apps targeting API 37. setForceDark is a no-op for any app with targetSdk >= 33. Safe Browsing still checks URLs served through shouldInterceptRequest. — WHY: It simplifies the WebView code (no setForceDark branch). It also confirms that turning off Safe Browsing in the viewer avoids Google lookups of allowed image URLs.
- Gmail serves different certificate chains by key type. ECDSA clients get WE2 < GTS Root R4 < GlobalSign Root CA, and RSA clients get WR2 < GTS Root R1 < GlobalSign. — WHY: If the 'pin Gmail roots' option is chosen, R4 must be in the pin-set. Android/Conscrypt offers ECDSA, so the R4 path is the likely one.
- Gmail can deliver message bodies over IMAP with links rewritten to google.com/url?q=...&source=gmail-imap&ust=..&usg=... for some account setups. This was reported in 2020 and could not be reproduced by most users. — WHY: Unwrapping google.com/url q= is needed in the reading path, not only for forwarded mail.
- In the Gmail API send path, the Received line carries a token that is 'a unique token for the client of the API, ie the specific third party client'. The source is a Google engineer on mailop in 2019. — WHY: Option B for the Gmail send path hides the IP but may tag every message with the app's OAuth-client identity. This is a fingerprint trade-off, and the source is from 2019.
- GnuPG 2.3+ (LibrePGP) encrypts with OCB AEAD packets (tag 20) when the recipient key advertises them. This is not RFC 9580 SEIPDv2, and OpenKeychain cannot decrypt it. — WHY: Many Riseup PGP users run GnuPG. The phase-2 library choice (PGPainless/BC or rPGP) must be tested for LibrePGP OCB decryption, and generated keys must not advertise features that peers cannot handle.
- AGP 8.3+ embeds VCS information (META-INF/version-control-info.textproto) in release builds by default. F-Droid lists it as a source of non-determinism. — WHY: The reproducible-build checklist should also turn off vcsInfo for the release build type, not only dependenciesInfo.
- The Riseup onion settings page REQUIRES 'SSL: No' (ports 143/25/110), and the onion also exposes 587 and 80. My attempt to repeat the onion TLS probe failed because the sandbox killed the Tor binary. — WHY: 'Onion with TLS verified against mail.riseup.net' rests on one unrepeated probe and runs against Riseup's own guidance. The app needs a defined fail-closed behavior (never silent plaintext) if the onion stops serving that certificate.
- Android 17 ECH works only if 'the networking library used by the app ... has integrated ECH support'. Otherwise the client sends ECH GREASE. — WHY: A custom IMAP/SMTP client on raw SSLSocket should not expect ECH, which matches the report's inference. No design change is needed.

## Implications
- Threat model to state in the app: these features protect against senders, trackers, network observers and other apps on the device. They do not protect against the provider (Google reads Gmail; Riseup holds the mail). For Gmail accounts, show this once and do not promise more.
- MUST - Remote content blocked by default (images, CSS url(), fonts, media, iframes). Choices: 'Show once', 'Always for this sender'. Honor the per-sender allow only when the provider's Authentication-Results show aligned dmarc=pass, so a spoofed trusted sender cannot unlock trackers. Usability: low (one tap; newsletters look plain at first). Build: sanitizer replaces remote src with a placeholder and keeps the URL in a data attribute. Facts G8, G15, G52.
- MUST - Tracking-pixel removal even when images are allowed: FairEmail heuristic (w*h <= 25 px, max-width/max-height <= 1px, display:none or 0-size images) plus a small built-in tracker-host list, and a counter 'N trackers removed'. Usability: none. Build: about 40 lines of Kotlin in the sanitizer. Facts G1, G13.
- SHOULD - The WebView never touches the network. Set blockNetworkLoads=true and a process-wide fake proxy (ProxyController 0.0.0.0, androidx.webkit), and serve allowed remote resources from the app's own fetcher in shouldInterceptRequest: HTTPS only, no cookies, no Referer, no Accept-Language, a fixed generic UA, size and time caps, no redirect over 3 hops, through Tor when enabled. Usability: none. Removes DNS-prefetch and redirect blind spots. Facts G10, G11, G17.
- MUST NOT - Never prefetch remote content over clearnet, never build link previews, never fetch favicons, BIMI, Gravatar or Libravatar by default. COULD - With Tor on, offer an MPP-like 'fetch images through Tor when mail arrives' (default off; battery and data cost). Facts G4, G13, G14, G16.
- MUST - HTML sanitizer: jsoup Safelist.relaxed plus a few presentational additions (font, center, table attrs, a filtered style attribute). Drop script, iframe, object, embed, form, input, button, textarea, select, link, meta, base and svg, and all on* attributes. Allow only http, https, mailto and cid in href/src, and data: only for inline images. Remove @import and url() from CSS unless images are allowed. Reason: POST forms bypass shouldOverrideUrlLoading. Usability: none. Facts G8, G17.
- MUST - WebView settings: JS off, allowFileAccess=false, allowContentAccess=false, cookies off, geolocation off, DOM storage off, mixed content NEVER, attribution registration disabled, setWebContentsDebuggingEnabled only in debug. Manifest: MetricsOptOut=true, EnableSafeBrowsing=false. Load with loadDataWithBaseURL(null, ...) and a CSP meta: default-src 'none'; img-src cid: data: (add https: only when the user allows, served by the interceptor); style-src 'unsafe-inline'; font-src data:; form-action 'none'; base-uri 'none'. Usability: none. Facts G2, G10, G18.
- SHOULD - Dark mode: setAlgorithmicDarkeningAllowed on sanitized HTML, plus a per-message 'view in light' toggle. Usability: positive. Fact G19.
- MUST - Link tap flow: shouldOverrideUrlLoading always returns true. Show a bottom sheet with the registrable domain in bold, the full URL, punycode when non-ASCII, and a warning when the link text looks like a URL or domain with a different host or when the host is an IP. Unwrap safelinks (url=), google.com/url (q= and url=), urldefense v3, awstrack.me and Mandrill. Strip utm_* plus the FairEmail list (gclid, fbclid, msclkid, mc_cid, mc_eid, igshid, yclid, twclid, gbraid, wbraid, _hsenc, __hs*, ...). Buttons: Open, Copy, Open original. Usability: one extra tap; Proton ships this on by default. Facts G3, G13, G20, G21.
- MUST - Outgoing header set kept minimal: Date, From, To, Cc, Subject, Message-ID, In-Reply-To, References, MIME-Version, Content-Type, and Autocrypt only when E2EE is on. Never send User-Agent, X-Mailer, X-Correlation-ID, Content-Language, Disposition-Notification-To, or IMAP ID. Usability: none. Facts G9, G25, G33.
- MUST - EHLO '[127.0.0.1]' (both servers accept it in the live probe). Never send the device's real LAN IP or hostname, and never an app-branded name. Usability: none. Fact G24.
- MUST - Message-ID '<' + UUIDv4 in upper case + '@' + From domain + '>' (blends with Apple Mail, as Thunderbird does). MIME boundaries are 30+ chars from SecureRandom. Never use Jakarta Mail defaults, which contain timestamps and counters. Facts G9, G25, G26.
- SHOULD - Date header in UTC '+0000' by default (seconds may be truncated). The reply attribution line ('On <date>, X wrote:') must follow the same policy (UTC or no time) and a fixed, neutral wording. Otherwise the quote leaks the timezone and locale anyway. Usability: recipients see UTC times only in raw headers; clients convert. Facts G9, G26, G27.
- MUST - Image metadata: on attach, strip EXIF/XMP/GPS and maker notes. Re-encode HEIC to JPEG; for JPEG use ExifInterface to remove tags, or re-encode at about q90 when resizing. Rename camera-style names (IMG_20261016_101523.jpg) to image-1.jpg. Warn that video, PDF and Office metadata are not cleaned. Allow 'send original' per item. Usability: low. Fact G28.
- MUST - Read receipts: never send automatically; default 'never', optional 'ask'. Never request receipts by default. Fact G29.
- SHOULD - Reply and forward: remove tracking pixels and remote images from quoted HTML (stop forward-tracking), and apply the same hardening to the compose WebView. Usability: none.
- MUST - Bcc: put recipients only in RCPT TO and omit the Bcc header on the wire. Keep Bcc in the Sent copy (Riseup needs APPEND; Gmail saves Sent itself). With encryption, send one separate encrypted copy per Bcc recipient and never gossip Bcc keys. Facts G26, G30.
- SHOULD - Gmail send-IP leak: tell the user once. Mitigate with the Gmail API send path, or Tor/VPN, or accept it (see decision). Riseup needs no mitigation. Facts G22, G23.
- MUST - Transport: implicit TLS only (IMAP 993, SMTP 465) for both providers. TLS 1.3 and 1.2 only, ECDHE AEAD suites only. No STARTTLS code at all and no plaintext path. This is simpler and safer, and both servers support it (live probe). Usability: none. Facts G31, G32.
- MUST - Certificate checks: platform TrustManager with system CAs only (no user CAs), SNI, explicit hostname verification, and CT on through network_security_config (opt-in on API 36, default on API 37). Hardcode the server settings for riseup.net and gmail.com, so there are no autoconfig, ISPDB or MX lookups. Do not implement leaf TOFU (Riseup rotates its key every ~60 days) and skip DANE (no TLSA on client ports). Facts G32, G34, G35, G36.
- SHOULD - Tor through Orbot: a toggle 'Use Tor (Orbot)'. Detect the SOCKS port at 127.0.0.1:9050. Connect with createUnresolved hosts (remote DNS) and use per-account SOCKS username/password for circuit isolation. Use the Riseup onion with TLS on 993/465, verified against mail.riseup.net. Fail closed when Orbot is unreachable, with no silent clearnet fallback. Warn about the Android 17 work-profile loopback block and possible Gmail login challenges. Usability: medium (needs Orbot; slower IDLE reconnects). Facts G12, G37, G38, G40, G42.
- COULD - 'VPN only' mode: bind sockets to a Network with TRANSPORT_VPN (Network.bindSocket or socketFactory) so connections fail closed when the VPN drops. Resolve with Network.getAllByName. Usability: low; opt-in. Fact G41.
- MUST - Credentials: Riseup password and Gmail OAuth refresh token encrypted with an AES-256-GCM key in AndroidKeyStore (StrongBox when available). Do not require user auth on the key, because background sync needs it. Do not use security-crypto (deprecated). Gmail login goes through Custom Tabs or the system browser with PKCE, never a WebView. Facts G23, G43, G50.
- MUST - Backup: allowBackup=false and dataExtractionRules that exclude every domain in <cloud-backup> and <device-transfer>, and that omit <cross-platform-transfer>. Usability: the user must re-add accounts on a new phone. Facts G2, G45.
- SHOULD - App lock: BiometricPrompt (BIOMETRIC_STRONG or DEVICE_CREDENTIAL) after a timeout or screen-off. While locked, notifications have no content and there is no Recents preview. Usability: opt-in. Facts G7, G46.
- MUST - Recents: setRecentsScreenshotEnabled(false) on API 33+ by default; users can still take screenshots. COULD - A FLAG_SECURE toggle (the only way to stop Content Capture on API 37). Facts G46.
- SHOULD - Notifications: VISIBILITY_PRIVATE with a public version ('New message'). The option 'hide content everywhere' posts only the count. Message previews are fetched with BODY.PEEK, which never triggers remote loads. Fact G46.
- SHOULD - Input privacy: wrap compose (recipients, subject, body) in InterceptPlatformTextInput to add IME_FLAG_NO_PERSONALIZED_LEARNING. Set EXTRA_IS_SENSITIVE when copying passwords, OTP-like codes or keys. Set isSensitiveData on credential and key screens, and filterTouchesWhenObscured on Send, Delete and 'Allow remote content'. Usability: the keyboard stops learning words from email. Facts G47, G48, G49.
- MUST - No telemetry: no analytics, no crash-reporting SDK, no downloadable fonts (bundle them), no Play Services dependency. Write crash logs to a local file the user can share. Release builds use R8 -assumenosideeffects for android.util.Log v/d/i, and code never logs addresses, subjects or bodies. Network allowlist: IMAP/SMTP hosts, accounts.google.com and oauth2.googleapis.com (plus www.googleapis.com only if the Gmail API is used). Facts G4, G18.
- MUST - Attachments: never open automatically. Keep them in cacheDir/att/, delete when the viewer closes and at start if older than 1 h. Open with a FileProvider content:// URI, FLAG_GRANT_READ_URI_PERMISSION and ACTION_VIEW, with the MIME type checked against magic bytes. Save with ACTION_CREATE_DOCUMENT. Warn for .apk/.apks/.xapk, for .html/.htm/.svg/.mht (phishing forms in the browser), for double extensions and U+202E (RTLO), and for MIME/extension mismatch. Use Gmail's blocked list as the baseline. Limits: Gmail 25 MB raw; Riseup SIZE 25.6 MB is about 18 MB raw after base64. Facts G33, G60.
- MUST - Sender display: always show the real address under the display name. Warn when the display name contains an email address or a domain different from the From domain, when the Reply-To domain differs, and when the sender is a first contact (from the local DB, no network). Facts G6, G53.
- SHOULD - Authentication: parse only the topmost Authentication-Results with a trusted authserv-id (Gmail: mx.google.com; Riseup: to be confirmed). Show only negative signals (a red banner on dmarc=fail, or when SPF and DKIM both fail) and no green 'verified' badge, as RFC 8601 advises. Do no client-side DKIM (battery, DNS leaks). Facts G6, G52.
- SHOULD - IDN homographs: show punycode for any domain label that fails a small Chrome-style check (IDNA errors, mixed scripts via UScript, Latin/Cyrillic/Greek mixing, a non-ASCII label that imitates an ASCII top brand). Always show punycode in the link sheet. Usability: none for Latin-script users. Fact G54.
- SHOULD - E2EE (phase 2): built-in OpenPGP with PGPainless 2.x, no OpenKeychain. Autocrypt Level 1 with prefer-encrypt=mutual and the 4-state UI (lock icon in compose, auto-on when 'encrypt'), gossip, and RFC 9788 hcp_baseline (Subject '[...]'), with separate copies for Bcc. Key discovery: Autocrypt headers first. WKD or keys.openpgp.org only on an explicit 'Find key' tap, over Tor when enabled. No WKD exists for riseup.net or gmail.com. Facts G55, G56, G58, G59.
- SHOULD - Reproducible build: dependenciesInfo { includeInApk=false; includeInBundle=false }, a pinned JDK/AGP/Kotlin, a deterministic or disabled baseline profile, no PNG crunching. Publish on F-Droid with the developer signature. Fact G51.
- Library budget (elegance): jsoup (0.5 MB) for sanitizing, androidx.webkit for ProxyController and algorithmic darkening, androidx.biometric for the app lock, and later PGPainless with Bouncy Castle for E2EE. Everything else (SOCKS, IMAP/SMTP, Keystore crypto, tracker lists, IDN check, EXIF stripping with androidx.exifinterface) is platform code. Avoid security-crypto, OkHttp (not needed for a few image GETs), SQLCipher, and Jakarta Mail (its SOCKS path leaks DNS).

## Decisions
### Default remote-content policy
- A. Block all; 'show once' / 'always for sender' (needs DMARC pass): + Matches Thunderbird, Tuta and FairEmail. Zero leaks by default. Simple. / - Newsletters look broken until the user taps.
- B. A plus 'load through Tor' when Orbot is on: + Closest serverless match to Apple/Proton proxying; hides IP and location. / - Needs Orbot; slower; more battery when used.
- C. Auto-load after tracker stripping (Proton style): + Best looking mail. / - Without a proxy server it leaks IP and open time to every sender. Not acceptable for this app.
REC: A by default, with B as an option once Tor support exists.
### Tor support
- A. None in app; user runs Orbot or Tor VPN in VPN mode: + No code. / - No onion endpoints, no per-account isolation, no fail-closed check, VPN DNS edge leaks.
- B. Orbot SOCKS integration (remote DNS, isolation, Riseup onion, fail closed): + About 100 lines. No binary. Strong privacy. / - Needs Orbot installed and running; cross-profile loopback blocked on Android 17.
- C. Embed tor-android (C-Tor): + Works without other apps. / - About 13 MB AAR (about 4-5 MB per ABI), its own battery and bootstrap cost, Tor updates to maintain.
- D. Wait for an Arti embedding library: + Rust, modern. / - No stable Android library found in Oct 2026.
REC: B now; revisit D in 2027.
### Gmail send path (SMTP leaks the client's public IP in Received)
- A. SMTP with XOAUTH2, show a one-time warning: + One protocol for both providers; simplest. / - Recipients see the user's IP unless a VPN or Tor is on.
- B. Gmail API users.messages.send (gmail.send scope): + No client IP in headers ('gmailapi.google.com with HTTPREST'). / - An extra HTTPS path; Google OAuth verification; the gmail.send scope must sit beside the IMAP scope.
- C. SMTP only through Tor or VPN for Gmail: + No new protocol. / - Gmail may challenge Tor exits; depends on the user's setup.
REC: B if the Gmail API is already planned for sync or labels; otherwise A plus the warning, with C as the advanced setting.
### Date header and quote line timezone
- A. Local zone (default of most clients): + Blends in with most mail. / - Leaks the user's timezone and travel.
- B. UTC '+0000', quote line also UTC or without time: + Hides the zone; common format. / - Times shown in some recipients' plain-text quotes are in UTC.
- C. '-0000' (RFC 'zone unknown'): + Semantically exact. / - Rare, so it is a fingerprint; some parsers mishandle it.
REC: B, on by default.
### Certificate trust model
- A. System CAs, hostname check, CT (Android 16 opt-in, 17 default): + No maintenance; no false alarms. / - Trusts every system CA (CT makes misissuance visible).
- B. A plus a CA-level pin-set with expiry (ISRG Root X1/X2/YE; GTS R1-R4 and GlobalSign): + Blocks rogue-CA interception for the 4 hosts. / - Breaks if a provider changes CA; needs regular app updates; Android advises against pinning.
- C. A plus leaf TOFU warnings: + Detects any change. / - Riseup changes its key every ~60 days, so the user sees warnings about 6 times a year (alarm fatigue).
REC: A. Consider B for Gmail only (stable GTS roots) with a 12-month expiry.
### Local database encryption
- A. Android file-based encryption plus optional app lock: + No library; background sync and notifications work. / - Data is readable by anyone with full device access after the first unlock.
- B. SQLCipher with a Keystore-wrapped random key: + Protects copied DB files. / - Large native library, open Room 3 driver bugs, little gain because the key is available whenever the app runs.
- C. SQLCipher with a user passphrase (Molly style): + Real protection while locked. / - No new-mail storage or notifications while locked unless a separate encrypted queue is built. Over-engineered for v1.
REC: A.
### Screen-capture protection
- A. Hide the Recents preview by default; FLAG_SECURE as an option: + Users keep screenshots. / - Content Capture is still on for API 37 unless the option is on.
- B. FLAG_SECURE always: + Maximum protection; also stops Content Capture. / - No screenshots or screen sharing; users complain.
REC: A.
### End-to-end encryption scope and timing
- A. No E2EE in v1: + Smallest app; ship faster. / - Less security for Riseup users who use PGP.
- B. Built-in OpenPGP (PGPainless 2.x) with Autocrypt L1 and RFC 9788 in phase 2: + Modern (RFC 9580/AEAD); no external app; matches the Delta Chat model. / - Bouncy Castle size and maintenance; key-handling UX to design.
- C. OpenKeychain integration: + Little code. / - Maintenance mode since 2021; cannot decrypt AEAD; poor UX (FairEmail lists many workarounds).
REC: A for v1, B in phase 2; do not choose C.
### When to emit the Autocrypt header
- A. Every outgoing message once E2EE is turned on for the identity (spec SHOULD): + Peers learn the key automatically. / - Publishes the public key to every recipient; long header.
- B. Only on signed or encrypted mail (FairEmail): + Fewer server problems with long headers. / - Peers rarely discover the key.
- C. Never; manual key exchange: + Least metadata. / - Encryption is almost never used.
REC: A, but only after the user turns on E2EE for that account.
### How links open
- A. Confirm sheet, then ACTION_VIEW in the default browser: + Respects the user's privacy browser; one code path. / - Leaves the app.
- B. Custom Tabs: + Faster, stays in context. / - Shares browser cookies and sessions with the tracking site.
- C. Ask every time: + Flexible. / - Extra tap on every link.
REC: A.
### Default message rendering
- A. Sanitized original HTML in a hardened WebView: + Looks like the sender intended; elegant. / - Larger attack surface than text (mitigated by the sanitizer, CSP and dead proxy).
- B. Reformatted or simplified view by default, original on tap (FairEmail): + Shows phishing links plainly; smaller attack surface. / - Many mails look wrong; more code.
REC: A, with a 'plain text' toggle per message.
### Keyboard incognito default for compose
- A. On (IME_FLAG_NO_PERSONALIZED_LEARNING): + Mail content does not train the keyboard's cloud or local models. / - The keyboard learns new words more slowly.
- B. Off with a toggle (Thunderbird): + Normal typing feel. / - Private text feeds the keyboard history.
REC: A.

## Open questions
- Does Riseup's inbound MX stamp Authentication-Results, with which authserv-id, and does it delete forged copies? One raw header from a Riseup inbox (checked by the user, not by us) settles it. Until then, show no authentication indicator for Riseup.
- Does Riseup's submission server keep the EHLO string in the first Received header? Only the IP removal is documented. Test with a self-sent message.
- Is the Gmail SMTP public-IP Received header consistent in 2026? One forum reply reports inconsistency. Test with a test account, with and without a VPN.
- Is the Gmail API in scope for other features (labels, sync)? This decides the Gmail send-path decision.
- How often does Google challenge OAuth logins and IMAP over Tor exits in 2026? Test with a throwaway Gmail account.
- Does Chrome (or Firefox) send an android-app://<package> Referer for third-party ACTION_VIEW links, and can a neutral EXTRA_REFERRER suppress it? Test with a header-echo page.
- Does Network Security Config CT enforcement (Android 16 opt-in / 17 default) apply to raw SSLSockets layered over a SOCKS socket with a custom hostname? FairEmail suggests yes; verify with a test that uses a non-logged certificate.
- Does the Android 17 ACCESS_LOCAL_NETWORK permission cover 127.0.0.1 (Orbot SOCKS)? The docs say nothing; test on API 37.
- Will Riseup always serve the mail.riseup.net certificate on its onion 993/465? It did on 2026-10-16, but Riseup's own guide expects warnings.
- Is a stable Arti library for Android apps expected in 2027 (Tor Project / Guardian Project roadmaps)?
- PGPainless 2.x plus Bouncy Castle size after R8, and decryption speed on low-end ARM. Compare with rPGP via JNI (Delta Chat) if size is too high.

## Verifier decision feedback
Most recommendations still hold. These need changes or caveats:
(1) Backup: replace 'omit <cross-platform-transfer>' with explicit exclude-all rules in <cloud-backup>, <device-transfer> and <cross-platform-transfer platform="ios">, plus allowBackup=false. The docs say a missing section means that mode is fully enabled.
(2) Tor B (Orbot SOCKS) is still right. Implement a small custom SOCKS5 handshake (RFC 1928/1929) with createUnresolved-style remote DNS. Java's Proxy(SOCKS) takes credentials from a global Authenticator, so per-account isolation cannot use it. The onion-over-TLS plan (verify the cert as mail.riseup.net) could not be re-probed and contradicts Riseup's own guide. Keep it, but fail closed (error, never plaintext fallback). Revisit Arti in 2027: an official Arti Mobile library exists but is build-from-source and lags the 2.x releases.
(3) Gmail send path: A plus a warning is the better v1 default. B (Gmail API) hides the IP but may stamp an app-identifying client token (2019 source), adds an HTTPS path and a sensitive scope. IMAP already needs the restricted https://mail.google.com/ scope, so Google OAuth verification is needed either way. Treat app passwords as an optional fallback, with a warning.
(4) Certificate trust A is still right. If B is used for Gmail, the pin-set must include GTS Root R4 (the ECDSA chain seen live), not only R1.
(5) WebView: drop the setForceDark branch (it is a no-op at targetSdk >= 33). Keep Safe Browsing off in the viewer: it would otherwise check allowed image URLs even when they are served through shouldInterceptRequest. The dead-proxy recommendation stays as defense in depth, but the Cure53 DNS leak was shown with JS on.
(6) Keystore 50k limit: not a concern (it applies only at targetSdk 37 and only with very many keys).
(7) E2EE: phase 2 with PGPainless still holds. Add an interop test for GnuPG LibrePGP OCB packets. PGPainless 2.0.4 pulls BC 1.84, slf4j and kotlin-stdlib, so the R8 size check stays open.
(8) Unwrapping google.com/url q= is justified even for IMAP-delivered Gmail bodies.
Unchanged: remote content A, Date header in UTC B (Thunderbird desktop's own sanitize pref also uses UTC with seconds 00), DB encryption A, screen-capture A, Autocrypt A, links A, rendering A, incognito keyboard A, EHLO [127.0.0.1] (both servers accepted it in the live probe), implicit TLS only, no DANE, no leaf TOFU.
