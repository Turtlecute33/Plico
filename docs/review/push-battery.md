# push-battery
Lens: push latency and battery (DESIGN.md §7.1, §7.3, §8, §9) in docs/DESIGN.md. The base design is correct and matches FairEmail and Thunderbird: one specialUse FGS, INBOX IDLE, one coalesced exact ELAPSED_REALTIME_WAKEUP alarm, the battery exemption first, the wake lock released during the blocking read, and TCP_USER_TIMEOUT. No critical findings. I found 16 major and 7 minor findings.

Main risk: lost-wakeup windows where mail is missed or delayed for a long time.
- kick() is lost when no IDLE is active (PB1).
- Mail that arrives between the last fetch and SELECT INBOX gets no event (PB2).
- The service PendingIntent alarm leaves a gap with no wake lock before onStartCommand runs (PB3).
- The network debounce holds no wake lock, and the alarm was already cancelled at onLost (PB5).
- The 60 s cap on each wake-lock acquire cuts long work and the in-process backoff (PB4).
- Ops and sends have no trigger at their due time (PB7).

Other breakage:
- Stopping before startForeground crashes the app on the Task Manager path (PB6).
- Notification updates are dropped above 5 per second, and setOnlyAlertOnce on the summary mutes later mail (PB8).
- A TLS error stops push until the user acts (PB9).
- The backoff has no definition of success, so reconnect loops are possible (PB10).
- Mail in notify=1 folders is not checked in the background (PB16).

Latency can improve at no battery cost:
- Post the notification right after the header fetch (PB15).
- Detect a dead Dovecot connection at c + margin, not 2.5c (PB12).
- Add NOOP to the Gmail refresh so a quiet IDLE is found (PB11).
- Check UIDNEXT before each IDLE (PB2).

Battery can drop:
- Run Gmail refreshes and polls during wakes that already happen, such as Riseup keepalives, with an interval-sized window as in Thunderbird (PB13).
- Add an 'Instant on Wi-Fi / poll on mobile data' mode for Riseup (PB14).
- Do less work per push event (PB15).
- Fix the server-mode rules (PB12).

One wrong fact: Riseup accounts on one phone do not always share the keepalive phase (PB18).

I checked these claims against AOSP main sources (PendingIntentRecord, ActiveServices, OomAdjuster, NotificationManagerService, PowerManager, ActivityManagerService), Dovecot 2.3.21 (cmd-idle.c, imap-keepalive.c), Thunderbird (RealImapFolderIdler, BackendIdleRefreshManager), FairEmail (GmailState) and the AlarmManager docs. While the FGS runs, an alarm may start it again: a running FGS gives the process the BFSL capability. So the PendingIntent problem is only the wake-lock gap and the restart after process death. I did not log in to a server and I changed no file. I deleted the temporary source files I downloaded to /tmp.

## PB1 [major] [valid] §7.1 AccountSession.kick / 4.3 ImapConnection.idle, done
PROBLEM: kick() can be lost. done() ends an IDLE only when one is active. Some kicks come while the loop syncs, or after SELECT but before IDLE is sent. Then there is nothing to end: the loop enters IDLE, and the request waits for the next server event or alarm (Gmail: 9-28 min, longer if the server is silent). The effects: openFolder/loadBody spin, a notification-action op does not run, and an alarm refresh does not happen. A kick after 'IDLE' is sent but before '+' puts DONE on the wire before the continuation. The design does not say which thread writes DONE. kick() from onStartCommand or ActionReceiver.onReceive runs on the main thread, and a TLS socket write there throws NetworkOnMainThreadException. The design also does not cover an EXISTS that arrives between the IDLE command and '+'.
FIX: kick() must write nothing. It sets an atomic 'workPending' flag and signals the session (a conflated Channel). The loop checks the flag just before it sends IDLE and does not send IDLE if the flag is set. idle() checks the flag again just after '+' and sends DONE at once if it is set. Any EXISTS/EXPUNGE/FETCH read before '+' also sets the flag. Only a coroutine on Dispatchers.IO writes DONE. Add scripted-server tests for three cases: a kick before IDLE, a kick between IDLE and '+', and an EXISTS before '+'.
VERIFY: §4.3/§7.1 say kick() 'sends DONE' and done() 'writes DONE once', with no pending-work state. A kick during sync either does nothing or writes a tagless DONE into a running command, which gets BAD. Then the loop goes back to IDLE and the work waits for the next event. kick() is a non-suspend fun that the main thread calls (onStartCommand, onReceive). Android's SocketOutputStream and Conscrypt call BlockGuard onNetwork, so a direct write there throws NetworkOnMainThreadException. Thunderbird RealImapFolderIdler keeps idleSent/doneSent and treats EXISTS/EXPUNGE/FETCH before '+' as a sync trigger. The flag + conflated-channel fix is the minimal correct pattern. Small note: Dovecot sends '+ idling' before its first sync, so EXISTS before '+' is a Gmail-only risk.

## PB2 [major] [valid] §7.1 loop order, 7.3 Gmail IDLE target
PROBLEM: Mail that arrives between the last new-mail fetch and the final SELECT INBOX gets no notification. The loop fetches new mail, then does other work (other folders, the backfill step, the Gmail All Mail pass), then SELECTs INBOX and starts IDLE. Messages that arrive in that interval are already counted in SELECT's EXISTS. IDLE reports only later changes, and a refresh (DONE + IDLE) does not sync. So these messages get no notification until the next EXISTS or reconnect. That can be ~24 h on a Gmail app-password session, and days on Riseup, where IDLE can run forever.
FIX: Keep a UID watermark for the IDLE mailbox: for Riseup, INBOX folder.uidnext; for Gmail, uidnext of the \Inbox label-view row (in INBOX UIDs). After every re-SELECT and before IDLE, compare UIDNEXT with the watermark. If UIDNEXT is higher, process new mail again and loop. For Gmail, run `UID FETCH <w>:* (UID X-GM-MSGID)` right after DONE, while INBOX is still selected. Then load the unknown X-GM-MSGIDs from All Mail and set w = highest INBOX UID + 1. Cost: no extra command on Riseup (SELECT returns UIDNEXT); one round trip per Gmail event.
VERIFY: This race is real. SELECT's EXISTS already counts mail that arrived after the last fetch, and RFC 2177 IDLE reports only later changes. A refresh is DONE/IDLE with no sync. On Gmail it is likely: two mails a few seconds apart, and the second lands after the All Mail fetch but before SELECT INBOX. It gets no notification until the next INBOX event. The delay is 'until the next mail', not always 24 h, but it hurts priority 1. A UIDNEXT watermark check before IDLE is free on Riseup (SELECT returns UIDNEXT) and costs one round trip on Gmail.

## PB3 [major] [valid] §8.3 Timers (alarm PendingIntent)
PROBLEM: The alarm uses PendingIntent.getForegroundService. AlarmManager holds its wake lock only while it delivers the PendingIntent. For a service PendingIntent, the system marks the alarm delivered right after it queues the start, before onStartCommand runs. The CPU can suspend in that gap. Then the refresh does not run. If the engine arms the next alarm when it handles the current one (the natural design), no alarm is armed, and push for silent client-mode accounts (Gmail) stops until another wake. There is a second gap in the inexact fallback (§8.2, neither grant). When the process is dead, an inexact while-idle alarm cannot start an FGS. The system swallows the exception, so push stays dead and nothing shows it. While the FGS runs, the start is allowed, because a running FGS gives the process the BFSL capability.
FIX: Use PendingIntent.getBroadcast (FLAG_IMMUTABLE) to an AlarmReceiver with exported=false. In onReceive, acquire the app wake lock, then give the alarm to the engine in-process. Only when the engine is not running, call startForegroundService inside try/catch (an exact alarm may start an FGS). Arm the next alarm, or a 2-min backstop, in finally, before the handler releases its lock. Let one scheduler object own the single PendingIntent and compute the earliest due time under a lock, so that one session cannot overwrite an earlier time from another. In inexact mode, the status line must say that push stops if Android kills the app.
VERIFY: Confirmed in AOSP PendingIntentRecord.sendInner. For INTENT_SENDER_FOREGROUND_SERVICE it calls startServiceInPackage, catches RuntimeException ('Unable to send startService intent'), and then calls finishedReceiver.performReceive at once. So AlarmManager releases its wake lock before onStartCommand runs, and the AlarmManager docs warn about this gap. The window is small but has no upper bound. If the process is dead, a failed FGS start is silent. With no grant, the inexact alarm has no FGS-start capability (G11). The research itself said to use an exported=false AlarmReceiver, and the design dropped it. One part of the fix is already in the design: one scheduler that computes the earliest due time.
BETTER FIX: Use getBroadcast(FLAG_IMMUTABLE) to an AlarmReceiver with exported=false. In onReceive, acquire the app wake lock, hand off to the engine, and arm the next alarm in finally. The receiver also checks the paused flag, so a paused or user-stopped app never starts the FGS (this removes PB6(1) for alarms). Start the FGS from the receiver only when the engine is not running, inside try/catch. With neither grant, the status line says push stops if Android kills the app.

## PB4 [major] [valid] §8.3 Wake lock (Power)
PROBLEM: The design uses one reference-counted lock, and every acquire has a 60 s timeout. (1) Work that takes longer than 60 s continues without a lock. Examples: a catch-up sync after hours offline, 25-body batches with text parts up to 2 MB, a backfill step, an SMTP upload of 25 MB, and the in-process backoff (retry at once, then 5 s and 20 s, each attempt with a 20 s connect timeout plus TLS/auth). The CPU can suspend during this work. The waits that use the uptime clock (20 s refresh wait, 2 s network debounce, 5/20 s backoff) can then take minutes. (2) Ownership is split across IdleHooks pairs. A read that throws skips afterRead. If the session's finally then releases, the count goes below zero, and a reference-counted release throws 'WakeLock under-locked'.
FIX: Give Power a scoped API, `power.hold(tag, maxMs) { … }`, that acquires and then releases in finally. Use one non-refcounted WakeLock per holder (each account session, the alarm handler, the network handler), so release() is idempotent. Renew the lock (acquire(60 s) again) on each server response and each progress step. A long sync then keeps the lock while it makes progress, and a stuck one loses it after 60 s. Cap one work unit at 10 min. Tags contain the account id, never the address. Add an engine test for this rule: no lock is released before the next alarm is armed.
VERIFY: With every acquire capped at 60 s, a sync, backoff sequence (0/5/20 s plus 20 s connects) or large SMTP upload that runs longer loses the lock. Uptime waits then stretch (G18). AOSP WakeLock.release() throws 'WakeLock under-locked' when a ref-counted lock's external count goes below 0. The split acquire/release across IdleHooks plus a session finally makes this easy: beforeBlockingRead releases, the read throws, afterRead is skipped, and finally releases again. A scoped hold{} on a non-refcounted lock per holder is simple. acquireLocked() removes the pending releaser when the lock is not refcounted, so re-acquire(60 s) on progress works as a renewal.

## PB5 [major] [valid] §8.3 Network (NetworkWatcher)
PROBLEM: (1) The callback path holds no wake lock, and the 2 s debounce runs on the uptime clock. onLost cancels the alarm. If onAvailable comes later with the screen off, the CPU can suspend during the debounce. There is then no socket and no alarm, and push stays dead until another wake (subway, airplane mode off, Wi-Fi with mobile data off). (2) Nothing recovers push if a callback is missed. (3) 'VALIDATED gained' and onBlockedStatusChanged(false) on the same network reconnect all sessions, healthy ones too. Validation and blocked state can flap, and each reconnect costs TLS plus a login (argon2 on Riseup). (4) After onLost closes the sockets, each session gets an IOException and starts its backoff (at once, 5 s, 20 s, then alarms) although there is no network. This conflicts with 'cancel the alarm'.
FIX: Acquire a 30 s lock in every callback, and keep it through the debounce and the reconnect. Store the Network each session connected on. On a new default network, reconnect only the sessions on another network. On VALIDATED gained or unblocked, reconnect only the sessions that are not connected. While there is no default network, park the sessions without a backoff, and keep one backstop alarm at 30 min (low cost, because the radio is off).
VERIFY: Network callbacks come with no app wake lock, and the 2 s debounce uses the uptime clock. onLost has already cancelled the alarm, so a screen-off onAvailable can leave the app with no socket and no alarm. On API 29+, onBlockedStatusChanged(false) follows onAvailable (G6), and VALIDATED often comes after the 2 s debounce (G35). 'Reconnect all' then reconnects healthy sessions twice for each network change, and each Riseup reconnect costs an argon2 login. The design does not say how backoff behaves with no network, and this conflicts with 'cancel the alarm'. The fix is small and correct.

## PB6 [major] [valid] §8.1 Service lifecycle (PushService)
PROBLEM: (1) If the service stops before it calls startForeground, the app crashes. Every alarm start uses startForegroundService. When the process was dead (after a Task Manager stop or an LMK kill), the new service has fgRequired set. The design then sets 'push paused by you' and stops, or stops because there is no account or push is paused. AOSP crashes an app whose service is brought down while it still waits for startForeground. (2) Without the battery exemption, a START_STICKY restart after process death can throw ForegroundServiceStartNotAllowedException. The design does not catch it. (3) 'StartReceiver enabled only while push is on' conflicts with 'A reboot clears the flag' if a Task Manager pause counts as push off. (4) REASON_USER_REQUESTED also covers remove-task kills (SUBREASON_REMOVE_TASK). On OEM builds that kill FGS apps on swipe, push would pause silently, with only a banner inside the app.
FIX: In onStartCommand, always call startForeground first, then decide, and call stopSelf after it if push must not run. Wrap startForeground in try/catch for ForegroundServiceStartNotAllowedException. On failure, arm an exact alarm for 1 min later (an exact alarm may start an FGS) and post the 'push stopped' alert. On a Task Manager pause: cancel the alarm, keep StartReceiver enabled (so a reboot resumes push), and post one silent notification 'Push stopped · Resume' (a notification action may start the FGS). Disable StartReceiver only when the user pauses push in the app.
VERIFY: (1) Confirmed in AOSP ActiveServices. bringDownServiceLocked with fgRequired posts SERVICE_FOREGROUND_CRASH_MSG ('Bringing down service while still waiting for start foreground'). The design starts from an alarm with getForegroundService and then 'sets paused and stops', which crashes the app after a Task Manager stop. (2) The research said to catch ForegroundServiceStartNotAllowedException on sticky restarts (G4/G34), and the design omits it. (3) 'StartReceiver enabled only while push is on' plus 'a reboot clears the flag' is a real contradiction. (4) Overstated: AOSP killProcessesForRemovedTask skips processes with an FGS, so this applies to OEM builds only. getSubReason is @hide, but getDescription() differs ('remove task'). The proposed silent 'Push stopped · Resume' notification covers the OEM case anyway.

## PB7 [major] [valid] §7.4 Ops, 7.5 Sender, 9 Actions
PROBLEM: Nothing runs ops and sends at their due time. Ops get run_at = now + 4 s, with backoff from 5 s to 1 h. Sends get send_at = now + 5 s. The session runs due work only 'before every sync', which means at the next server event or alarm. With the screen off, that can be minutes on Riseup or 9-28 min on Gmail. Polling accounts have no connection, so kick() does nothing until the next poll (up to 60 min). If the user taps Send and locks the phone, the mail goes out much later. Notification actions are worse: if they use the same op kinds, run_at is 4 s in the future, so the kick in goAsync finds no due work, the receiver finishes, and the server gets the archive or delete only at the next wake. If the engine is not running, the op waits until the user opens the app.
FIX: Ops and Sender give a nextDueAt value, and the engine treats it as one more due time. If it is due within ~60 s, hold the account lock and wait (the uptime clock is reliable while the lock is held). If it is due later, use the coalesced alarm. The user action that creates the op or the send acquires the lock at once. Notification actions use run_at = now, because they have no undo UI. For a polling or disconnected account, kick() opens a connection. If the engine is not running, ActionReceiver starts PushService (a notification action may start an FGS).
VERIFY: §7.4/§7.5 run due ops and sends only 'before every sync', and no rule wakes the session at run_at or send_at. A kick at action time finds the op not yet due (4 s or 5 s), so the work waits for the next event or alarm (Gmail 9-28 min, polling up to 60 min). With the screen locked after Send, mail can go out many minutes late. §7.4 gives archive/delete a 4 s run_at with no exception for notification actions, which have no undo UI. kick() on a polling account has no connection. The fix makes nextDueAt one more due time (wake lock and wait if it is soon, else the coalesced alarm). That is the minimal correct change.

## PB8 [major] [valid] §9 Notifications
PROBLEM: Three platform limits break alerts. (1) NotificationManagerService drops updates to an existing notification when the app's enqueue rate is above 5 per second. A sync that posts 5 or more new children and then updates the summary loses that update. The InboxStyle text is then stale, and because of GROUP_ALERT_SUMMARY the burst makes no sound. (2) 'setOnlyAlertOnce on updates': if this applies to the summary, mail #2 makes no sound when it arrives while the summary for mail #1 is still shown (the flag means 'alert only if the notification is not already showing'). (3) An app can show at most 50 non-FGS notifications. After a long offline period with several accounts, one child per message reaches this limit, and the system refuses new posts, including the newest mail.
FIX: For each account and each sync batch, build the summary from the DB and post it before the new children, with alert on (setOnlyAlertOnce(false)) when the batch has new mail. A new key is not rate-limited, but an update is. Post children only for the 5 newest messages, and show the older new ones as summary lines ('+N more'). Content-only updates (snippet, cancel) use setOnlyAlertOnce(true) and are combined into one per second per account. Keep fewer than ~40 children across all accounts, and cancel the oldest first. Debounce the FGS status text in the same way.
VERIFY: Confirmed in AOSP NotificationManagerService. DEFAULT_MAX_NOTIFICATION_ENQUEUE_RATE = 5f applies only when isUpdate ('Shedding'). MAX_PACKAGE_NOTIFICATIONS = 50 applies to non-FGS records ('Not showing more'). A burst of 5 or more new children followed by a summary update can drop the only alerting post under GROUP_ALERT_SUMMARY. setOnlyAlertOnce on an already-showing summary silences mail #2. One child per message across accounts can reach 50 after a long offline period. Summary-first with alert on, a cap on children, and batched silent updates is the right fix.

## PB9 [major] [valid] §6 AuthRequired/TLS, 8.3 Backoff
PROBLEM: After a TLS failure, the design stops all retries for the account until the user acts. Many TLS failures are temporary: a captive portal or hotel proxy that answers port 993 with its own certificate when it is the only default network (the design does not require VALIDATED), a server-side certificate incident (Riseup had a 4-hour CA-expiry outage on 2026-03-30), or a wrong phone clock after the battery ran out. Push then stays off after the cause is gone, possibly for days. The notification also says 'Sign-in needed', which is wrong for a TLS problem.
FIX: Keep fail-closed for each connection: no credentials go out before TLS is valid, as the design already requires. But do not stop the account. After a TLS failure, stop retries on that Network only. Retry on the next network change, and on the alarm backoff (15, 30, then 60 min cap). If the default network does not have VALIDATED, classify the failure as Network. Post 'Secure connection to <label> failed' only when the failure continues for 1 h or more, or happens on two different networks. Keep the no-retry rule only for AuthRequired, because of the lockout risk.
VERIFY: Retrying a TLS failure leaks nothing, because validation fails closed before AUTH. 'No retry' is needed only for auth lockout. Riseup R10 shows a real 4 h CA incident, and the design would keep push off until the user acts. The problem is worse than stated: Conscrypt throws SSLException and SSLHandshakeException for ordinary I/O errors ('Read error: ssl=…: I/O error during system call, Connection reset by peer'). §14 lists SSLException as a thrown type, so a plain cellular reset can be classified as Tls and stop push for good. The 'Sign-in needed' text is also wrong for TLS.
BETTER FIX: Add one rule to the proposed fix: classify as Tls only certificate and hostname failures (cause is CertificateException or CertPathValidatorException, SSLPeerUnverifiedException, or verifyHostname false). Map every other SSLException to Network. For Tls, use alarm backoff plus a retry on network change, and show the state in the app at once. Post a 'Secure connection failed' alert only if the failure continues or happens on a second network. Keep no-retry for AuthRequired only.

## PB10 [major] [valid] §8.3 Backoff
PROBLEM: The design resets the backoff 'on success' but does not define success. If success means connect + login, a path that fails soon after login makes a tight loop: login OK → reset → failure → 'retry at once' → and so on. Examples: a Gmail BYE after SELECT, a middlebox that resets long TLS flows, a NAT with a timeout under 1 min. Each cycle costs TLS and auth (argon2 on Riseup; on Gmail, connection-count and lockout risk) and battery. Throttled errors (Gmail 'Too many simultaneous connections', [UNAVAILABLE]) also start with 'at once, 5 s, 20 s', which makes the limit problem worse. And the design has no rule for a user action (pull to refresh, opening the app) during a 30-60 min alarm backoff.
FIX: Define a healthy connection: IDLE '+' received, and the connection stayed up for 2 min or more (or one refresh succeeded). Reset the backoff only then. A connection that dies earlier continues the backoff sequence. Throttled errors start at the 2-min alarm step and skip the in-process steps. A user action makes one attempt at once and does not change the stored step. Reset on a network change at most once for each new Network.
VERIFY: 'Reset on success' has no definition. A path that fails soon after login (BYE after SELECT, a middlebox reset, a short NAT) loops forever at 'retry at once', and each loop costs TLS plus auth (argon2, and Gmail connection-limit pressure, gmail G24). FairEmail adds fast-fail compensation for this reason (G3). Throttled is already a MailError class, but the backoff ignores it, so 'Too many simultaneous connections' gets immediate retries. There is also no rule for a user refresh during a long backoff. The fix is small and correct.

## PB11 [major] [partly] §8.3 Keepalive — client mode (Gmail)
PROBLEM: The adaptation measures only one thing: whether the socket is alive at the refresh. (1) It ignores closes by the server. If Gmail ends IDLE after ~10 min with BYE/FIN, the +2 min steps take the interval above that limit. Because only deaths found by a refresh count, the interval never comes down. Plico then does a full reconnect (TLS, XOAUTH2, SELECT, All Mail sync) about every 10 min, instead of a cheap DONE/IDLE at 9 min. (2) 'Alive' does not mean 'delivering'. Field reports say Gmail IDLE can go quiet after 15-20 min without a close. The DONE/OK check still passes, the interval grows to 28 min, and new mail waits up to 28 min. (3) 'lock; unlock after the next failure' is not clear. As written, a second failure at the locked value allows growth again instead of a lower value. The interval then oscillates around the failing value, and each upward probe costs one period of delayed push.
FIX: Make the client-mode refresh DONE → NOOP → IDLE: one more round trip in a wake that already happens. Count three cases as a failure: (a) the refresh found the socket dead; (b) NOOP or the DONE response showed an EXISTS that IDLE did not push; (c) the server sent BYE or closed at IDLE age ≥ 5 min with no network change. In case (c), also cap the interval at (age − 1 min). On a failure, lower the interval by 2 min (minimum 5) and set it locked. A locked interval never grows, and each later failure lowers it again. Unlock only on a new network key or after 24 h. Add KeepalivePolicy unit tests for these rules.
VERIFY: (3) is real. 'Lock; unlock after the next failure' inverts FairEmail, which locks after successes (G2). As written, a second failure allows growth again, so the interval oscillates around the failing value. (1) is real but only costs efficiency. A server close at about 10 min arrives as FIN/BYE and goes to the reconnect path, never to 'refresh found dead', so the interval never comes down. Plico then does a full reconnect about every 10 min instead of a cheap refresh. No mail is lost, because the FIN wakes the phone. (2) has weak evidence: gmail G26 says the Home Assistant cause is 'not clear: NAT or server'. Detecting 'an EXISTS that IDLE did not push' from a NOOP is racy, because a mail can arrive at that moment.
BETTER FIX: Do not add NOOP. Count two cases as a failure: a refresh that finds the socket dead, and a server BYE or close at IDLE age ≥ 5 min with no network change. In the second case, also cap the interval at (age − 1 min). On a failure, lower by 2 min and lock. A locked interval never grows, and each later failure lowers it again. Unlock only on a new network key or after 24 h. Add unit tests in KeepalivePolicy.

## PB12 [major] [partly] §8.3 Keepalive — server mode (Riseup/Dovecot)
PROBLEM: (1) The design takes the cadence c as the median gap between server bytes. Dovecot realigns its keepalive timer after any other output: idle_add_keepalive_timeout runs when output was sent, and the interval is shortened to the hash phase. So gaps after an EXISTS or FETCH are shorter than c. Busy mailboxes therefore make c too low, and the dead-peer alarm fires falsely. (2) If c later grows, or the server stops sending keepalives, the stored c stays. Each dead-peer alarm at lastByte + 2.5c finds the socket alive and arms another one. That is a wake every 5 min (288 per day) with no server keepalive, which is worse than client mode. (3) The 'c ≤ 5 min' limit has no basis. With c = 10 min, the design uses client mode and adds its own 15-min alarm, although the server keepalives already keep the NAT open and prove the link is alive. (4) 2.5c is slow. Dovecot's schedule follows the wall clock exactly, so the client knows a keepalive is missing at c plus a small margin. With 2.5c, Riseup needs 5 min to find a dead path.
FIX: Compute c only from ServerKeepalive events (consecutive '* OK Still here'). Use server mode when c is less than the client interval for the current network. Set the dead-peer alarm to lastKeepalive + c + max(30 s, c/4): 2.5 min on a Riseup default, not 5. If a dead-peer alarm finds the socket alive, clear server_keepalive_s, go to client mode, and measure again. The battery cost does not change, because the alarm fires only when a keepalive is missing. The delay after a silent drop is about half.
VERIFY: The Dovecot facts are right. cmd-idle.c calls idle_add_keepalive_timeout after other output, and imap_keepalive_interval_msecs aligns each keepalive to (time + hash) mod interval. So keepalive-to-keepalive gaps are exactly c, and gaps after an EXISTS are shorter. (1) A false alarm needs 2.5c below the true gap, so c under 48 s, so 3 of the last 5 gaps must be very short. That happens only on a very busy INBOX, and the cost is one extra refresh. (2) is overstated: refresh replies are server bytes, so the median grows by about 2.5x every few cycles and moves to client mode after about 6 alarms, not 288 per day forever. (3) is minor. (4) Tighter detection is a fair gain from the wall-clock alignment. But the fix's 'one alive dead-peer alarm → client mode' is too eager on lossy cellular links.
BETTER FIX: Compute c only from consecutive ServerKeepalive events. Set the dead-peer alarm at lastKeepalive + c + max(30 s, c/4). Leave server mode only after 2 consecutive dead-peer alarms that find the socket alive. Use server mode whenever c is less than the client interval for the network, not a fixed 5 min.

## PB13 [major] [valid] §8.3 Timers — coalescing
PROBLEM: The engine coalesces work only when its own alarm fires, with a fixed 3-min window. This misses the biggest saving for the target setup, Riseup and Gmail on one phone. The Riseup keepalive already wakes the CPU and radio every ~2 min, but Gmail still uses its own alarm: at the 9-min start, that is about 160 extra radio wakes per day. Two Gmail accounts whose phases differ by more than 3 min never align, so N accounts cost N wakes per interval. Polls (15/30/60 min) are approximate by design, but they also get only the 3-min window.
FIX: Make every wake a point for coalescing: the alarm, any server byte (keepalive or EXISTS), a network callback, and the app becoming visible. At each one, run every client refresh, poll and OAuth reconnect that is due before now + W. W = max(3 min, interval/3) for refreshes, and interval/3 for polls. An early refresh only shortens one cycle, and after one cycle the phases align. With a Riseup account in server mode, Gmail refreshes and polls then run during Riseup keepalive wakes, and the Gmail alarm is only a backstop. Code: the IDLE thread calls engine.onWake() from afterRead.
VERIFY: Confirmed. Thunderbird BackendIdleRefreshManager fires every timer due before now + minTimeout − MIN_TIMER_DELTA (1 min), so its window is about the full interval, not 3 min. With a fixed 3-min window, accounts with the same interval and phases more than 3 min apart never align. A Riseup server-mode connection already wakes CPU and radio about every 2 min, so a Gmail refresh or a poll can ride on those wakes with no extra radio promotion (G26, android-push missed fact). This adds little code (engine.onWake() from afterRead) and saves up to about 160 wakes per day. One gap in the fix: early refreshes must not count as 'alive at interval' in the keepalive adaptation.
BETTER FIX: Use the proposed fix and add one rule: a refresh that runs early (age < interval) does not count toward interval growth, but its failure still counts.

## PB14 [major] [partly] §8.3 Riseup cost note, 13 account settings
PROBLEM: The Riseup mode is all or nothing for each account: Instant, or a poll every 15/30/60 min. The 2-min keepalive is expensive only on cellular: up to ~12.6 J per LTE wake, against tens of mJ in Wi-Fi power-save. A user who wants instant mail at home must accept ~720 cellular wakes per day outside, or a 15-60 min delay at home. The research recommended a default that depends on the transport (android-push D5-C). The design dropped it and gives no reason.
FIX: Add one mode: 'Instant on Wi-Fi and while charging, every N min on mobile data'. Make it the default for Riseup when the measured c ≤ 3 min. Gmail stays Instant, because Gmail is silent during IDLE. NetworkWatcher already knows the transport; on a transport change, the engine moves the account between IDLE and polling. Small code, no new permission.
VERIFY: The research recommended D5-C, and the design dropped it without a reason. A transport-aware mode is cheap, because NetworkWatcher already knows the transport. But the problem is overstated. 12.6 J per wake is a 2012 LTE upper bound, and G26 says modern C-DRX and 5G cost much less. Making cellular polling the default trades away priority 1 (fastest notifications) on cellular, which is a product choice and not a bug.
BETTER FIX: Add the option 'Instant on Wi-Fi or while charging, every N min on mobile data' next to Instant and poll. Show the measured keepalive cost to recommend it. Keep Instant as the default.

## PB15 [major] [valid] §7.1 loop, 7.2 Standard sync, 7.3 Gmail, 9 notify
PROBLEM: (1) Order. syncNow(push) means 'flush ops, then sync' every mailbox with sync = 1, and bodies come last (step 7). The design does not say when Notifier posts. If it waits for the full pass, or for a body to show a snippet, notification delay grows with the number of folders, the body size (text parts up to 2 MB), and any queued send (a 25 MB upload on cellular takes minutes). (2) Cost per event. Every EXISTS/EXPUNGE/FETCH ends IDLE and runs the standard algorithm, including step 6 (`UID SEARCH UID <lowest>:*`). On a Gmail All Mail with 100k messages, that is a large ESEARCH set and a diff of 100k rows for each new mail. With NOMODSEQ (possible on Riseup TREES), step 5 fetches FLAGS again for the whole local range at each event. Bursts of FETCH events, for example when the user reads mail on a desktop, repeat all of this. (3) The Gmail category filter sends one SEARCH for each enabled category.
FIX: Define a fast path for push events. DONE → fetch new headers of the IDLE mailbox (Gmail: new All Mail UIDs with labels, plus one search such as `X-GM-RAW "category:primary OR category:updates"`) → commit → post notifications. After that: flush due ops, sync only the other folders whose STATUS changed, fetch bodies, update the notification text silently, do the UIDNEXT check (PB2), and IDLE. Skip step 6 when the server MESSAGES count equals the local count after the new rows. Without CONDSTORE, a push event fetches flags for the newest 200 UIDs only; the full range runs when the user opens the folder or every 6 h. Debounce IDLE events for 1 s under the lock to batch bursts.
VERIFY: §7.4 runs due ops before every sync, and 'send' is an op kind. So a 25 MB upload or other queued work can run before the new-mail fetch. The design does not say when Notifier posts relative to step 7 bodies or the other mailboxes. Each push event runs the full standard algorithm, including step 6's whole-range UID SEARCH and diff, and the NOMODSEQ fallback refetches FLAGS for the full range. A defined fast path (new headers of the IDLE mailbox → commit → notify → then ops, folders, bodies) fixes priority 1 at almost no code cost. One OR'd X-GM-RAW search and a 1 s debounce are cheap improvements. Detail: the 'MESSAGES equals local count' skip is valid only when backfill is complete; otherwise compare ESEARCH COUNT for UID ≥ backfill_uid.

## PB16 [major] [valid] §9 New-mail rule (folder.notify), 7.3 label views
PROBLEM: folder.notify = 1 promises notifications for folders and labels other than the inbox. But nothing checks those folders soon in the background. IDLE watches INBOX only, a refresh does DONE/IDLE without a sync, and a full sync runs only on INBOX events and reconnects. Riseup filters put mail into other folders, and Dovecot lets IDLE run forever, so such mail can wait for days. On Gmail, mail with a 'skip the inbox' label waits for the next INBOX event or reconnect: up to ~24 h with an app password.
FIX: Send STATUS at three points: every client refresh, every Dovecot re-IDLE (≤ 25-28 min), and every push fast path. Send `STATUS <folder> (UIDNEXT)` for each Riseup folder with notify = 1. For Gmail, send `STATUS "<All Mail>" (UIDNEXT)` when any label has notify = 1. On a change, sync and notify. This adds one round trip per folder inside a wake that already happens. The folder setting says 'Notifies within about 25 min'.
VERIFY: §9 promises notify for folder.notify = 1, but IDLE watches only INBOX, a refresh is DONE/IDLE with no sync, and Dovecot allows IDLE forever (R13). Sieve-filed Riseup mail and Gmail skip-inbox labels make no INBOX event, so they wait for the next INBOX mail or a reconnect. The research decisions (riseup A: STATUS-poll the other folders; gmail C: a LIST-STATUS sweep on each wake) covered this, and the design dropped it. Adding STATUS UIDNEXT to wakes that already happen costs one round trip. For Gmail there is an alternative the research names: IDLE on All Mail when any label has notify = 1.

## PB17 [minor] [valid] §8.3 OAuth reconnect, 6 Credentials.expiresAt
PROBLEM: Gmail ends an OAuth session when the access token used for that session expires, not 1 h after the connect. OAuthCredentials refreshes the token only 5 min before expiry. So a reconnect after a network change at token age 45 min gets a session of about 15 min, and then a second reconnect follows. DeviceCredentials cannot know the token age, because AccountManager returns its cached token; expiresAt is not defined for it. The expiry is also a separate due time that coalesces only within 3 min of a refresh, so it often costs one extra wake per hour.
FIX: On every OAuth or device-auth IMAP connect, use a token with at least 45 min left, and refresh it if not. For a device account: call invalidateAuthToken + getAuthToken when the token was acquired more than 10 min ago or at an unknown time. Store the acquired time, and refresh at most once per 10 min. Then expiresAt = acquired + 55 min is known. Treat `* BYE` session expired as a normal reconnect: no backoff step, and invalidate the cached token. At a refresh wake, if expiresAt comes before the next refresh, reconnect now instead of refreshing.
VERIFY: Minor. G8 says an OAuth session 'lasts approximately the validity period of the access token used'. FairEmail GmailState confirms the practice: it stores 'acquired', assumes TOKEN_LIFETIME = 60 min, and force-refreshes when less than MIN_FORCE_REFRESH_INTERVAL (15 min) is left. With a refresh only 5 min before expiry, a reconnect at token age 45 min gets a short session and a second reconnect. DeviceCredentials has no defined expiresAt, so the session expiry goes through the error and backoff path. Refreshing when less than about 45 min is left, and treating a 'session expired' BYE as a normal reconnect, is simple.

## PB18 [minor] [valid] §8.3 Riseup cost note
PROBLEM: The design says as a fact that all Riseup accounts on one phone share the keepalive phase. That is not always true. Dovecot uses the client IP for the phase only when the backend sees a public client IP. For private or proxy-hidden IPs, it hashes the username. The riseup research reports that Riseup's front-end to back-end hop uses 10.0.1.x addresses. If so, N Riseup accounts cost N × ~720 wakes per day.
FIX: Describe both cases in the design. Record the keepalive times of each account. If the keepalives of two accounts do not arrive within ~1 s of each other, show the total cost and suggest polling (or the PB14 mode) for the second account.
VERIFY: Dovecot imap_remote_ip_is_usable rejects 10/8, 172.16/12 and 192.168/16, and then uses crc32(username). The riseup research (missed fact) infers a 10.0.1.x front-end hop, which gives different phases for each account. The design states the opposite android-push inference as fact. Whether Riseup forwards the client IP is unknown. The fix needed is to reword §8.3 to cover both cases and to show the measured cost per account. The extra alignment-detection logic is optional.

## PB19 [minor] [partly] §8.3 Keepalive — network key
PROBLEM: The network key is transport + hash(interface name + DNS servers). On cellular, the interface name (rmnet_dataN) and the carrier DNS addresses change between attaches, so the learned value is often lost, and cellular is the network type with the shortest NAT timeouts. On Wi-Fi the interface is always wlan0, so only the DNS servers make keys different, and many routers use the same 192.168.x.1. The design never removes old keys.
FIX: For cellular, use one key ('cellular', or transport + carrier id). For Wi-Fi, use a hash of the DNS servers + the IPv4 default gateway. Keep at most 16 keys in Prefs, and remove the least recently used.
VERIFY: The cellular part is real. rmnet_dataN and carrier DNS change between attaches, so the learned value is lost on the network type with the shortest NAT timeouts (G25). Unbounded key growth in Prefs is also a real small gap. The Wi-Fi part of the fix adds little: on most home routers the IPv4 gateway and the DNS server are the same 192.168.x.1 address, so adding the gateway does not separate networks.
BETTER FIX: Use one key for cellular ('cellular'). For Wi-Fi, keep hash(DNS servers) as it is. Keep at most 16 keys with LRU eviction. Do not use carrier id or the gateway.

## PB20 [minor] [partly] §7.3 Gmail sync, 9 cancel on archive
PROBLEM: When the user archives a message on another device, Plico must cancel its notification and remove it from the unified inbox. INBOX IDLE reports this only as `* n EXPUNGE`, a sequence number, and the design keeps no map from INBOX sequence numbers to messages. The design depends on All Mail CHANGEDSINCE to return the label change. Whether Gmail raises MODSEQ for X-GM-LABELS changes is an open question in the research. If it does not, archived mail stays in the unified inbox and its notification stays.
FIX: Put this live test on the test list before the design relies on it. Add a small fallback: store the INBOX UID of each notified message (from the INBOX FETCH in PB2). On an INBOX EXPUNGE event, run `UID SEARCH UID <those UIDs>` in INBOX, then cancel the notifications and remove \Inbox membership for the UIDs that are missing.
VERIFY: The dependency is real and untested. gmail open questions ask whether X-GM-LABELS changes raise MODSEQ, and §7.3 relies on this for archive-elsewhere. Adding the live test to the test list is correct. But Gmail is widely reported to bump MODSEQ on label changes, and the proposed fallback adds a new stored INBOX-UID mapping (schema plus an extra FETCH), which is more than needed.
BETTER FIX: Add the live test. If it fails, use a fallback that needs no new state: on an INBOX EXPUNGE event, in All Mail run `UID SEARCH UID <All Mail UIDs of local \Inbox rows> X-GM-LABELS \Inbox`, then remove \Inbox membership and cancel notifications for the UIDs that are missing.

## PB21 [minor] [valid] §9 New-mail rule (notification watermark)
PROBLEM: The design does not define 'newer than the account's notification watermark'. If the watermark is a date, for example message.date from the Date header, a message from a sender with a wrong clock, or a message delivered late, gets no notification. A spam message with a future Date moves a date watermark forward.
FIX: Define the watermark as a UID for each notifying mailbox (for Gmail, the All Mail UID). Set it to UIDNEXT at account setup, and when the user turns on notify for a folder. Notify only when uid ≥ watermark, notified = 0, the message is unseen, and the folder and category rules match.
VERIFY: §9 uses 'the account's notification watermark', but the schema has no such column and the design gives no definition. A date watermark from the Date header fails on wrong sender clocks and on late delivery, and a future-dated spam moves it forward. A UID watermark per notifying mailbox (All Mail for Gmail) is the simple, correct definition. Set it to UIDNEXT at setup, when notify is turned on, and after a UIDVALIDITY reset.

## PB22 [minor] [invalid] §8.3 Polling accounts
PROBLEM: Each poll does TCP + TLS + AUTHENTICATE (argon2 on the Riseup server) + COMPRESS + ENABLE + sync + LOGOUT. At 15 min, that is 96 times per day. Dovecot sends 'Still here' only during IDLE, so an open connection that is not in IDLE causes no wakes.
FIX: For 15-min polls on Riseup, keep the authenticated connection open without IDLE. At each poll, send NOOP (10 s timeout under the lock) and sync; if NOOP fails, reconnect. For 30- and 60-min polls, which exceed Dovecot's 30-min autologout, disconnect after the poll as the design does now. This is the session loop without IDLE, so it adds almost no code.
VERIFY: The facts are right (Dovecot sends 'Still here' only inside IDLE, autologout is 30 min), but the gain is weak. Polling has the same number of radio wakes either way, and the radio tail dominates the energy (G26). A full login adds only a few RTTs. A connection kept open without traffic for 15 min will often lose its NAT entry on cellular (G25: about 17 of 73 carriers under 20 min). Each poll then waits up to TCP_USER_TIMEOUT 30 s under a wake lock before it reconnects anyway. Polling is the user's explicit battery-saver mode, and disconnect after the poll is the simpler and more robust choice.

## PB23 [minor] [valid] §8.2 Power grants, 8.3 alarm fallback
PROBLEM: The grants can change while the app runs. The user can remove the battery exemption in Settings, and the app is not killed. If SCHEDULE_EXACT_ALARM is also missing, setExactAndAllowWhileIdle then throws SecurityException, and an uncaught exception in the scheduler stops push. If the user grants the exact-alarm permission outside the app, nothing tells the engine to leave the inexact fallback.
FIX: Check canScheduleExactAlarms() each time an alarm is armed, and catch SecurityException: fall back to inexact and update the status line. Add SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED to StartReceiver. Check isIgnoringBatteryOptimizations() again at each app start and each time the 'Push & battery' screen opens.
VERIFY: Minor but real. An app can lose the battery exemption at runtime without being killed. Only the revocation of SCHEDULE_EXACT_ALARM stops the app (G21). After that, setExactAndAllowWhileIdle throws SecurityException, and an uncaught throw in the alarm path stops push. FairEmail AlarmManagerCompatEx falls back exact → inexact on SecurityException (G2). The research already listed SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED for StartReceiver. The fix is to check canScheduleExactAlarms() and catch the exception on each arm, which is a few lines.
