# android-apis
Lens: Android API feasibility at API 35-37. I checked the claims against android.jar stubs (API 35, 36, 37 on this Mac, via javap), AOSP main (ActiveServices, AlarmManagerService, ActivityManagerService, ApplicationExitInfo), Conscrypt, Chromium (aw_proxying_url_loader_factory.cc, Blink computed_style.cc), the material3 1.5.0-beta01 and navigation3 1.2.0 source jars, compose-ui 1.12.1, developer.android.com, and FairEmail source.

Claims that are correct:
- A specialUse FGS with the subtype property is valid.
- An exact while-idle alarm can start the FGS from the background (AOSP gives it mOptsWithFgs). When the FGS already runs, startForegroundService passes, because AOSP keeps the earlier allow reason and logs "already foreground; no new timeout".
- The battery allowlist makes every alarm UNRESTRICTED and exempts FGS starts.
- getHistoricalProcessExitReasons and REASON_USER_REQUESTED exist (public API 30). This reason also covers Settings force stop, Recents removal and adb kills. A running FGS defers the Recents kill.
- Os.setsockoptInt, OsConstants.TCP_USER_TIMEOUT and ParcelFileDescriptor.fromSocket are public in the API 35, 36 and 37 stubs.
- Conscrypt honours endpointIdentificationAlgorithm="HTTPS".
- The CT element syntax is <certificateTransparency enabled="true"/>.
- setAlgorithmicDarkeningAllowed is a platform API since API 33.
- Chromium still calls shouldInterceptRequest when blockNetworkLoads=true (it blocks only by forcing cache-only loads).
- CookieManager, setRecentsScreenshotEnabled (API 33) and BiometricPrompt with STRONG|DEVICE_CREDENTIAL exist.
- InterceptPlatformTextInput is stable in compose-ui 1.12.
- NavDisplay takes any List<T>.
- MaterialExpressiveTheme no longer needs an opt-in in 1.5.0-beta01. That beta depends on stable foundation/ui 1.12.0, which matches BOM 2026.09.00. SwipeToDismissBox(onDismiss) and PullToRefreshBox exist.
- AGP 9 built-in Kotlin works next to a kotlin("jvm") module.
- Android 17: ACCESS_LOCAL_NETWORK is not needed, ECH does not apply to raw sockets, and the cross-profile loopback block does not apply (no Tor).

Research correction: API 37 adds a public listener overload of setExactAndAllowWhileIdle (android-push G21 says @SystemApi). It does not help at minSdk 35.

Main problems:
- (1) PushService crashes if it stops before startForeground.
- (2) The alarm-to-service PendingIntent has a wake-lock gap, and the inexact fallback cannot restart push.
- (3) The base CSS color-scheme declaration defeats algorithmic darkening.
- (4) The saved SwipeToDismissBox state breaks the toggle actions and Undo.
- (5) The device-account sign-in has no account chooser and no token-expiry tracking.

The rest are smaller API gaps: notification PendingIntents, summary alerting, manifest permissions, nav3 serialization, the socket construction, CT coverage, lint for :mail, image re-encode, power-grant states, OAuth state on process death, and wake-lock renewal.

Not tested: the AccountManager Gmail token for an unregistered sideloaded signature (it needs a device test). No change was made to any file. Temporary downloads in /tmp were deleted.

## AF1 [major] [partly] §8.1 Service (push paused check, onStartCommand)
PROBLEM: In the design, PushService reads the exit reason on start and then does 'set push paused by you and stop'. The same applies to any start where the service decides not to run. A service started through startForegroundService (alarm PendingIntent.getForegroundService, BOOT_COMPLETED, MY_PACKAGE_REPLACED) that calls stopSelf before startForeground crashes the app with 'Context.startForegroundService() did not then call Service.startForeground()'. The alarm is still scheduled, so the crash comes back at each alarm. Separately, a START_STICKY restart can throw ForegroundServiceStartNotAllowedException in startForeground when the battery exemption is missing.
FIX: Rule for PushService.onStartCommand: always call startForeground(ID, notification, ServiceInfo.FOREGROUND_SERVICE_TYPE_SPECIAL_USE) first, inside try/catch(ForegroundServiceStartNotAllowedException). If the call throws, post the 'Push stopped, open Plico' alert and stop. Only after that call do the paused, no-accounts or exit-reason checks. Then use stopForeground(STOP_FOREGROUND_REMOVE) + stopSelf(). When you set 'push paused by you', also cancel the alarm PendingIntent and disable StartReceiver, so that nothing starts the service again.
VERIFY: The core fault is real and serious. In AOSP main, ActiveServices.bringDownServiceLocked posts SERVICE_FOREGROUND_CRASH_MSG when a service is brought down while r.fgRequired is set. Section 8.1 does 'set push paused by you and stop' on starts that come from the alarm or from MY_PACKAGE_REPLACED, both of which use startForegroundService. G34/G4 (Thunderbird #7416) show that a sticky restart can throw ForegroundServiceStartNotAllowedException, and the design has no catch for it. Two parts are overstated or wrong. (1) 'The crash comes back at each alarm': the alarm is one coalesced one-shot, and nothing re-arms it after the service stops, so the crash happens about once. The crash does replace REASON_USER_REQUESTED with REASON_CRASH, which defeats the paused check later. (2) The fix says to disable StartReceiver. That contradicts the design rule 'A reboot clears the flag', which needs the boot receiver to stay enabled.
BETTER FIX: In PushService.onStartCommand, always call startForeground(ID, n, FOREGROUND_SERVICE_TYPE_SPECIAL_USE) first, inside try/catch(ForegroundServiceStartNotAllowedException). If it throws, post 'Push stopped, open Plico' and stopSelf. Only after that, run the paused, no-accounts and exit-reason checks. To stop, call stopForeground(STOP_FOREGROUND_REMOVE) and then stopSelf(). When you set 'paused by you', cancel the alarm PendingIntent. Keep StartReceiver enabled so that a reboot still resumes push. On MY_PACKAGE_REPLACED, check the paused flag in the receiver and do not start the service.

## AF2 [major] [valid] §8.3 PushEngine Timers / 8.2 Power grants
PROBLEM: There are two defects in the alarm path setExactAndAllowWhileIdle -> PendingIntent.getForegroundService -> onStartCommand. (a) For a service PendingIntent, AlarmManager releases its own wake lock as soon as the send returns. Thus the CPU can suspend before onStartCommand acquires the Power lock, and the keepalive or dead-peer check then runs late. (b) The fallback setAndAllowWhileIdle (no exemption and no exact-alarm permission) gets a temp allowlist WITHOUT the FGS-start capability. After any process death (low-memory kill, OEM kill, Android 17 MemoryLimiter), the alarm cannot start PushService. The start fails silently in system_server, and push stays dead until the user opens the app. The status 'push works with delays' is wrong for this case.
FIX: Send all alarms as an explicit broadcast: PendingIntent.getBroadcast(ctx, 0, Intent(ctx, AlarmReceiver::class.java), FLAG_IMMUTABLE), with <receiver .push.AlarmReceiver exported=false>. In onReceive, while AlarmManager still holds its wake lock: Power.acquire(). If push is paused, cancel the alarm and return. If the engine is alive, call engine.onAlarm(). Else try startForegroundService and catch ForegroundServiceStartNotAllowedException; if it throws, post 'Push stopped, open Plico' on the alerts channel. Use the same receiver for the inexact fallback. Change the status text with neither grant to 'Push stops if Android closes the app'.
VERIFY: Both parts are confirmed in AOSP main. (a) PendingIntentRecord.sendInner, in the INTENT_SENDER_FOREGROUND_SERVICE branch, calls finishedReceiver.performReceive immediately after startServiceInPackage. AlarmManager's DeliveryTracker then releases its wake lock before onStartCommand runs. The AlarmManager class doc also warns about this. For broadcasts, sendFinish=false, so the lock is held until the receiver finishes. In client mode (Gmail), a missed handling means the next alarm is never armed, so push can die silently. (b) AlarmManagerService.set() gives inexact allow-while-idle alarms mOptsWithoutFgs ('temporary allow-list ... but without FGS capability'). startServiceLocked then throws ForegroundServiceStartNotAllowedException, and PendingIntentRecord catches it and only logs it ('Unable to send startService intent'). So 'push works with delays' is wrong after process death. The broadcast fix is safe on Android 17 QPR2: the self-broadcast change excludes broadcasts sent through a PendingIntent. The proposed AlarmReceiver is also the receiver that research Implications already lists.

## AF3 [major] [valid] §11.1 Output document base CSS / 11.2 Dark email
PROBLEM: The base CSS has 'color-scheme: light dark'. This tells Blink that the page supports dark mode, so WebView does NOT apply algorithmic darkening (setAlgorithmicDarkeningAllowed is ignored for that page). In a dark app theme, the canvas becomes #121212 and the default text becomes light, but the sender's explicit colours stay. The result is dark text on a dark background in most HTML mail, with 'Dark email' on and also with it off. Separately, WebView takes prefers-color-scheme and darkening from the activity theme's isLightTheme. The usual Compose template theme (Theme.Material.Light.NoActionBar) keeps isLightTheme=true in night mode, and then darkening never happens.
FIX: Remove color-scheme from the base CSS. With 'Dark email' on: setAlgorithmicDarkeningAllowed(true) and no color-scheme declaration. For 'Show original colours' (or Dark email off): setAlgorithmicDarkeningAllowed(false) and add ':root{color-scheme: only light}', so that the page keeps a white canvas. Give MainActivity a day/night platform theme: values/themes.xml parent android:Theme.Material.Light.NoActionBar, values-night parent android:Theme.Material.NoActionBar. Then isLightTheme follows the system.
VERIFY: Confirmed in Blink ComputedStyleBuilder::SetUsedColorScheme. With 'color-scheme: light dark' and a dark preferred scheme, has_dark is true, so dark_scheme is true and forced_scheme is false. The page then gets a dark canvas and light default text, with no algorithmic darkening, and the sender's explicit dark colours stay: dark text on a dark background. The Android WebView dark-theme doc says darkening applies only if the content does not opt in, and that 'WebView always sets prefers-color-scheme according to isLightTheme'. The theme part is real in the actual repo, but the reverse of what the finding assumes: app/src/main/AndroidManifest.xml uses @android:style/Theme.Material.NoActionBar, which is always dark (isLightTheme=false). WebView therefore reports dark even when the system is in light mode.
BETTER FIX: Remove color-scheme from the base CSS. Use setAlgorithmicDarkeningAllowed(darkTheme && darkEmail && !showOriginal). With no color-scheme declaration and darkening off, the canvas is already light, so 'only light' is optional. Add res/values/themes.xml with parent android:Theme.Material.Light.NoActionBar and res/values-night/themes.xml with parent android:Theme.Material.NoActionBar, and point the manifest at that theme.

## AF4 [major] [valid] §13 Mailbox swipe actions
PROBLEM: In material3 1.5.0-beta01, rememberSwipeToDismissBoxState is rememberSaveable. SwipeToDismissBox turns gestures off when settledValue != Settled, and it calls onDismiss from LaunchedEffect(state.settledValue). This causes three faults. (1) Toggle actions (Read/Unread, Star, None) leave the row slid off-screen, and it cannot be swiped again. (2) After Undo, the restored row has the same LazyColumn key. The lazy SaveableStateHolder restores the saved 'dismissed' state, so the row shows as an empty gap. The LaunchedEffect can also run again and archive or delete the message again. (3) The default positionalThreshold is 56 dp, so an accidental archive is easy.
FIX: In each row: val state = remember(msg.id) { SwipeToDismissBoxState(Settled) { it * 0.4f } }. Use remember, not the saveable variant, so that an undone row gets a fresh state. In onDismiss: queue the action, then for non-removing actions call scope.launch { state.reset() }. Removing actions (Archive, Delete) need no reset, because the row leaves the list.
VERIFY: Confirmed in material3-android-1.5.0-beta01 sources (SwipeToDismissBox.kt). rememberSwipeToDismissBoxState uses rememberSaveable(saver=...). anchoredDraggable is enabled only when settledValue == Settled. LaunchedEffect(state.settledValue, onDismiss) calls onDismiss whenever the state is not Settled. The public constructor SwipeToDismissBoxState(initialValue, positionalThreshold) and suspend reset() exist, and the default threshold is 56.dp. The fix is incomplete: the LaunchedEffect is also keyed on the onDismiss lambda. A toggle action (Read/Unread, Star) changes the message row, which recomposes and gives a new lambda if it captures msg. While the reset animation is still running, the effect restarts and calls onDismiss again, so the toggle flips back.
BETTER FIX: val state = remember(msg.id) { SwipeToDismissBoxState(Settled) { it * 0.4f } }. The onDismiss lambda must capture only msg.id, so that its identity stays stable. For toggle actions: scope.launch { state.reset(); apply(action, id) }, that is, reset before the DB change. Removing actions (Archive, Delete) apply at once; the row leaves the list, and Undo gets a fresh remembered state.

## AF5 [major] [valid] §6 DeviceCredentials / 13 Setup
PROBLEM: The device-account path is incomplete for API 26+. (1) An app can see another authenticator's Google accounts only if the user picks one in the system chooser. getAccountsByType('com.google') returns nothing, and GET_ACCOUNTS does not help. The design has no account picker. (2) AccountManager gives no token expiry and can return a cached token that is almost 1 h old. Gmail closes an OAuth IMAP session when the token expires, so 'expiresAt about 55 min' is not known for this path. (3) Do not wrap the foreign KEY_INTENT in Plico's own notification PendingIntent; a direct Activity re-request is simpler. (4) Not verified: whether GMS issues a mail.google.com token to an unregistered, sideloaded signing key. FairEmail limits Gmail OAuth to its official builds.
FIX: Setup: launch newChooseAccountIntent(null, null, arrayOf("com.google"), null, null, null, null). Store KEY_ACCOUNT_NAME. Get the first token with getAuthToken(account, "oauth2:https://mail.google.com/", null, activity, cb, null), so that GMS shows its consent screen in the app. Background: use the notifyAuthFailure=false overload. On KEY_INTENT, post 'Sign-in needed'; its tap opens Plico's account screen, which repeats the Activity overload. Record the token acquisition time in memory. If it is unknown or older than 45 min, call invalidateAuthToken before you connect. Then expiresAt = acquired + 55 min. Before you write code, test the path once with the user's Cloud project, with an Android client registered for Plico's package name and signing SHA-1.
VERIFY: (1) Since API 26, apps see another authenticator's accounts only through user-granted visibility. FairEmail's FragmentGmail calls newChooseAccountIntent(..., new String[]{TYPE_GOOGLE}, ...) before getAccountsByType. Section 6 and section 13 have no picker, so the device path cannot get an Account. (2) FairEmail's GmailState stores 'acquired', uses TOKEN_LIFETIME = 1 h, and calls invalidateAuthToken near expiry. AccountManager returns no expiry, so expiresAt is unknown for a cached token. gmail G8 says the session ends with the token. (3) Wrapping KEY_INTENT is not broken, but the Activity overload of getAuthToken is simpler. (4) The FairEmail FAQ says Google approved OAuth 'for one app signature only'. This supports the concern that GMS will not issue tokens to an unregistered package and SHA-1. The design shows the card whenever a com.google authenticator exists.
BETTER FIX: Same as proposed. Also add to the setup text for 'Google account on this phone' that it needs the same Android-type OAuth client (Plico's package name and signing SHA-1) that browser OAuth uses. If GMS returns an error, point the user to the app-password method.

## AF6 [minor] [valid] §9 Notifications (tap and actions)
PROBLEM: The design gives each message its own tap and action PendingIntents, but it does not say how they are kept distinct. Intents that differ only in extras give the same PendingIntent. Without FLAG_UPDATE_CURRENT every notification opens the first message; with it, every notification opens the last one. The same applies to Archive, Delete and Mark read. Also, with the standard launch mode, each tap puts a second MainActivity on top of the existing task.
FIX: For each message intent, call Intent.setIdentifier("msg:$id") (tap) and set an action plus the identifier for each button. Use FLAG_IMMUTABLE. Declare MainActivity android:launchMode="singleTop" and handle the new intent with addOnNewIntentListener, which pushes Route.Message(id) on the existing back stack.
VERIFY: Section 9 specifies per-message tap and action PendingIntents but nothing that keeps them distinct. Per the PendingIntent reference, intents that differ only in extras give the same PendingIntent (Intent.filterEquals ignores extras; setIdentifier exists since API 29). With the standard launch mode, a notification intent that does not match the task's root intent creates a second MainActivity on top. The fix is minimal and correct.

## AF7 [minor] [valid] §9 Notifications (summary)
PROBLEM: The design has 'GROUP_ALERT_SUMMARY ... setOnlyAlertOnce on updates'. With GROUP_ALERT_SUMMARY only the summary alerts. If the summary update carries setOnlyAlertOnce(true), new mail that comes while older mail is still in the shade does not sound or vibrate. The user then misses the alerts for later mail.
FIX: Repost the summary with setOnlyAlertOnce(false) when the update adds at least one new message that should notify. Use setOnlyAlertOnce(true) only for updates that remove messages or mark them seen. Cancel the summary when it has no children left.
VERIFY: Section 9 says 'GROUP_ALERT_SUMMARY ... setOnlyAlertOnce on updates'. With GROUP_ALERT_SUMMARY only the summary alerts. setOnlyAlertOnce suppresses sound and vibration while the notification is already showing. So a second message that arrives while the first is in the shade does not alert, which goes against priority 1. The research text has the same ambiguity. The fix (alert-once only for updates that remove or mark messages seen) is right. The Android 15 cooldown already softens bursts.

## AF8 [minor] [valid] §12 Device privacy (tapjacking)
PROBLEM: The design asks for 'filterTouchesWhenObscured on Send, Delete and Show remote content'. Compose has no per-composable equivalent. The View attribute exists only on the host ComposeView, where it blocks every touch in the app, and users who run screen-dimmer overlays then cannot use the app.
FIX: Add one small modifier for the three buttons: Modifier.pointerInteropFilter { it.actionMasked == ACTION_DOWN && (it.flags and MotionEvent.FLAG_WINDOW_IS_OBSCURED) != 0 }, which consumes obscured gestures. Do not set it on the root view, and do not check FLAG_WINDOW_IS_PARTIALLY_OBSCURED (false positives from system UI).
VERIFY: compose-ui 1.12.1 sources have no filterTouchesWhenObscured API. The only text match for 'obscured' is an unrelated KDoc. The View attribute exists only on the host ComposeView, where it would block the whole UI for users of dimmer overlays. In PointerInteropFilter.android.kt, DOWN events go to onTouchEvent in the Initial pass and are consumed when the handler returns true. A modifier on the button (outer to the Surface's clickable) therefore blocks the press. The fix is small and correct.

## AF9 [minor] [partly] §4.1 MailSocket / 8.3 TCP_USER_TIMEOUT / refresh timeout
PROBLEM: (1) The public path to the fd is ParcelFileDescriptor.fromSocket(socket); the design does not name it. (2) SSLSocketFactory.createSocket(host, port) has no connect timeout, so connectTimeoutMs needs another construction. With createSocket() + connect(addr) on an unconnected socket, the peer host can be unknown, and Conscrypt then skips CT and SNI. (3) The design has 'Refresh: wait for the tagged OK (20 s)'. Setting readTimeoutMs (SO_TIMEOUT) while the IDLE reader thread is already blocked in read with timeout 0 has no effect on that read: Java and Conscrypt read the timeout when the read starts.
FIX: MailSocket.open: val raw = Socket(); raw.connect(InetSocketAddress(host, port), connectTimeoutMs); hooks.onConnected(raw) [app: ParcelFileDescriptor.fromSocket(raw).use { Os.setsockoptInt(it.fileDescriptor, IPPROTO_TCP, TCP_USER_TIMEOUT, 30_000) }]; val s = factory.createSocket(raw, host, port, true) as SSLSocket. Then set the protocols, SSLParameters (endpointIdentificationAlgorithm = "HTTPS", serverNames = SNIHostName(host)), startHandshake(), and hooks.verifyHostname. For the IDLE refresh, put the 20 s timeout on the waiting side (withTimeout around the idle() return, under the wake lock), then call socket.close(). Do not use SO_TIMEOUT for that read.
VERIFY: Real: SSLSocketFactory.createSocket(host, port) connects with no timeout, so connectTimeoutMs needs another construction. Wrong: the claim that createSocket() + connect() loses the host for SNI and CT. Conscrypt AbstractConscryptSocket.connect(SocketAddress, int) stores peerHostname from InetSocketAddress.getHostString() when it is unset. The other points are implementation notes, not design defects. ParcelFileDescriptor.fromSocket works on Conscrypt sockets (getFileDescriptor$ is implemented). Section 8.3 says 'wait for the tagged OK (20 s)' and does not say to use SO_TIMEOUT. TCP_USER_TIMEOUT already ends a blocked read on a dead path.
BETTER FIX: MailSocket.open: val s = factory.createSocket() as SSLSocket; s.connect(InetSocketAddress(host, port), connectTimeoutMs), which keeps the hostname for SNI and CT. Then set protocols and endpointIdentificationAlgorithm, call startHandshake(), and call hooks.verifyHostname. In onConnected, name ParcelFileDescriptor.fromSocket(socket).use { Os.setsockoptInt(it.fileDescriptor, IPPROTO_TCP, TCP_USER_TIMEOUT, 30_000) }. In section 8.3, say that the 20 s refresh wait is a withTimeout on the waiting coroutine (under the wake lock) that ends with socket.close().

## AF10 [minor] [valid] §12 Network security config (CT claim)
PROBLEM: 'Certificate Transparency on' is not true on every supported device. Android 15 (API 35) has no CT. Android 16 has CT off by default unless the app opts in. Only Android 17 turns CT on by default for apps that target 37. The cleartext and system-only trust-anchor lines are already the defaults at targetSdk 37.
FIX: Keep the NSC file with only <base-config><certificateTransparency enabled="true"/></base-config>, which Android 16 devices need, and drop the redundant lines. In About, say: 'Certificate Transparency on Android 16 and later'. CT coverage of raw sockets depends on AF9: the SSLSocket must know the hostname.
VERIFY: Confirmed on developer.android.com/privacy-and-security/security-config: <certificateTransparency enabled=...> in base-config or domain-config. API 37+: enabled by default. API 36: disabled by default, opt-in. API 35 and lower: not available. The default base-config for API 28+ is cleartextTrafficPermitted=false with system certificates only. With minSdk 35, 'Certificate Transparency on' is false on Android 15 and needs the explicit element on Android 16. Dropping the redundant lines is optional. The required parts are the CT element and correct About text.

## AF11 [minor] [partly] §2 Dependencies / 8 / 12 (manifest)
PROBLEM: The design has no manifest permission list. USE_BIOMETRIC is missing, so BiometricPrompt throws SecurityException. ACCESS_NETWORK_STATE is missing, so registerDefaultNetworkCallback throws. FOREGROUND_SERVICE_SPECIAL_USE is missing, so startForeground with the type throws. FileProvider is androidx.core, not the platform, and it is not in the dependency list (it arrives only through activity).

Declare: INTERNET, ACCESS_NETWORK_STATE, POST_NOTIFICATIONS, FOREGROUND_SERVICE, FOREGROUND_SERVICE_SPECIAL_USE, RECEIVE_BOOT_COMPLETED, WAKE_LOCK, REQUEST_IGNORE_BATTERY_OPTIMIZATIONS, SCHEDULE_EXACT_ALARM, USE_BIOMETRIC. Do not declare: GET_ACCOUNTS, USE_EXACT_ALARM, ACCESS_LOCAL_NETWORK, READ_MEDIA_*. Components: PushService, StartReceiver, AlarmReceiver, ActionReceiver, OAuthRedirectActivity, and a FileProvider with <cache-path name="att" path="att/"/>. Note androidx.core in the dependency list as 'already transitive; used for FileProvider'. When you build BiometricPrompt with DEVICE_CREDENTIAL, never call setNegativeButton (it throws).
VERIFY: The facts are correct. Platform BiometricPrompt needs USE_BIOMETRIC. registerDefaultNetworkCallback needs ACCESS_NETWORK_STATE. A specialUse FGS needs FOREGROUND_SERVICE_SPECIAL_USE. Building with DEVICE_CREDENTIAL plus a negative button throws. FileProvider is in androidx.core, which is transitive through activity. The impact is overstated: each missing permission fails loudly on first run, and docs/research/android-push.md Implications already gives the full permission and component list. For a privacy app, a short, explicit permission list in DESIGN is still useful.
BETTER FIX: Add a short 'Manifest' paragraph to DESIGN with the permission and component list from android-push Implications, plus USE_BIOMETRIC, the AlarmReceiver (AF2) and the FileProvider <cache-path name="att" path="att/"/>. Add one line to section 2: 'FileProvider from androidx.core (already transitive)'.

## AF12 [minor] [valid] §2 Dependencies / 13 Navigation3
PROBLEM: rememberNavBackStack in navigation3 1.2.0 needs @Serializable NavKey routes. That needs the kotlinx-serialization compiler plugin, and the plugin is not in the dependency list or in gradle/libs.versions.toml. Without it, the back stack cannot be saved, and an implementer may add a hand-written Saver.
FIX: Add org.jetbrains.kotlin.plugin.serialization 2.4.21 (compiler plugin only; no new runtime) to the catalog and to :app. Declare '@Serializable sealed interface Route : NavKey', with the View variants also @Serializable. Write this in §2 with the reason 'saves the back stack across process death'.
VERIFY: Confirmed in navigation3-runtime-android 1.2.0 sources. RememberNavBackStack.android.kt says 'Each element placed in the NavBackStack must be @Serializable', and it uses rememberSerializable. NavKey.kt requires @Serializable. Plico's libs.versions.toml and app/build.gradle.kts have no serialization plugin. MegaGlass-Android applies org.jetbrains.kotlin.plugin.serialization, and section 2 says 'same as MegaGlass-Android'. The compiler plugin adds no new runtime, because kotlinx-serialization-core is already transitive.

## AF13 [minor] [valid] §15 Build (:mail pure JVM)
PROBLEM: The :mail module compiles against the full JDK 21 class library. Lint for :app does not analyze plain JVM modules. A call such as Thread.ofVirtual, a Java 21 API that Android 35 lacks, or java.net.http compiles and then fails at run time on the device with NoSuchMethodError.
FIX: In :mail add plugins { id("com.android.lint") } (it is part of AGP 9.4.1). In :app use lint { checkDependencies = true; abortOnError = true }. Run :app:lintRelease in the build check, so that NewApi tests :mail against minSdk 35.
VERIFY: mail/build.gradle.kts applies only kotlin-jvm with jvmToolchain(21). It compiles against the JDK 21 class library, and app lint does not analyze it without com.android.lint plus checkDependencies. Kotlin member resolution can pick JDK 21 members (for example StringBuilder.repeat or Math.clamp) that may be missing on API 35, and nothing catches this at build time. The fix adds no library and only uses AGP's own lint plugin.

## AF14 [minor] [valid] §10 Image attachments (photo picker)
PROBLEM: 'Images picked as attachments are re-encoded (JPEG)' also hits PNG screenshots and GIF/animated WebP. JPEG has no alpha, so transparent pixels become black. ImageDecoder.decodeBitmap decodes only the first frame, so animations are lost. Text in screenshots also gets JPEG artifacts.
FIX: Re-encode only camera formats that carry EXIF: image/jpeg, image/heic, image/heif. Use ImageDecoder, which applies EXIF orientation, then JPEG q90 at 2560 px. Send PNG, GIF and WebP unchanged, or re-encode PNG as PNG, which keeps alpha and drops metadata chunks.
VERIFY: Section 10 re-encodes every picked image as JPEG. That drops PNG alpha (transparent areas become black), turns GIF and animated WebP into one frame, and adds artifacts to screenshot text. privacy-security G28 says the photo picker already redacts location, and its MUST item targets EXIF carriers (JPEG and HEIC). Limiting the re-encode to image/jpeg, heic and heif, and sending other formats unchanged, keeps the privacy goal with no usability loss.

## AF15 [minor] [partly] §8.2 Power grants
PROBLEM: Two states that stop push without any sign are missing from 'Push & battery'. (1) App hibernation ('Pause app activity if unused') force-stops an app that has gone unused for about 90 days. Alarms do not count as use. (2) The user can set Battery usage to 'Restricted', and then foreground services cannot start from the background and alarms do not run. isIgnoringBatteryOptimizations shows only 'not granted'.
FIX: In the status screen, add two rows that use platform APIs only. Hibernation: packageManager.isAutoRevokeWhitelisted, fix button Intent(Intent.ACTION_AUTO_REVOKE_PERMISSIONS, package URI). Restricted: activityManager.isBackgroundRestricted, fix button ACTION_APPLICATION_DETAILS_SETTINGS. Show 'Push may be late' or 'Push off' from them as well.
VERIFY: Background restriction is real. ActivityManager.isBackgroundRestricted docs say that alarms do not run and an FGS cannot start. AOSP Settings RequestIgnoreBatteryOptimizations only calls addToWhitelist and does not clear the restriction. So the design's status shows only 'not granted' / 'Push may be late' when push is actually off. Hibernation is low value for a mail client: per the app-hibernation doc, a resumed activity or a notification tap counts as use, so it needs months without opening the app and without tapping a notification. The doc also calls isAutoRevokeWhitelisted a legacy API it does not recommend.

## AF16 [minor] [valid] §6 Browser OAuth
PROBLEM: The PKCE code_verifier and state stay in memory in 'the waiting flow' while the user is in the browser. If Android kills Plico's process during consent (a common low-memory case), OAuthRedirectActivity gets the code in a new process that has no verifier and no state. The sign-in then fails.
FIX: Before the ACTION_VIEW, save {state, code_verifier, email, started_at} in the setup screen's SavedStateHandle (or in app-private SharedPreferences, deleted after use or after 10 min). OAuthRedirectActivity compares state against the saved value. Not a secret at rest: the verifier is single-use and expires.
VERIFY: Section 6 keeps state and the verifier only in 'the waiting flow'. Setup happens before the FGS exists, so Plico is a cached background process while the browser is in front and can be killed. OAuthRedirectActivity then has no verifier or state, and sign-in fails. Persisting them is the standard fix (AppAuth does it). Prefs are simpler than SavedStateHandle here: OAuthRedirectActivity is a separate activity in a possibly new process and cannot reach the setup ViewModel's SavedStateHandle.
BETTER FIX: Before ACTION_VIEW, write {state, verifier, email, started_at} to app-private SharedPreferences. In OAuthRedirectActivity, read and delete the entry, check state and age (10 min or less), then start MainActivity (singleTop) with the code so that setup continues and does the token exchange.

## AF17 [minor] [valid] §8.3 Wake lock (Power)
PROBLEM: In the design, 'every acquire has a 60 s timeout' and 'sync holds it'. The first sync, a backfill step of 500 headers, or a 25-body batch on a slow network can take longer than 60 s. The lock then expires while the screen is off. The CPU suspends between incoming packets, and the uptime-based read timeouts stop. The sync then crawls, or ends only at the next alarm.
FIX: Use Power.hold { } for each step: re-acquire 60 s at each IMAP response or batch, as afterRead already does for IDLE, and release in finally. Put a hard cap of about 10 min on each sync job, so that a stuck server cannot keep the CPU awake.
VERIFY: Section 8.3 says every acquire has a 60 s timeout and that sync 'holds it'. Background syncs after a long offline period (many 25-body batches) or backfill steps on Wi-Fi with the screen off can take longer. After the lock expires, the CPU suspends, and uptime-based read timeouts freeze (android-push G18). The sync then stalls until the next wake. The engine recovers at the next alarm, so the impact is moderate. The fix (re-acquire per response or batch, plus a hard cap) is small and matches the afterRead pattern already used for IDLE.
