# privacy-security
I found 19 privacy and security problems in docs/DESIGN.md: 1 critical, 9 major, 9 minor. I changed no files.

Critical:
- A sender can put path parts (`../`) in an attachment filename. When the user opens or saves the attachment, the app could overwrite its own private files.

Major:
- Share intents and `mailto:` links can make Plico attach its own private files.
- Decoded values that contain line breaks (CR/LF) can add headers to outgoing mail and hidden recipients to SMTP commands.
- The "always show remote content from this sender" rule (`auth != 2`) is easy to spoof.
- Links that the cleaner unwraps skip the scheme allowlist.
- No Public Suffix List exists, so the bold domain in the link sheet and the sender checks will often be wrong.
- If the WebView renderer crashes, the whole process stops, push included.
- Search index (FTS) rows are never deleted, so deleted mail stays on disk.
- `app/build.gradle.kts` already puts the user's own Google client ID into release builds. Every GitHub user who signs in sees the user's developer email, and each one uses part of the project's 100-user limit.
- The "Google account on this phone" method needs more Cloud setup than the design says. On phones without Google services, another app can claim the `com.google` account type.

Minor: lock-screen notification actions, system "Open link" chips that skip the link sheet, RemoteFetcher limits, small WebView/CSP gaps, attachment MIME handling, extras on the exported MainActivity, OAuth robustness, image metadata, logging, and password-manager autofill.

These parts of the design are correct:
- PKCE S256 plus the `state` check stop the custom-scheme redirect hijack. A stolen code has no use without the verifier.
- `shouldInterceptRequest` still runs when `blockNetworkLoads` is on. The block only adds `LOAD_ONLY_FROM_CACHE` (Chromium net_helpers.cc), so the cid and remote-content paths work.
- Android's AccountManagerService already rejects grant flags and `content:` schemes in a `KEY_INTENT`.
- Android's SQLite build has `SQLITE_SECURE_DELETE` on.
- `res/xml/data_extraction_rules.xml` already excludes every domain in all three sections.

Two points come from developer reports, not official docs. Loopback may not be covered by Android 17 local network protection. The device AccountManager path with an unverified restricted scope is untested.

Sources: [Content resolvers](https://developer.android.com/privacy-and-security/risks/content-resolver), [Untrusted ContentProvider filename](https://developer.android.com/privacy-and-security/risks/untrustworthy-contentprovider-provided-filename), [Dirty Stream](https://www.microsoft.com/en-us/security/blog/2024/05/01/dirty-stream-attack-discovering-and-mitigating-a-common-vulnerability-pattern-in-android-apps/), [Managing WebView](https://developer.android.com/develop/ui/views/layout/webapps/managing-webview), [Local network permission](https://developer.android.com/privacy-and-security/local-network-permission), [Notification.Action.Builder](https://developer.android.com/reference/android/app/Notification.Action.Builder), [FairEmail FAQ](https://m66b.github.io/FairEmail/), plus AOSP RegisteredServicesCache.java, AccountManagerService.java and external/sqlite/dist/Android.bp, and Chromium aw_proxying_url_loader_factory.cc and net_helpers.cc.

## PS1 [critical] [valid] §11.5 Attachments; 5 draft.attachments; 4.5 MimePart.fileName
PROBLEM: Attachment files go to cacheDir/att/<messageId>/ and shared files go to filesDir/outbox/<id>/, and both use a filename that an attacker controls. MimePart.fileName decodes RFC 2231 and 2047, so a sender can send '/', '..', NUL, CR/LF or U+202E. One example is filename*=utf-8''..%2F..%2F..%2Fshared_prefs%2F<prefs>.xml. When the user taps Open or Save, the app writes attacker bytes over its own Prefs (remote-content default, link confirmation, app lock) or over the DB. The share-intent path is open to the same attack: DISPLAY_NAME from another app goes into the outbox path.
FIX: Use one helper for att, outbox and save. Path = <base>/<ownerId>/<itemId>/<safeName>. To make safeName, replace '/', '\', ':', NUL, C0/C1 controls and bidi controls (U+202A-202E, U+2066-2069) with '_'. Remove leading dots, limit the length to 100 chars, and use 'attachment' when the result is empty. Then require file.canonicalPath to start with base.canonicalPath + '/'. Keep the original name only in the DB. Add unit tests with '../', '%2F', NUL and RTLO.
VERIFY: §11.5 and §5 give no rule for file names on disk. A raw filename="../../shared_prefs/x.xml" works even without RFC 2231 decoding: cacheDir/att/<id>/../../shared_prefs resolves into the app data dir. The Android page 'untrustworthy-contentprovider-provided-filename' names this exact risk (prefs overwrite) and prefers internally generated names. Outbox DISPLAY_NAME is the Dirty Stream pattern. The fix (id directory + safe name + canonical-path check, real name only in DB) is correct and small.

## PS2 [major] [partly] §13 Compose (ACTION_SEND/SEND_MULTIPLE/SENDTO, pickers); 11.3 mailto
PROBLEM: Plico copies a received URI with its own permissions. A malicious app can send EXTRA_STREAM=file:///data/user/0/app.plico/databases/<db> or a content:// URI of Plico's own FileProvider (cached attachments of other mails) with To and Subject filled in. The user then emails private Plico data to the attacker. mailto: URIs from mails or apps can carry attach=/attachment= parameters for the same purpose, and a bcc= the user does not see. A malformed EXTRA_STREAM (wrong Parcelable type) causes a crash, and that crash stops push because push runs in the same process. A wrong share also gets uploaded to the server Drafts on 'leave' (append_draft).
FIX: Add one IncomingUri.check() for EXTRA_STREAM, ClipData items, picker results and mailto. Accept only content:// URIs whose authority is not Plico's (packageManager.resolveContentProvider(authority,0)?.packageName != packageName). Reject file:// and all other schemes. Read extras with typed getters (getParcelableArrayListExtra(EXTRA_STREAM, Uri::class.java)) inside try/catch. Copy at once, with a cap at the server SIZE. In the mailto parser, accept only to, cc, bcc, subject and body (RFC 6068) and ignore all other parameters. Expand Cc/Bcc when an outside source fills them. A draft from a share intent queues no append_draft until the user edits it.
VERIFY: Core is real. ContentResolver.openInputStream accepts file:// URIs into Plico's own data dir, and a sender can turn off StrictMode in its own process. The Android 'content-resolver' risk page describes this mail-app case and gives belongsToCurrentApplication(). Overstated parts: the design has no mailto attach= support, so the 'Mailto: Me Your Secrets' attack does not apply. Typed getters on API 33+ with lazy bundles make the parcel-crash claim weak. append_draft only uploads to the user's own server. The special 'no append_draft for shared drafts' rule adds state with no security gain once the URI check exists.
BETTER FIX: One IncomingUri check for EXTRA_STREAM and ClipData (system photo and document pickers need no check). Accept only content:// URIs whose resolveContentProvider(authority,0).packageName is not Plico. Reject file:// and every other scheme. Use typed getters inside try/catch and copy at once, with a size cap. In the mailto parser, accept only to/cc/bcc/subject/body and show the Cc/Bcc rows when they are prefilled. Normal draft rules stay unchanged.

## PS3 [major] [valid] §10 MessageBuilder; 4.7 SmtpClient; 4.6 EncodedWords
PROBLEM: The design gives no rule against CR/LF in header values or SMTP addresses. EncodedWords.decode can return CR/LF. Subject gets RFC 2047 encoding only 'when non-ASCII', and CR/LF are ASCII, so 'Re: <decoded subject>' can add headers such as Reply-To: attacker or Content-Type to the user's reply or forward. Display names in reply-all, identity names, attachment filenames and References/In-Reply-To all come from attacker mail. mailto: percent-decoding gives %0D%0A. SmtpClient writes 'RCPT TO:<addr>' without validation, so an address like 'a@b>\r\nRCPT TO:<spy@evil' adds a silent recipient. (The IMAP side is safe because Command.string() uses literals.)
FIX: In MessageBuilder, pass every header value through one clean() function. It changes C0 controls and DEL to a space, then RFC 2047-encodes non-ASCII text. Quote display names that contain specials. Write the Content-Disposition filename as RFC 2231, or quoted with '"' and '\' escaped. For In-Reply-To/References, accept only tokens that match <[^\s<>]+@[^\s<>]+> and keep the first plus the last 10. Before SmtpClient.send writes a byte, it rejects any address that is not a strict addr-spec (no CR, LF, '<', '>', space or controls). Add tests with CRLF in the subject, name, address, filename and References.
VERIFY: §10 encodes Subject only 'when non-ASCII'. CR and LF are ASCII, and Q/B encoded words decode =0D=0A, so 'Re: <decoded subject>' can add headers, or even an empty line plus attacker body text, to the user's reply-all. §4.7 has no rule to validate addresses, and percent-decoded mailto: input can carry CRLF into RCPT TO. The §15 MessageBuilder tests do not cover injection. One clean() for header values plus a strict addr-spec check before SMTP is the simplest correct fix.

## PS4 [major] [partly] §11.4 SenderCheck; 13 Message (Unsubscribe)
PROBLEM: 'Always show remote content from this sender' applies when auth != 2, so it also applies when auth = 0 (unknown). Riseup always gives 0. Gmail gives 0 for a domain with no DMARC record and spf=softfail/dkim=none, because the fail rule needs spf=fail AND dkim=fail. A spoofed From of a trusted newsletter therefore loads remote images and sends the user's IP and open time to the spoofer. The rule 'topmost A-R whose authserv-id is mx.google.com' skips a non-Google header at the top. Mail that the Gmail MX did not stamp (POP fetch until Jan 2027, APPENDed or imported mail) can carry a forged lower 'mx.google.com; dmarc=pass'. One-click unsubscribe POSTs to a URL from a possibly spoofed or spam mail, and the POST tells the spammer that the address is live.
FIX: Parse only the first Authentication-Results header, and use it only if its authserv-id is mx.google.com. Set auth=1 only for dmarc=pass. Apply per-sender trust and the one-click POST only when auth == 1 and the message is not in Junk. Otherwise offer 'Show once' and the link sheet. For Riseup, read its authserv-id from one raw header in the first live test (already an open question in the research). Until then, Riseup trust uses From only, and the toggle says 'can be faked'.
VERIFY: The design (auth != 2) differs from the research Implication ('only when aligned dmarc=pass'). RFC 8058 §3.2 says receivers SHOULD NOT offer one-click without the DKIM signature, so tying the POST to auth==1 is right. Overstated part: for Gmail the hole is mostly domains with no DMARC record. A spoof of a DMARC-protected newsletter (all bulk senders since 2024) gives dmarc=fail and auth=2, which is already blocked. The forged lower mx.google.com header needs POP fetch, which takes no new users and ends Jan 2027. For Riseup the proposed fix keeps From-only trust, so that hole stays open. Only a label is added.
BETTER FIX: Gmail: read only the first Authentication-Results header and use it only if its authserv-id is mx.google.com. Set auth=1 only for dmarc=pass. Honour per-sender trust and one-click POST only when auth==1 and the message is not in Junk. Riseup: say in the design that per-sender trust is From-only and can be faked until the authserv-id is confirmed. One-click POST is not offered on Riseup (use the link sheet).

## PS5 [major] [valid] §11.3 LinkCleaner
PROBLEM: The sanitizer allows only http/https/mailto in href. LinkCleaner then unwraps google.com/url q=, safelinks url=, urldefense and Mandrill base64 into a new string that the attacker chose: intent:, file:, content://app.plico..., market:, or the custom scheme of any app. ACTION_VIEW sends this string out. The WebView gives a canonical (GURL) URL, but the unwrapped string is raw, so android.net.Uri and the browser can read '\', '@', spaces and controls differently. The host shown in bold can then differ from the host the browser opens.
FIX: After the unwrap, parse the URL again and allow only http/https (mailto goes to the composer). Otherwise show the URL as text with Copy only. Reject or warn on userinfo, '\', whitespace and controls. Rebuild the URL from the parsed parts, then show and open that exact string. Run the domain, IP and IDN warnings on the final host. Launch with Intent(ACTION_VIEW, uri).addCategory(CATEGORY_BROWSABLE), with no component and no selector. Links in plain-text bodies must use the same sheet (no autoLink).
VERIFY: §11.1 checks schemes before the §11.3 unwrap. The unwrapped q=/url= value is a raw attacker string, and Open does ACTION_VIEW on it. A file: result gives FileUriExposedException, which crashes the push process. Custom app schemes skip the browser. android.net.Uri.getHost() takes the text after the last '@' ('https://evil.com\@good.com' gives good.com), but Chrome treats '\' as '/' and opens evil.com, so the bold domain can lie. Some examples are weak: content://app.plico without a grant is harmless, and no app handles intent:. The fix is still correct and small: re-parse, http/https only, reject userinfo, '\' and controls, rebuild, CATEGORY_BROWSABLE.

## PS6 [major] [valid] §11.3 link sheet; 11.4 SenderCheck
PROBLEM: 'Registrable domain in bold', 'display name domain differs' and 'Reply-To domain differs from From' all need the Public Suffix List. Android has no public PSL API, and section 2 allows no library. With a naive last-two-labels rule, phishing hosted on shared platforms shows a trusted name in bold (github.io, web.app, pages.dev), UK hosts show 'co.uk', and normal subdomain senders (news.example.com with Reply-To example.com) get false warnings. False warnings make users ignore real ones.
FIX: Bundle public_suffix_list.dat (ICANN and PRIVATE sections, about 230 KB, MPL-2.0) as an asset. Write a matcher of about 40 lines (normal, wildcard and exception rules) and refresh the file at each release. Use it in LinkCleaner (the bold part), SenderCheck (display name, Reply-To vs From) and tracker-host matching.
VERIFY: Android has no public PSL API, and §2 allows no library, so the design's 'registrable domain in bold' and the domain-mismatch checks have no defined source. A last-two-labels rule gives 'co.uk' and 'github.io'. One example is wrong: news.example.com against example.com gives a false warning only when you compare full hosts, not under a last-two rule. The core still holds. A bundled public_suffix_list.dat plus a small matcher is the standard approach and adds no dependency.

## PS7 [major] [valid] §11.2 MessageWebView; 3 single process
PROBLEM: The design does not handle renderer death. Android documents that if the renderer goes away and the app does not handle it, the app crashes. The UI and PushService share one process (section 3). So one hostile HTML mail (renderer OOM from a huge table or data: image, or a renderer bug) stops push, and START_STICKY restarts it only later with crash backoff. If the UI restores Message(id), the crash repeats.
FIX: Override onRenderProcessGone. Remove and destroy the WebView, show the plain-text part (or 'Message could not be shown'), and return true for both didCrash and OOM. Remember the message id for this process session and show it as plain text the next time it opens.
VERIFY: Android 'Termination Handling API' docs: if onRenderProcessGone returns false or is not handled, the app process is killed. §3 puts PushService in the same process, so a renderer crash, or a renderer killed by the system for memory (didCrash=false), stops push. The design does not say to handle it. Destroying the WebView, showing the plain text and returning true is the minimal fix. The per-session 'show as text next time' memory is optional.

## PS8 [major] [valid] §5 Data (message_fts); 6 account removal
PROBLEM: message_fts is a normal FTS4 table that keeps its own copy of the subject, people and body. Virtual tables do not take part in foreign keys, so ON DELETE CASCADE never removes these rows. Expunge, delete forever, a UIDVALIDITY reset and account removal all leave the full text on disk. INTEGER PRIMARY KEY without AUTOINCREMENT reuses max(id)+1 after the newest row is deleted (common, for example spam that is expunged soon after it arrives). The FTS insert for the new message then fails on an existing rowid, or text from the old mail matches the new message. Account removal also leaves outbox/att files and the mail_<id> channel.
FIX: Add CREATE TRIGGER message_ad AFTER DELETE ON message BEGIN DELETE FROM message_fts WHERE rowid=old.id; END; and add a unit test that shows it fires for cascade deletes. Insert FTS rows with INSERT OR REPLACE. On account removal, delete the account's outbox and att dirs, call deleteNotificationChannel, then run INSERT INTO message_fts(message_fts) VALUES('optimize') and PRAGMA wal_checkpoint(TRUNCATE).
VERIFY: Tested with sqlite3. Rows deleted by ON DELETE CASCADE leave message_fts rows, including the text. The next INSERT gets the reused id max+1, and the FTS insert then fails with 'constraint failed'. An AFTER DELETE trigger on message fires for cascades (the FTS count was 0 after an account cascade). INSERT OR REPLACE and 'optimize' both work on FTS4. The design's account removal also does not delete outbox/att dirs or the mail_<id> channel.

## PS9 [major] [partly] §6 Browser OAuth (client ID preset); app/build.gradle.kts
PROBLEM: app/build.gradle.kts puts GOOGLE_CLIENT_ID from local.properties into defaultConfig, so the GitHub release APK contains the user's own client ID. Google's unverified-app screen shows 'Until the developer (<email>) verifies this app ...'. Every stranger who signs in with that APK therefore sees the user's developer email and the project name. Each of them also uses part of the project's 100-user lifetime limit, which nobody can reset.
FIX: Move the buildConfigField to the debug build type and set it to "" in release, or make assembleRelease fail when plico.googleClientId is set. Release builds always ask for the user's own client ID (the bring-your-own model). In the setup note, tell the user to put a non-personal support email on the consent screen.
VERIFY: Real: buildConfigField is in defaultConfig, and the unverified-app screen reads 'Until the developer (xxx@gmail.com) verifies this app' (reported in the Apps Script community). The 100-user lifetime cap is gmail G6. (local.properties has no preset now, so the risk is latent.) The fix is incomplete. An Android OAuth client is bound to package name + signing SHA-1, and Google requires that pair to be unique across all Cloud projects (Firebase help 6401008). So for every copy of the APK signed with the user's key, the project that registered app.plico + that SHA-1 also serves the AccountManager method and browser OAuth. Removing the preset ID does not stop strangers from using the user's project. Strangers also cannot 'bring their own' Android client for the same APK.
BETTER FIX: Make the preset debug-only (or fail assembleRelease when it is set). In the design, state that the Android OAuth client is tied to package + signing key. Sign the user's personal build with a key, or an applicationId, that is not used for the public GitHub APK. Say that users of the public APK get app password only (or must build and sign their own copy). Put a non-personal support email on the consent screen.

## PS10 [major] [partly] §6 DeviceCredentials (AccountManager)
PROBLEM: (1) Wrong fact: the method is offered whenever com.google exists, but Google's authenticator gives tokens only to apps whose package and signing SHA-1 are registered as an Android OAuth client in some Cloud project. Without that, the result is UNREGISTERED_ON_API_CONSOLE. The method therefore needs the same Cloud setup as browser OAuth, and the unverified restricted scope through GMS is untested. (2) On API 26+, getAccountsByType does not show the account unless the user picks it in the system chooser, and the design gives no picker. (3) Squatting: RegisteredServicesCache gives an account type to the first non-system app that declares it, and a system app replaces it. On a de-Googled phone, any installed app can own com.google. Plico then offers 'Google account on this phone', and the squatter's KEY_INTENT (its own activity, which AMS allows) shows a fake Google login.
FIX: Offer the method only when the AuthenticatorDescription for com.google comes from a package with ApplicationInfo.FLAG_SYSTEM (GMS or system microG), and only after the user has created the Android client. Pick the account with AccountManager.newChooseAccountIntent(null, null, arrayOf("com.google"), null, null, null, null), which needs no GET_ACCOUNTS. Map UNREGISTERED_ON_API_CONSOLE to a clear setup message. On removal, call invalidateAuthToken and POST the current access token to /revoke.
VERIFY: (1) Correct: the FairEmail FAQ confirms that account selection gives UNREGISTERED_ON_API_CONSOLE unless the package + signature is registered. So the device method needs the same Android OAuth client setup, and §6 does not say this. (2) Correct: since API 26, Google accounts are hidden without newChooseAccountIntent, and §6/§13 give no picker. (3) The squatting risk is contrived, and the proposed FLAG_SYSTEM check is harmful. GrapheneOS sandboxed Google Play is a regular, non-system app that provides the com.google authenticator. A privacy-first user is likely to run it, and the check would hide the method there.
BETTER FIX: Document that the device method needs the Android OAuth client (package + release SHA-1) and map UNREGISTERED_ON_API_CONSOLE to a setup message. Pick the account with newChooseAccountIntent(null,null,arrayOf("com.google"),...). If an authenticator check is wanted, verify that the authenticator package is com.google.android.gms with Google's signing certificate (PackageManager.hasSigningCertificate, CERT_INPUT_SHA256), not FLAG_SYSTEM. On removal, invalidateAuthToken (revoke is optional; it removes the whole project grant).

## PS11 [minor] [valid] §9 Notifications
PROBLEM: (1) With the default lock-screen setting, private content and its actions show, so anyone who holds the phone can run Archive or Delete without unlocking. (2) The system adds contextual 'Open link' chips for URLs in the snippet. They open the browser directly, without the cleaning, IDN and domain checks of section 11.3. (3) The public version uses the account label, which defaults to ''. The likely fallback is the email address, which then shows on the lock screen. The same applies to 'Sign-in needed' alerts and to channel names.
FIX: Call setAuthenticationRequired(true) on Archive and Delete. Call setAllowSystemGeneratedContextualActions(false) on every mail notification. Public versions (children, group summary, alerts) never contain an address: 'N new messages', plus the label only when the user set one. The default label and channel name is 'Riseup' or 'Gmail', with a number when needed.
VERIFY: All three gaps are real and each fix is one line. With the default 'show all content' lock-screen setting, the private version and its broadcast actions run without unlock. Notification.Action.Builder.setAuthenticationRequired (API 31) exists for this. Notification.Builder lets system contextual actions through by default, and an 'Open link' chip skips the §11.3 link sheet. The default label '' gives no defined public text or channel name, so an implementation will likely fall back to the address on the lock screen.

## PS12 [minor] [partly] §11.2 RemoteFetcher; 13 Unsubscribe POST
PROBLEM: After the user taps Show, image URLs and the unsubscribe POST target are attacker-chosen. The design does not check local hosts (IP literals, .local, 127.0.0.1, LAN), does not re-check hosts at each redirect hop, does not check the response type, and has no limit per message (500 images x 5 MB) and no total deadline (a server can send 1 byte every 9 s and stay under the 10 s timeout). The sanitizer finds trackers in CSS with a regex, so escaped url() (u\72l) and image-set("...") get past its count. A bare 'User-Agent: Mozilla/5.0' is rare, so it marks Plico users in tracker logs.
FIX: Never declare ACCESS_LOCAL_NETWORK, and write that rule in the design. Reject IP-literal hosts, localhost, single-label names and .local/.lan/.home.arpa/.internal. Resolve the host first, and reject it if any address is loopback, any-local, link-local, site-local, fc00::/7 or 100.64/10. Run the same check at each redirect hop and for the unsubscribe POST. Accept only image/* responses (check the header and the magic bytes). Set a budget per message (for example 20 MB in total, 4 parallel fetches) and a 20 s deadline per request. Run the tracker-host list in the interceptor, which is the single choke point. Send the reduced Chrome-Android UA ('Mozilla/5.0 (Linux; Android 10; K) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/<WebView major>.0.0.0 Mobile Safari/537.36').
VERIFY: Some points are useful: §11.2 has no per-message budget (only 5 MB per resource), and moving the tracker-host block into the interceptor gives one choke point that CSS escapes cannot get past. The SSRF part is over-engineered. Requests are HTTPS-only with system CAs, so LAN targets rarely pass TLS, and the attacker never sees the response. On Android 17 with target 37, private-range traffic is blocked unless the app declares ACCESS_LOCAL_NETWORK (official doc). The proposed 'resolve first, then check the IPs' step is also not sound with HttpsURLConnection: it resolves the name again (DNS rebinding TOCTOU), and the step adds a lookup. Content-type and magic-byte checks give little, because the WebView only renders images. The UA change is optional; the Conscrypt TLS fingerprint differs from Chrome anyway.
BETTER FIX: Never declare ACCESS_LOCAL_NETWORK. At each redirect hop and for the unsubscribe POST, reject IP-literal hosts, localhost, single-label names and .local/.lan/.home.arpa/.internal with a string check only. Add a per-message budget (for example 20 MB, 4 parallel fetches) and a total deadline per request. Apply the tracker-host list in the interceptor.

## PS13 [minor] [partly] §11.1 CSP; 11.2 WebView
PROBLEM: (1) CSP img-src 'https:' blocks http: images in the renderer before shouldInterceptRequest runs, so the rule 'an http: URL is tried as https:' never applies, and http images stay blank after Show. (2) font-src data: lets mail load font files, which adds a font-parser attack surface for little gain. (3) The research asked for setAttributionRegistrationBehavior(DISABLED), but the design leaves it out. (4) ProxyController.setProxyOverride is async, and without removeImplicitRules() it bypasses localhost. (5) The cid interceptor 'loads parts on demand'. A sender can point <img> at the Content-ID of a 25 MB non-image part, or at a cid of another message, and force downloads.
FIX: The sanitizer rewrites http:// to https:// in img src and CSS url() (or add 'upgrade-insecure-requests' to the CSP). Remove 'font-src data:' so that default-src 'none' blocks fonts. Call WebSettingsCompat.setAttributionRegistrationBehavior(ATTRIBUTION_BEHAVIOR_DISABLED). Use removeImplicitRules() and wait for the override callback before the first load. The cid handler serves only image/* parts from the BODYSTRUCTURE of the message on screen, with the Content-Type taken from the magic bytes. It answers 403 for every other cid.
VERIFY: (1) Real: CSP is enforced in the renderer before shouldInterceptRequest runs, so img-src https: blocks http: images, and the 'try http as https' rule never runs. (5) Real: a cid can point at a large non-image part and force a download on open. (3) Real but small: research G2 listed the attribution setting. The safelist already strips attributionsrc and JS is off. (2) Weak: fonts are parsed in the sandboxed renderer (OTS-sanitized), and data: fonts in mail are rare. (4) Has almost no effect: blockNetworkLoads=true is always set, so the WebView makes no network loads, and the proxy's localhost bypass does not matter.
BETTER FIX: Add 'upgrade-insecure-requests' to the CSP (or rewrite http:// to https:// in the sanitizer). The cid handler serves only image/* parts from the BODYSTRUCTURE of the message on screen, with a size cap, and answers 403 for every other cid. Add the one-line setAttributionRegistrationBehavior(DISABLED). Drop the font-src and removeImplicitRules items.

## PS14 [minor] [partly] §11.5 Attachments
PROBLEM: The design does not say what happens when the MIME type and the magic bytes disagree. If the declared Content-Type goes into ACTION_VIEW, a file named invoice.pdf that has text/html content opens in a browser, and a phishing form runs from content://. The warning list does not include .apkm .xhtml .xht .mhtml .shtml .hta .dll .dmg .appx .msix .com .pif .cpl .reg .wsf .chm .url (gmail G60 blocks most of them). The FileProvider path XML is not given. Section 2 says to decode received images with ImageDecoder for previews. That decodes attacker images in the process that holds the Keystore access and all mail, while the WebView renderer is sandboxed.
FIX: On a mismatch, show the warning and use the sniffed type. Never pass declared text/html, image/svg+xml or application/xhtml+xml to ACTION_VIEW without the warning. Add the extensions above to the list. The FileProvider (exported=false, grantUriPermissions=true) exposes only <cache-path name="att" path="att/"/>: no files-path (outbox, DB) and no root-path. Grant read only. Never declare REQUEST_INSTALL_PACKAGES, so an APK attachment cannot start an install from Plico. Attachment cards show an icon, name and size. Image previews come only from the sandboxed WebView, not from in-process ImageDecoder.
VERIFY: Real gap: §11.5 checks magic bytes but does not say what happens on a mismatch. A declared text/html part named invoice.pdf would pass the extension list and open in the browser. .apkm, .xhtml/.xht, .mhtml and .shtml are relevant additions. The Windows-only types (.dll .reg .pif ...) cannot run on Android and are low value. Stating that the FileProvider exposes only cache-path att/ is a useful spec detail. Misread: §2 lists ImageDecoder, but the design never says it decodes received images for previews (the attachment cards have no thumbnails). That part is not a design defect.
BETTER FIX: When the declared type and the sniffed type differ, show the warning and pass the sniffed type to ACTION_VIEW. Apply the warning to the effective type as well as the extension (text/html, application/xhtml+xml, image/svg+xml, multipart/related/mhtml). Add .apkm .xhtml .xht .mhtml .shtml. The FileProvider XML is <cache-path name="att" path="att/"/> only. Never declare REQUEST_INSTALL_PACKAGES.

## PS15 [minor] [valid] §9 Tap PendingIntent; 13 entry points; 12 App lock
PROBLEM: MainActivity must be exported (launcher, SEND, SENDTO), but it also reads the message id from notification taps. Any app can therefore open Plico on any message. That marks the message seen, cancels its notification, and for trusted senders loads remote content, so the tracker records an open. PendingIntents that differ only in extras are the same PendingIntent (filterEquals), so a tap can open the wrong message. The design does not say that the app lock gates the share and compose entry, which shows autocomplete contacts and the account addresses.
FIX: Add <activity-alias android:name=".OpenMessage" android:targetActivity=".MainActivity" android:exported="false"/>. Notifications target the alias with data plico:message/<id>. MainActivity reads internal routes only when intent.component?.className is the alias. External intents can only open Compose. The app lock check runs for every entry intent.
VERIFY: MainActivity must be exported for the launcher and SEND/SENDTO, and §9 sends the message id to it. Any app can then open a message by guessing a small integer id. The open marks the message \Seen on the server and, for trusted senders, loads remote content (a tracker open). PendingIntent equality ignores extras, so notifications with the same requestCode and no data reuse old extras. A non-exported activity-alias with data plico:message/<id> fixes both. The point about the app lock gating share is minor, because §12 locks the whole UI.

## PS16 [minor] [partly] §6 Browser OAuth
PROBLEM: The redirect hijack by another app with the same scheme is covered: PKCE S256 makes a stolen code useless, and state blocks injected codes. The gaps are elsewhere. (1) The 'waiting flow' is only in memory. During setup there is no FGS, so on low-RAM phones the browser often pushes Plico out of memory, the redirect arrives in a new process, and sign-in fails again and again. (2) login_hint is only a hint, so the user can consent with another Google account. XOAUTH2 with user=<typed email> then fails with an unclear error. (3) 'Sign in again' leaves the old refresh token live on Google's side.
FIX: Keep {state, code_verifier, email, createdAt} in Prefs. Use it once and drop it after 10 min. OAuthRedirectActivity completes the token exchange through PlicoApp. Compare state with MessageDigest.isEqual. Add the scopes 'openid email', read the email claim from the id_token payload (a direct TLS response from the token endpoint, so no signature check is needed), and use that address as the XOAUTH2 user. After a successful re-sign-in, revoke the old refresh token. Send /revoke with the token in the POST body, not in the query.
VERIFY: (2) Real: login_hint is not binding, and XOAUTH2 with the typed address then fails. Reading the email claim from the id_token, delivered directly over TLS from the token endpoint, is fine. (1) Real but overstated: process death during the browser step is possible, but 'again and again' is not typical on minSdk-35 phones. Persisting state and verifier is still cheap. (3) The fix is wrong: Google's docs say revocation 'removes all OAuth 2.0 scopes previously granted to a project, invalidating any issued access or refresh tokens'. Revoking the old token after a re-sign-in therefore kills the new token too (Mailspring hit this in 2026). MessageDigest.isEqual for state is unneeded, because no timing oracle exists.
BETTER FIX: Persist {state, code_verifier, email, createdAt} for single use with a 10-minute limit. Add the scopes 'openid email' and use the id_token email as the XOAUTH2 user, or show 'you signed in as X'. On 'Sign in again', overwrite the old refresh token locally. Do not revoke it after the new consent. If revocation is wanted, do it before the new consent starts. Send /revoke with the token in the POST body.

## PS17 [minor] [partly] §10 Outgoing images
PROBLEM: Only images that are 'picked' get re-encoded. The photo picker already removes location, but files from ACTION_SEND or the document picker keep EXIF/GPS (privacy-security G28). These are the most important paths. Only camera-style names get renamed, so names like Screenshot_20261016-101523_Signal.png still show the time and the app. Re-encoding a PNG screenshot as JPEG makes text blurry.
FIX: Re-encode every image/jpeg, heic, png and webp attachment, from any source. Keep PNG as PNG (Bitmap.compress drops the tEXt/eXIf chunks), encode JPEG/HEIC to JPEG at about q90, and do not touch GIF. Every re-encoded image gets the name image-N.<ext> unless the user renames it. 'Original quality' stays available for each item.
VERIFY: Real: 'Images picked as attachments' does not clearly cover ACTION_SEND and SAF files, which G28 says are not redacted. Re-encoding PNG screenshots to JPEG blurs text. Screenshot names (Screenshot_20261016-101523_Signal.png) show the time and the app, like camera names. Overreach: renaming every re-encoded image to image-N discards meaningful names the user chose (floorplan.png), and the default should not do that.
BETTER FIX: Re-encode every JPEG/HEIC/PNG/static WebP from every source (photo picker, document picker, share). PNG stays PNG; JPEG and HEIC become JPEG at q≈90. GIF and animated WebP stay untouched, with the 'metadata kept' note. Extend the rename rule to camera and screenshot patterns (names with date/time stamps) only. Keep 'original quality' for each item.

## PS18 [minor] [valid] §12 Logging; 4.3 / 4.7 log callbacks
PROBLEM: Redaction is defined only for IMAP AUTHENTICATE lines. SmtpClient logs 'AUTH PLAIN <base64>' and XOAUTH2 bearer tokens, and debug builds are used for live tests with real accounts. In release, Log.w and Log.e stay, and exception messages from :mail contain server text with addresses (for example SMTP '550 5.1.1 <bob@x> ...'). The R8 rule does not strip System.out/err (println, printStackTrace).
FIX: Apply the same redaction in SmtpClient (AUTH lines and 334 exchanges). In release, log only the exception class and the reply code, never e.message. Add a lint/R8 rule so that no code uses printStackTrace or println.
VERIFY: §4.3 redacts only IMAP AUTHENTICATE lines. §4.7 gives SmtpClient a log callback with no redaction, so debug builds used for live tests write the AUTH PLAIN base64 password or the XOAUTH2 bearer token to logcat. ## PS19 [minor] [valid] §13 Setup (credentials)
PROBLEM: The design does not say that the Riseup password and the Gmail app password fields support password-manager autofill. Riseup users with long random passwords expect it. Without it, users copy passwords through the clipboard or pick weaker passwords. The Riseup password also unlocks the user's encrypted mail at Riseup (privacy-security G23).
FIX: On the setup fields, set contentType Username/EmailAddress and Password, use KeyboardType.Password with autocorrect off and PasswordVisualTransformation, and clear the field value after the connection test.
VERIFY: The design gives no autofill rule for the Riseup password, the Gmail app password and the address fields. Users with long random passwords expect a password manager to fill them. Compose 1.8+ semantics contentType (Username/Password) and the Material 3 secure text field do this with no new library, and they do not conflict with the incognito-keyboard flag. Minor, but a real missing feature with a one-line fix per field.
