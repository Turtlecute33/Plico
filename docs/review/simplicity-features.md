# simplicity-features
I read DESIGN.md completely and checked it against the five research files, RFC 7162/3501, the SQLite docs (I also ran a local test), FairEmail's manifest and FAQ, the Google IMAP extensions doc and the Surreptitious Sharing write-up. I found 9 major problems. (1) Delayed ops and queued sends have no wake-up: notification Archive/Delete, and Send followed by screen-off, can wait up to 28 min. (2) The notification watermark is not in the schema, so old mail notifies on first sync, backfill and resync. (3) Standard sync has no first-sync limit or backfill, so the first Riseup sync fetches every header. (4) Drafts show twice, have no stable Message-ID, and drafts made on other devices cannot be edited. (5) Riseup has no Archive target. (6) Share and mailto intents can attach Plico's own private files (Surreptitious Sharing); the mailto VIEW filter is also missing. (7) IDLE events use sequence numbers that the app cannot map, and changes in the Gmail INBOX have no defined action. (8) Folders with notify=1 are never checked in the background and have no UI. (9) FTS rows are orphaned and ids are reused, so deleted mail text stays searchable and ops can hit the wrong message. The 14 minor findings fall into three groups. Over-engineering and dead code: duplicate columns, capability fallbacks for capabilities both servers have, the send op that duplicates the draft outbox. Inconsistencies: unread counts with no source, mass-delete guard stored per account, Gmail INBOX taken as a user label, sort date not defined. Expected features that are missing: reply identity rules, Bcc in the Riseup Sent copy, forward with attachments, autosave, Select all / Empty trash, chunked attachment download, device-account selection, UTF-8 server search. Each fix is small, and several remove code. I did not challenge the fixed decisions.

## EM1 [major] [valid] §§7.4 Ops, §7.5 Sending, §8.3 Timers, §9 Actions
PROBLEM: Nothing wakes the session when a delayed op or a queued send becomes due. Archive/delete/move/spam ops get run_at = now + 4 s, and queued drafts get send_at = now + undo seconds. But §8.3 computes the alarm only from keepalive, backoff, poll and OAuth expiry. ActionReceiver makes the op with the same 4 s delay and calls kick() at once, so the op is not due and does not run. After that, only an IDLE exit runs it: up to 25 min on Riseup, 9–28 min on Gmail. Example: the user taps Send, then turns the screen off. Op retry backoff (up to 1 h) has the same gap.
FIX: (1) Notification actions make ops with run_at = now (no snackbar, so no undo). (2) In PushEngine, add per account min(op.run_at) and min(draft.send_at WHERE state = queued) to the earliest-due-time calculation. When that alarm fires, call kick(). While the UI is visible, a coroutine delay to run_at is a shortcut, but the alarm is the authority.
VERIFY: The gap is real. §7.4 sets run_at = now+4 s and runs ops only 'before every sync'. §7.5 sets send_at = now+undo. §8.3 names keepalive, backoff, poll and OAuth expiry as due times, and no op or draft time. §9 calls kick() when the op is not due yet. §8.3 itself forbids delay() for work that must run with the screen off (android-push G18). The fix is minimal and correct.

## EM2 [major] [valid] §§5 Schema, §9 New mail
PROBLEM: §9 notifies messages 'newer than the account's notification watermark'. No column or Prefs key holds a watermark. message.notified defaults to 0, so rows from the first sync, header backfill, server-search hits and a UIDVALIDITY resync are unseen inbox rows that pass the rule. Adding an account with 300 unread inbox mails, or a folder resync, gives a burst of notifications for old mail.
FIX: Remove the watermark concept. Insert every row with notified = 1, except rows from the step-4 'new UIDs' fetch when folder.uidnext was already > 0 before the sync (that is, not the first sync and not after a UIDVALIDITY reset). Backfill and search hits always insert notified = 1. This is one rule with no new column.
VERIFY: §9 uses an 'account's notification watermark', but §5 has no column or Prefs key for it, and message.notified defaults to 0. As written, the first sync, backfill, search hits and a UIDVALIDITY resync all qualify. The rule 'notified = 1 unless the row came from a step-4 new-UID fetch with uidnext > 0 before the sync' needs no new column and covers all of these cases.

## EM3 [major] [valid] §§7.2 Standard sync step 4, §7.3 backfill, §7.1 loop
PROBLEM: Step 4 fetches 'UID <uidnext_local>:*'. folder.uidnext defaults to 0, so the first sync of every Riseup mailbox fetches the headers of all messages in one command. '0:*' is also not a valid UID set, because UIDs start at 1. The backfill (newest 200 first, 500 per step, backfill_uid) is written only for Gmail in §7.3, but §7.1 runs a 'bounded backfill step' for every account. A 1 GB Riseup mailbox with tens of thousands of mails, argon2 logins and server throttling (riseup R4, R15) keeps the first screen empty and blocks IDLE for a long time.
FIX: Move the backfill into §7.2 so it applies to every kind-0 mailbox. First sync: UID SEARCH ALL (ESEARCH returns compact ranges), fetch the newest 200 UIDs, set backfill_uid = the lowest UID fetched and uidnext = server UIDNEXT. Later steps fetch the next 500 below backfill_uid. §7.3 then only adds the X-GM fetch items. This gives one code path.
VERIFY: §7.2 step 4 is 'UID FETCH <uidnext_local>:*' and uidnext defaults to 0. The backfill rules appear only under §7.3 Gmail, but §7.1 runs a backfill step for every account. RFC 3501 seq-number is nz-number, so '0:*' is also invalid. With TREES, every header fetch decrypts on the server. Moving the backfill into §7.2 gives one code path.
BETTER FIX: Same as proposed. You do not need UID SEARCH ALL: 'FETCH <max(1,EXISTS-199)>:* (UID ...)' by sequence number gets the newest 200 at once. Later steps fetch below backfill_uid. Always clamp the lower UID bound to 1.

## EM4 [major] [partly] §§5 draft table, §7.3 Gmail drafts, §7.5, §13 Drafts/Compose
PROBLEM: (a) The Drafts view lists the local `draft` row ('Edit', 'Retry'). append_draft also puts a copy on the server, which syncs back as a `message` row (Riseup Drafts is kind 0 with sync=1; Gmail's \Draft label view comes from All Mail). Each draft therefore shows twice. (b) `draft` has no Message-ID column. MessageBuilder makes a new one on each build, so no rule can match the local and server copies, and each server version gets a different id. (c) A draft started in Gmail web or Roundcube shows in Drafts, but no UI path opens a `message` row for editing. (d) Gmail: APPEND needs the real mailbox name ([Gmail]/Drafts, localized), and server_uid is a UID in that mailbox. But §7.3 stores only the label view (kind 1, path '\Draft'), so the name and its UIDVALIDITY are not stored anywhere.
FIX: Add draft.message_id. Make it once and reuse it for every APPEND and for the final send. Drafts view = local drafts + server draft rows whose message_id is not in a local draft. Opening a server draft copies it into a new local draft (text, plus attachments downloaded into outbox/) with server_uid set, so the next save or send deletes the old copy. For Gmail, store the \Drafts mailbox as a kind-0 folder row with sync = 0 (name and uidvalidity only). Accept both \Draft and \Drafts as the label.
VERIFY: (a) is real. Drafts syncs back as message rows: Riseup Drafts is kind 0 with sync=1, and Gmail drafts are in All Mail with the \Draft label (Mozilla bug 844494; a live 2026 fetch returned \\Draft, while Google's doc example shows \Drafts). (c) is real: no path edits a server draft. (d) is real: the [Gmail]/Drafts name and its UIDVALIDITY are not stored. (b) is overstated. On Riseup, draft.server_uid comes from APPENDUID and is the UID of the synced row in the same Drafts folder, so a match is possible. Only Gmail, where the synced row comes from All Mail, needs another key.
BETTER FIX: As proposed: add draft.message_id, reuse it for every APPEND and the send, and use it as the one dedup key for both providers. Store the Gmail \Drafts mailbox as a kind-0 row that is not synced, and accept both \Draft and \Drafts. Opening a server draft copies it into a local draft with server_uid set.

## EM5 [major] [valid] §§7.2 step 1 roles, §13 swipe/drawer, §9 Archive action
PROBLEM: Roles come only from SPECIAL-USE attributes. Riseup's sample Archive folder has no \Archive flag, and new Riseup accounts may have no Archive folder. The default start→end swipe, the notification Archive action and the drawer item 'Archive (Riseup)' then have no target folder. §7.2 also never defines the Riseup action mapping (archive, delete, delete forever, spam, not spam); only Gmail has one in §7.3. ImapClient.create() exists but no algorithm uses it.
FIX: Set the archive role from the \Archive attribute. If no folder has it, use a folder named 'Archive' (case-insensitive). If none exists, create 'Archive' on first use. Add an 'Archive folder' picker to account settings. In §7.2, write the Riseup mapping: archive = UID MOVE to the archive folder; delete = MOVE to \Trash; delete inside Trash = \Deleted + UID EXPUNGE; spam = MOVE to Spam; not spam = MOVE to INBOX.
VERIFY: Riseup R12: the Archive folder had no \Archive flag. The research says to let the user choose the archive folder. §7.2 sets roles only from attributes, and only §7.3 (Gmail) has an action mapping. Without a fix, the default swipe, the notification Archive action and the drawer item have no target.
BETTER FIX: As proposed. Also match 'Archives' (the Thunderbird default) when you look for a folder by name, before you create 'Archive'.

## EM6 [major] [valid] §§13 Compose intents, §11.3 mailto
PROBLEM: Compose accepts ACTION_SEND / SEND_MULTIPLE EXTRA_STREAM URIs with no origin check. A malicious app can send file:///data/data/app.plico/databases/... or a content:// URI from Plico's own FileProvider (cacheDir/att, outbox) with a prefilled To and subject. Plico can read its own files, so it attaches the mail database or other mails' attachments, and one tap on Send leaks them. Some clients also honour mailto 'attach=' parameters. Separately, browsers open mailto: links with ACTION_VIEW + BROWSABLE, and the design declares only SENDTO, so a mailto link in a browser does not offer Plico.
FIX: Accept only content:// URIs whose authority is not Plico's own. Reject file:// and own-authority URIs with a short message. Copy accepted streams into outbox/ at once (the design already does this). Parse only to, cc, bcc, subject and body from mailto (RFC 6068) and ignore all other parameters. Add a VIEW + BROWSABLE mailto intent filter that uses the same parser.
VERIFY: This is the Surreptitious Sharing attack class. ContentResolver.openInputStream accepts file:// and Plico's own FileProvider URIs, and Plico can read its own files. The design copies EXTRA_STREAM content into outbox/ with no check of the source. FairEmail's manifest has both a VIEW+BROWSABLE mailto filter and a SENDTO mailto filter, and browsers send mailto links as VIEW+BROWSABLE. §13 declares only SENDTO, so browsers do not offer Plico. The fix is small and correct.

## EM7 [major] [valid] §§4.4 IdleEvent, §4.3 onUnsolicited, §7.1 loop, §7.3 Gmail IDLE
PROBLEM: IdleEvent.Expunge(seq) and Flags(seq, uid?, flags) carry sequence numbers, but the design keeps no seq-to-UID map. For Gmail, the IDLE mailbox (INBOX) is a label view, not a synced mailbox, and its UIDs are not All Mail UIDs. So an EXPUNGE or FETCH in INBOX (mail archived or read in Gmail web) cannot change any local row. §7.3 defines only the EXISTS path. Result: notifications for mail already read or archived on another device stay on the phone until some later full sync, which breaks the §9 rule 'by sync, cancel its child'. onUnsolicited also lists VANISHED, which needs QRESYNC, which is not used.
FIX: Reduce IdleEvent to `Changed` and `Keepalive`, and remove the typed seq/uid/flags events and VANISHED. On Changed: send DONE, then run §7.2 steps 4–6 on the synced mailbox behind the IDLE (Riseup INBOX; Gmail All Mail with CHANGEDSINCE + X-GM-LABELS). If live tests show that Gmail label-only changes do not raise MODSEQ, compare `UID SEARCH X-GM-LABELS "\\Inbox"` in All Mail with the local inbox rows instead. This is less code, and notifications get cancelled.
VERIFY: For Gmail, INBOX is a label view and its sequence numbers and UIDs do not map to All-Mail rows. §7.3 defines only the EXISTS path. RFC 7162 §3.2.4 requires UID in unsolicited FETCH only on QRESYNC servers, and Gmail has no QRESYNC. VANISHED comes only after ENABLE QRESYNC, which the design never sends. A single 'Changed' event followed by the incremental sync of the backing mailbox is less code, and it also cancels the notifications.
BETTER FIX: As proposed. Gmail may send no IDLE events for changes made on other devices (gmail open question), so also run the cheap CHANGEDSINCE check at each Gmail client-mode refresh.

## EM8 [major] [valid] §§5 folder.notify, §8.3, §9, §13 Settings
PROBLEM: §9 notifies for folders with folder.notify = 1, but no algorithm checks those folders in the background. IDLE watches only INBOX, and the refresh is only DONE + IDLE. Mail that Riseup filters put into another folder, or Gmail filters that skip the inbox and only add a label, never triggers a notification until the app opens. The UI also has no control to set folder.notify.
FIX: At every re-IDLE wake (Riseup about every 25 min during a server keepalive; Gmail at each 9–28 min refresh) and at every IDLE exit, send STATUS (UIDNEXT) for each notify=1 kind-0 folder. For Gmail, send STATUS on All Mail when any label has notify=1. If UIDNEXT changed, run step 4 on that folder. This adds no new wake-up. Add a 'Notify for new mail' toggle to the folder long-press menu in the drawer.
VERIFY: folder.notify is read in §9, but nothing sets it: §13 has no control for it. Nothing checks those folders in the background either, because §8.3 refresh is only DONE+IDLE. The research decisions (riseup A, gmail C) both said to send STATUS to the other folders at wake-ups. The proposed STATUS sweep at existing wakes adds no radio wake-up.

## EM9 [major] [valid] §§5 message_fts, message.id
PROBLEM: message_fts is a virtual table, so ON DELETE CASCADE does not reach it, and the design defines no trigger. Rows deleted by expunge sync, UIDVALIDITY resync, delete forever or account removal leave their subject, address and body text in the FTS index on disk. message.id is INTEGER PRIMARY KEY without AUTOINCREMENT, so SQLite reuses the highest deleted id. A new message then inherits the old FTS text (wrong search hits). op.message_ids, draft.source_message and notification ids can also point to the wrong message, so an op could act on the wrong message.
FIX: Add `CREATE TRIGGER message_ad AFTER DELETE ON message BEGIN DELETE FROM message_fts WHERE rowid = old.id; END;` (it also fires on cascades). Declare message.id and draft.id as INTEGER PRIMARY KEY AUTOINCREMENT so ids are never reused.
VERIFY: I tested this in sqlite3. An AFTER DELETE trigger on message fires on an FK cascade and empties message_fts. Without AUTOINCREMENT, a deleted max id is reused at once, and after all rows of an account are deleted, ids start again at 1. The design has no trigger, so FTS text is left on disk and attaches to new rows. op.message_ids is not a foreign key, so a reused id can make a pending op act on the wrong message. The trigger plus AUTOINCREMENT is the minimal fix.

## EM10 [minor] [valid] §§5 folder.unread/total, §13 drawer
PROBLEM: folder.unread and folder.total have no defined source. Gmail label views (kind 1), including the inbox, are never STATUSed or SELECTed, so 'All inboxes (unread count)' is 0 or stale for Gmail. A server count also ignores local optimistic changes (hidden rows, mark read before the op runs). The drawer shows no counts for each account or folder, which users expect.
FIX: Drop folder.unread and folder.total. Compute counts with one query: SELECT folder_id, count(*) FROM message_folder JOIN message ... WHERE seen = 0 AND hidden = 0 GROUP BY folder_id, driven by Db.changes. Show the count next to every drawer entry.
VERIFY: No algorithm writes folder.unread or folder.total. Gmail kind-1 views, including the inbox that the unified count uses, are never sent STATUS. A local GROUP BY count is simpler and includes the optimistic local changes. It undercounts only until the backfill is complete, which is acceptable.

## EM11 [minor] [valid] §§7.4 op kinds, §7.5 Sending, §5 draft.state
PROBLEM: There are two outbox mechanisms. §7.4 lists a `send` op kind, but §7.5 sends from the draft table using state and send_at. draft.state 4 'sent' can never be seen, because §7.5 deletes the row at that moment. A crash while a draft is in state 2 'sending' has no defined result: a resend can duplicate the mail, and leaving it hides it.
FIX: Make the draft table the only outbox and remove the `send` op kind and state 4. At startup, set any state-2 draft to 3 'failed' with the text 'May have been sent — check Sent before you retry'. Do not resend it automatically.
VERIFY: §7.4 lists a 'send' op kind, but §7.5 sends from the draft table. State 4 is set and the row is deleted in the same step. A crash in state 2 has no defined result. One outbox, with state 2 changed to 'failed — may have been sent' at startup, is simpler and does not send twice.

## EM12 [minor] [partly] §§7.2 steps 3 and 6 (mass-delete guard)
PROBLEM: The guard writes account.state_text, which also holds sign-in and TLS errors. It is per account, so the 'Resync folder' banner cannot tell which folder triggered it. A UIDVALIDITY change drops all local rows of the mailbox without any guard, even though riseup R22 (no backups; reset wipes mail) asks to keep local copies and ask first.
FIX: Add folder.guard INTEGER (0/1) and show the banner for each folder. Treat a UIDVALIDITY change as 'all local rows would be deleted' and send it through the same guard, so no new code path is needed.
VERIFY: Two points are real. account.state_text is shared with the sign-in, TLS and pause states, and the guard is per account, not per folder. The UIDVALIDITY drop also ignores the riseup R22 implication. But the fix is incomplete. After a UIDVALIDITY change the local UIDs are stale. If you only skip the deletes, steps 4–6 and pending ops continue with old uidnext and old UIDs. They then collide with UNIQUE(folder_id, uid) or act on the wrong messages.
BETTER FIX: Add folder.guard and show a banner for each folder. While guard=1, freeze the folder: no sync steps, and ops on it are held. Send the UIDVALIDITY change through the same guard. 'Resync folder' then drops the rows, resets uidvalidity, uidnext and modseq, clears the guard and syncs. 'Keep' stops sync of that folder.

## EM13 [minor] [valid] §§5 Schema (redundant or unused columns)
PROBLEM: Several columns duplicate another mechanism or are never used. account.offline_all + body_days store one setting twice. folder.sync + folder.hidden are two switches with no UI. folder.selectable is not needed, because \Noselect folders are hidden anyway. account.notify duplicates the per-account channel mail_<id>, which the user can already turn off, together with sound and lock-screen settings. message.mdn_requested and the DISPOSITION-NOTIFICATION-TO header fetch have no reader, because receipts are never sent or shown. attachment.file stores a path into a cache that is deleted after 1 h. body.headers has no source, because sync fetches only HEADER.FIELDS. message.gm_thrid has no user, because there are no threads in v1.
FIX: Use body_days with 0 = all. Keep only folder.hidden (hidden kind-0 folders are not synced). Do not store \Noselect folders. Drop account.notify: skip posting when the channel importance is IMPORTANCE_NONE, and link to ACTION_CHANNEL_NOTIFICATION_SETTINGS. Drop mdn_requested and that header. Derive attachment paths as cacheDir/att/<messageId>/<attachmentId> and check exists(). Drop body.headers and fetch BODY.PEEK[HEADER] on demand for 'View headers'. Drop gm_thrid until threads come.
VERIFY: Each item is dead or duplicated in the design text. mdn_requested has no reader (§10 never sends or shows receipts). body.headers has no fetch that fills it. offline_all duplicates body_days. sync, hidden and selectable overlap and no UI sets them. attachment.file points into a cache that is deleted after 1 h. account.notify duplicates the per-account channel. gm_thrid can be fetched later with one UID FETCH when threads come. All of these are small, safe cuts.
BETTER FIX: As proposed. To stay consistent with EM4, store the non-synced Gmail \Drafts mailbox row as kind 0 with hidden=1 ('hidden kind-0 = not synced').

## EM14 [minor] [valid] §§2, §4.4 ImapClient, §6 Riseup login, §7.3 categories
PROBLEM: Some code exists only for cases that cannot happen with the two hardcoded servers. The uidMove COPY+STORE+EXPUNGE fallback and the plain-SEARCH fallback are dead: both servers advertise MOVE and ESEARCH. select(mailbox, condstore) duplicates ENABLE CONDSTORE, which already makes every SELECT CONDSTORE-aware. examine() has no caller. kotlinx-coroutines-core is listed for :mail, which is a blocking module. The Riseup 'retry once with the bare username' cannot help (both forms work, and an alias cannot log in), and on a wrong password it doubles the failed argon2 logins. The Gmail category filter runs one SEARCH per category where one is enough.
FIX: After login, require {IDLE, MOVE, UIDPLUS, ESEARCH, SASL-IR} and fail with Server('missing <cap>') if one is absent. Delete the MOVE/SEARCH fallbacks, the condstore parameter, examine() and VANISHED handling. Remove coroutines from :mail. Remove the bare-username retry. Use one search: UID SEARCH UID <new> X-GM-RAW "category:primary OR category:updates".
VERIFY: Both servers advertise MOVE, UIDPLUS and ESEARCH (gmail G15, riseup R11). RFC 7162 lists ENABLE CONDSTORE as a CONDSTORE enabling command, after which SELECT returns HIGHESTMODSEQ, so the condstore parameter adds nothing. Nothing calls examine(). §4 makes :mail blocking, so it does not need coroutines. R7 and the missed fact say that both login forms work and an alias cannot log in, so the bare-name retry only doubles failed argon2 logins. X-GM-RAW supports OR, so one search is enough. Checking the required caps once is simpler than keeping fallbacks.
Superseded 2026-10-17: fallbacks needed for generic servers. The required set is only IMAP4rev1 or IMAP4rev2; MOVE, UIDPLUS, ESEARCH and SASL-IR are optional with fallbacks, and setup retries once with the local part as user name, only for servers found by DNS SRV (RFC 6186). See DESIGN.md §4.4 and §6.3.

## EM15 [minor] [partly] §§7.6 Search, §4.3 Command builder
PROBLEM: Server search with non-ASCII terms (for example Italian or German words, or names) is sent as a literal without 'CHARSET UTF-8'. RFC 3501 then assumes US-ASCII, so Gmail and Dovecot reject the search or match wrongly. For Riseup, §7.6 does not say which mailboxes 'UID SEARCH TEXT' runs in. Because the account has only one connection and a mutex, a long search (every message decrypted on the server) blocks push and body loads for that account, with no way to cancel.
FIX: When a query has non-ASCII characters, send 'UID SEARCH CHARSET UTF-8 ...' with the term as a literal. On Riseup, search only the open folder (INBOX when the view is unified). Show 'Searching on server…' with Cancel, which closes the socket and reconnects through the normal backoff.
VERIFY: The scope and blocking points are real. §7.6 does not say which mailbox the Riseup UID SEARCH TEXT runs in, and a long TREES search holds the account mutex with no cancel. The charset claim is overstated. Dovecot 2.3 cmd-search.c uses charset = "UTF-8" when no CHARSET is given, so Riseup works. Command.string() already sends non-ASCII as a literal. Only Gmail is at risk: a report shows CHARSET UTF-8 plus a literal works, and RFC 3501 defaults to US-ASCII.
BETTER FIX: Always send 'CHARSET UTF-8' when the query has non-ASCII characters. This is one rule for both servers. On Riseup, search the open folder. Show Cancel, which closes the socket and reconnects through the normal backoff.

## EM16 [minor] [valid] §§13 Compose (reply addressing)
PROBLEM: The design has identities but no reply rules. It does not say which From a reply uses, so replies to mail sent to a Riseup alias or Gmail Send-as address go out from the main address and expose it. Reply-To handling is not stated, and Reply all does not remove the user's own addresses, so users email themselves.
FIX: Default From = the identity whose address is in the source's To or Cc (case-insensitive), else the account address. Reply goes to Reply-To if present, else From (for a message in Sent, to its To). Reply all = that target + To + Cc minus all of the account's own addresses. Do not stack 'Re:' prefixes.
VERIFY: The design has identities but no rule for the reply From, Reply-To or Reply all. A reply to mail sent to a Riseup alias or a Gmail Send-as address then goes out from the main address and exposes it, which conflicts with priority 2. The proposed rules are the standard minimal set.

## EM17 [minor] [valid] §§7.5 Riseup Sent APPEND, §10
PROBLEM: The Riseup Sent copy is the same MIME as the wire message, which never has a Bcc header. The user's Sent folder therefore loses the record of who got a Bcc. The research says to keep Bcc in the Sent copy.
FIX: MessageBuilder.build() returns two byte arrays: wire (no Bcc) and sentCopy (the same Date, Message-ID and boundary, plus a Bcc header). Riseup APPENDs sentCopy. Gmail is unchanged.
VERIFY: §10 removes Bcc from the wire, and §7.5 APPENDs that same MIME to the Riseup Sent folder, so the user loses the Bcc record. privacy-security says: 'Keep Bcc in the Sent copy (Riseup needs APPEND...)'.
BETTER FIX: Simpler: make the Sent copy by putting the line 'Bcc: …\r\n' before the wire bytes. A header line can go first, so you do not need a second build.

## EM18 [minor] [valid] §§13 Compose, §7.5 size check
PROBLEM: Forward does not say what happens to the original attachments, but users expect them to be included. The draft is saved only when the user leaves Compose, so text is lost if Android kills the process during a photo or document pick. The compose 'size check' needs a limit before any SMTP connection exists, but SIZE is known only after EHLO at send time.
FIX: Forward: download the source attachments (loadAttachment) into outbox/<draftId>/ and list them as removable chips. Save the draft row locally on every onStop, and queue append_draft only on leave. Put maxMessageBytes in Providers (Riseup 25,600,000; Gmail 35,882,577). Warn in compose when raw size × 1.37 is over it. Keep the SMTP SIZE check at send.
VERIFY: Forward does not say what happens to the original attachments. 'Leaving saves the draft' does not clearly cover process death while a picker is open. The compose-time size check has no limit, because SIZE is known only after EHLO at send time. The server settings are already hardcoded, so a maxMessageBytes value per provider fits the design (R14 25,600,000; G28 35,882,577).

## EM19 [minor] [valid] §§13 Mailbox multi-select, message overflow
PROBLEM: Users of a Riseup/Gmail client expect some bulk and folder actions that are missing: Select all, Empty Trash / Empty Spam, Spam/Not spam and Labels in multi-select, and 'New folder/label' when moving. ImapClient.create() exists but no UI uses it.
FIX: Add 'Select all' (loaded rows of the view) to the selection bar. In the Trash and Spam overflow, add 'Empty' → confirm → one delete_forever op over all local rows of that folder, after a sync. Add Spam/Not spam and Labels (Gmail) to the multi-select overflow. Add a 'New…' row in the Move/Labels picker that calls create() online and shows an error when offline.
VERIFY: §13 multi-select has only Archive, Delete, Read/Unread, Star and Move. There is no Select all, no Empty Trash or Spam, no Spam/Labels in multi-select, and nothing calls create(). Users of Gmail and K-9/FairEmail expect these actions, and each reuses the existing op kinds.

## EM20 [minor] [valid] §§4.2 ImapReader, §4.4 FetchItem.sections, §7.1 loadAttachment
PROBLEM: An attachment download reads the whole literal into one ByteArray (up to 50 MB, with base64 about 1.37× the raw size), then decodes it in memory. The UI process and the FGS are the same process, and Android 17 adds memory limits for all apps (android-push G15). The user also sees no progress for a 25 MB download.
FIX: Fetch BODY.PEEK[<section>]<offset.1048576> in a loop (the tokenizer already supports <n> partials). Append the raw bytes to a temp file, then decode with Base64.getMimeDecoder().wrap(FileInputStream) into the cache file. Progress = offset / part size. No streaming reader is needed.
VERIFY: §4.2 and §4.4 read each literal fully into a ByteArray (up to 50 MB), and the UI and the service share one process (§3). A 25 MB attachment uses about 34 MB as a literal plus 25 MB decoded, and the user sees no progress. Chunked BODY.PEEK[section]<offset.size> keeps the reader as it is and gives progress. JavaMail, which FairEmail uses, also fetches in partial chunks by default. This is minor, but real.

## EM21 [minor] [valid] §§6 DeviceCredentials, §13 Setup
PROBLEM: The design does not say how the user picks the Google account on the phone. Since Android 8, getAccountsByType('com.google') returns nothing to an app that does not own the accounts unless the user grants visibility, and GET_ACCOUNTS no longer helps. The first getAuthToken for mail.google.com also needs a consent screen (KEY_INTENT), which should appear during setup, not as a later 'Sign-in needed' alert.
FIX: At setup, launch AccountManager.newChooseAccountIntent(null, null, arrayOf("com.google"), null, null, null, null). Store the chosen name in device_account. Call the Activity overload of getAuthToken once, so the consent screen shows. Background calls keep notifyAuthFailure = false. If the account disappears from AccountManager, set AuthRequired.
VERIFY: The Android 8.0 changes page says that apps cannot see other authenticators' accounts unless the user grants access, that GET_ACCOUNTS is not sufficient, and that newChooseAccountIntent grants access. The design stores device_account but never says how the user picks the account, and it sends the first consent (KEY_INTENT) to a later 'Sign-in needed' alert instead of showing it during setup.

## EM22 [minor] [partly] §§5 message.date, §7.2 step 4, list ORDER BY
PROBLEM: Sync fetches both the Date header and INTERNALDATE, but `date` does not say which one it holds. If it is the Date header (sender-controlled), spam with a future date stays at the top of every list, and the body window (date >= now - body_days) uses a value that the sender can forge.
FIX: Define message.date = INTERNALDATE (server arrival time) and use it for sort and for the body window. Show the Date header only in the message view (parse it from the fetched fields; no new column).
VERIFY: Real ambiguity. Step 4 fetches both INTERNALDATE and the Date header, and §5 'date' does not say which one it holds. Sorting by the Date header lets the sender pin mail to the top with a future date. But part of the fix does not work: the fetched header fields are not stored, so the message view cannot 'parse the Date header from the fetched fields' without a column or a new fetch.
BETTER FIX: Define message.date = INTERNALDATE and use it for sort, the body window and display. Show the sender's Date header only in 'View headers', which fetches the header on demand. You need no new column.

## EM23 [minor] [partly] §§7.3 Gmail label views from LIST
PROBLEM: 'Every user label from LIST (folders that are not system mailboxes)' also matches INBOX, because Gmail lists INBOX without a SPECIAL-USE attribute. That gives a second, always-empty 'INBOX' label view next to the \Inbox view, because X-GM-LABELS uses \Inbox. 'System mailbox' is not defined.
FIX: Label views = LIST entries that are not \Noselect, have no SPECIAL-USE attribute, and are not named INBOX (case-insensitive). Map INBOX to the \Inbox view.
VERIFY: 'System mailboxes' is not defined, and Gmail lists INBOX with no SPECIAL-USE attribute. But the design already names the \Inbox label view as the inbox, so most readers would not make an 'INBOX' user label. The risk is low. The one-line definition is still a useful clarification.
BETTER FIX: Label views = LIST entries that are not \Noselect, have no SPECIAL-USE attribute, and are not named INBOX (case-insensitive).
