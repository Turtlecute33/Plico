# protocol-sync
I checked §4, §7 and §10 of DESIGN.md against RFC 3501/9051/5321/6851/7162, the research files, and live Gmail transcripts from go-imap PRs #29/#31/#32 and issue #19. I logged in to no mail server and changed no file. The low-level parts are mostly correct: implicit TLS, the SASL PLAIN and XOAUTH2 flows (including the empty answer to the JSON challenge), the literal rules, no UTF8=ACCEPT, modified UTF-7 in X-GM-LABELS for FETCH/STORE, \Draft as the live label name, the CONDSTORE-only path, and no Sent APPEND on Gmail. The real problems are in the sync and send logic. One is critical: when a Riseup Sent APPEND fails after a good SMTP send (for example when the 1 GB quota is full), the retry sends the whole message again. The major ones: sync can overwrite local changes that are still queued. Mail that arrives just before IDLE starts is never notified. The expunge diff on Gmail All Mail runs on every new mail and can go over the 1 MB line limit. Riseup has no Archive role, so the default swipe breaks. Gmail labels created or renamed after a LIST never fill. On Gmail, deleted drafts go to Trash and appear twice in Drafts. Gmail Move has no rule. The mass-delete guard fires on normal Trash/Spam purges. UID n:* returns the last message again. UIDVALIDITY changes leave pending ops on stale UIDs. Queued work (undo windows, Send) has no alarm, so it can wait up to 28 min. The design does not handle Gmail accounts that hide All Mail from IMAP. Error classification is missing. A partial RCPT failure can duplicate mail. Non-ASCII server search fails on Gmail. Inbox correctness depends on an unverified MODSEQ behaviour. Folders with notifications on get no background sync. Display can drop parts of multi-part bodies. Each finding has a small fix that fits the priorities.

## PS1 [critical] [valid] §7.5 Sending, 7.4 Ops, 4.7 SmtpClient
PROBLEM: The send pipeline can send the same mail more than once. SMTP send, the Riseup Sent APPEND, the server-draft delete and the \Answered flag run as one unit, and '4xx/transient → retry with backoff' runs the whole unit again. So an IMAP step that fails after SMTP returned 250 sends the mail again at each backoff step (5 s, 30 s, 2 m, 10 m, 1 h ...). Examples of such failures: Riseup quota full (NO [OVERQUOTA] on APPEND), a network drop, or throttling. There is also no rule for a draft left in state 2 'sending' after a process kill. And the 60 s read timeout covers the reply to the final '.'. A timeout after a full upload is ambiguous, and a retry makes a duplicate.
FIX: In the same DB transaction that records the 250 for the final dot, set draft.state = 4 (sent). Then queue separate ops: append_sent (Riseup only), delete_draft, and flags \Answered. Each op retries on its own and never resends. At start-up, set any draft in state 2 to state 3 with the text 'May have been sent. Check Sent before you retry' (no auto-resend). Use a 10-min read timeout only for the reply to the final dot. A timeout there gives the same 'may have been sent' state.
VERIFY: §7.5 runs SMTP, Sent APPEND, draft delete and \Answered as one chain. 'state = sent' is set only at the end. §7.4 lists 'send' as an op kind, so a transient failure means attempts++ and a retry. Nothing records that SMTP already returned 250. An IMAP failure after the 250 (an OVERQUOTA APPEND on Riseup, per R18, or a network drop) therefore sends the mail again. No rule covers state 2 after a process kill. A timeout after the final dot is ambiguous by nature (RFC 5321 §4.5.3.2.6 gives 10 min for it). The fix is minimal: commit state 4 when the 250 arrives, make the follow-up steps separate ops, and move state 2 to 'may have been sent' at start-up.

## PS2 [major] [valid] §7.4 Pending operations vs 7.2/7.3 sync
PROBLEM: Sync can overwrite local changes that are still queued. Ops run 'before every sync', but only due ops run. Ops in the 4 s undo window or in backoff (up to 1 h when offline) do not run. openFolder() is not said to flush ops at all. The sync then writes the server flags (CHANGEDSINCE) and rewrites the Gmail label rows from X-GM-LABELS. Gmail often raises the modseq of new mail (read on another device, \Important added). So an archive, delete or read that the user just did comes back in the UI until the op runs. Also, 'permanent error → drop the op and resync' has no rule that undoes the local change. A row with hidden = 1 stays hidden for ever if sync keeps hidden, and comes back if sync resets hidden.
FIX: Add one rule to the sync writer: do not update seen/flagged/answered/draft, Gmail label rows or hidden for a message id that any op row still references (any run_at). After the op is done, the next CHANGEDSINCE returns the message (the op's STORE raised its modseq) and makes local and server equal. When an op is dropped (permanent error or retry limit), undo its local change explicitly (hidden = 0, restore label rows and flags), then resync. openFolder() and loadBody() also flush due ops first.
VERIFY: §7.4 runs only due ops before a sync. Ops inside the 4 s undo window or in backoff do not run. §7.3 rewrites label rows and flags for every CHANGEDSINCE hit, and no rule protects rows that have a pending op. A dropped op has no undo step. CHANGEDSINCE does not return a row whose modseq did not change, so a hidden = 1 row or a removed \Inbox row stays wrong for ever. Both the skip-rows-with-pending-ops rule and the explicit undo on drop are small and correct. Flushing due ops in openFolder/loadBody is a small addition.

## PS3 [major] [valid] §7.1 loop, 7.3 IDLE target
PROBLEM: Mail that arrives just before IDLE starts gets no notification. The loop is 'sync → backfill step → SELECT INBOX → IDLE', and on Gmail 'fetch new UIDs in All Mail → back to INBOX IDLE'. Such mail is in the EXISTS/UIDNEXT of SELECT INBOX, but IDLE reports only later changes, so no EXISTS event comes. The keepalive refresh (DONE + IDLE) does not sync, so the notification waits for the next unrelated INBOX event. That can take hours. The 500-header backfill step makes this window wider. This works against priority 1.
FIX: Store the last INBOX UIDNEXT that sync saw (Riseup: folder.uidnext of INBOX; Gmail: the uidnext column of the \Inbox label row, updated after each All Mail new-fetch with the INBOX STATUS/SELECT value). After every SELECT INBOX, compare SELECT UIDNEXT with this value. If it is larger, run the new-mail path again before IDLE. This is one comparison and adds no round trip.
VERIFY: RFC 9051/2177: IDLE reports only changes after IDLE starts, and SELECT reports the current EXISTS/UIDNEXT one time. §7.1 and §7.3 (sync, then backfill, then SELECT INBOX, then IDLE) never compare that SELECT result with local state. Mail that arrives during the backfill step or between the All Mail fetch and SELECT INBOX therefore waits for the next unrelated INBOX event. This hurts priority 1. On Gmail the proposed fix needs an INBOX UIDNEXT, and the finding gets it from a STATUS. That contradicts its own 'no round trip' claim, so a simpler comparison is given in better_fix.
BETTER FIX: Use one rule that does not depend on the server type. Before the sync starts, record the INBOX UIDNEXT (the Riseup sync already gets it; on Gmail, take it from the previous SELECT INBOX). After the final SELECT INBOX, if UIDNEXT is larger than that value plus the number of new \Inbox messages fetched in this cycle, run the new-mail fetch again before IDLE. An un-archive in another client can cause one extra cheap fetch. That is harmless and needs no STATUS round trip.

## PS4 [major] [partly] §7.2 step 6 expunge detection, 4.2 line limit
PROBLEM: Expunge detection is costly, and on large Gmail accounts it can stop sync. Step 6 runs 'UID SEARCH UID <lowest_local>:*' each time the cheap check fails, so after every new mail. Gmail All Mail UIDs have a gap for each message sent to Trash or Spam, so for 100k messages the ESEARCH ALL set can have tens of thousands of ranges. That is hundreds of KB for each push, which costs radio time and CPU. When the line is longer than the 1 MB limit, ImapReader throws ImapProtocolException on every attempt. Sync of that account then stops for good.
FIX: Compare counts first. When backfill is complete and SELECT EXISTS equals the local row count (including hidden rows), no expunge occurred, so skip the step. Otherwise send 'UID SEARCH RETURN (COUNT) UID a:b' for each window of about 5,000 UIDs. Send 'RETURN (ALL)' only for windows where the counts are different. Lines stay short, and the normal case costs one small reply.
VERIFY: The problem is real. Step 6 runs each time the cheap check fails, which is after every new mail. On a large Gmail All Mail, deleted messages, spam and draft revisions leave many gaps in the UID set, so the ESEARCH ALL reply can be hundreds of KB on each push. The plain SEARCH fallback can go past the 1 MB line limit. The count shortcut is correct and cheap. But the proposed bisection 'for each window of about 5,000 UIDs' can need hundreds of COUNT commands, because Gmail UIDs are sparse. The windows must be based on local rows.
BETTER FIX: Keep the count check: skip step 6 when backfill is complete and SELECT EXISTS equals the local row count (hidden rows included). If backfill is not complete, use 'UID SEARCH RETURN (COUNT) UID <backfill_uid>:*'. When the counts differ, send RETURN (ALL) in windows defined by local rows (for example every 5,000th local UID), not by UID span. Gmail All Mail UIDs can span millions, so 5,000-UID windows can mean hundreds of commands.

## PS5 [major] [valid] §7.2 step 1 roles (Riseup), 13 swipe default
PROBLEM: On Riseup the default swipe (Archive) has no target. Roles come only from SPECIAL-USE attributes. Riseup's 'Archive' folder has no \Archive flag, and new accounts may have no Archive folder. So the default start→end swipe and the drawer entry 'Archive (Riseup)' have no folder. The design also has no rule for a missing Sent/Drafts/Trash folder (APPEND fails with [TRYCREATE]) or a missing Spam folder.
FIX: Riseup: if no mailbox has \Archive, use the mailbox named 'Archive'. If there is none, CREATE 'Archive' on the first archive action (accept ALREADYEXISTS) and store role = archive. Do the same for Sent, Drafts and Trash. For junk, create exactly 'Spam'. Add an Archive-folder picker to the account screen.
VERIFY: §7.2 step 1 takes roles only from SPECIAL-USE. R12 shows that Riseup's Archive has no \Archive attribute. The research implication 'let the user choose the Archive folder' is not in DESIGN. So the default start→end swipe and the drawer item 'Archive (Riseup)' have no target. Missing Sent/Drafts/Trash is rare on Riseup, but a missing Spam folder is possible (R20).
BETTER FIX: Use the name fallback 'Archive' when no mailbox has \Archive. If there is no such mailbox, CREATE 'Archive' on the first archive action (accept ALREADYEXISTS) and store role = archive. For spam, create exactly 'Spam' when it is missing. Note that this also turns on server-side spam filing (R20). A folder picker is optional; the name fallback covers the default case.

## PS6 [major] [valid] §7.3 label views
PROBLEM: Gmail labels that LIST does not know never fill. Label folders come only from LIST, which refreshes at most every 6 h. X-GM-LABELS can name a label that LIST does not show: one made after the last LIST (in Gmail web or by a filter), one hidden with 'Show in IMAP' off, or a renamed one. Then no message_folder row is written. When LIST adds the folder later, CHANGEDSINCE does not return the old messages, because their modseq did not change, so those messages never show in the view. A rename deletes the old folder (cascade) and the new view stays empty. Also, Google's doc example shows \Drafts, but a live account returns \Draft.
FIX: When sync finds an unknown user label, create the kind-1 folder row at once (hidden = 1 if LIST does not show it) and write the membership. When LIST shows a label folder that has no rows (new or renamed), fill it one time: EXAMINE that label mailbox, send 'UID FETCH 1:* (X-GM-MSGID)', and map the msgids to local rows (index message_gm). Do not use SEARCH X-GM-LABELS (different encoding). Map both \Draft and \Drafts to role drafts.
VERIFY: §7.3 makes label views only from LIST, and step 1 refreshes LIST at most every 6 h on a long-lived connection. The membership rule writes rows only for known label folders. So labels applied before LIST knows the folder are lost: CHANGEDSINCE never returns those messages again, because their modseq does not change. A rename has the same effect. Creating the kind-1 row when sync finds an unknown label, plus a one-time EXAMINE fill by X-GM-MSGID, is a small and correct fix. The \Draft/\Drafts point is only robustness, because DESIGN already uses \Draft.

## PS7 [major] [valid] §7.3 Drafts, 7.4 append_draft/delete_draft
PROBLEM: Drafts on Gmail go to Trash and show twice. (a) When Gmail expunges a message that has the \Draft and \Deleted flags, it moves the message to [Gmail]/Trash. So each 'leave compose' puts an old revision into Trash, which Plico syncs as a kind-0 folder. (b) draft.server_uid is a [Gmail]/Drafts UID (from APPENDUID), but rows in the Drafts view have All Mail UIDs. Code that deletes the server draft of a draft opened from that view uses the wrong UID space. (c) Each APPENDed draft comes back through the All Mail sync (Gmail) or the Drafts sync (Riseup) as a message row. So the Drafts view shows it two times: once as the local draft row and once as the server row. (d) The design gives no APPEND flags.
FIX: APPEND drafts with (\Draft \Seen). Give each draft one Message-ID and keep it for all revisions. Hide message rows whose message_id matches a local draft; this also finds orphan revisions after a crash (UID SEARCH HEADER Message-ID). Gmail delete: UID MOVE the old revision to \Trash, take the Trash UID from COPYUID, then set \Deleted and run UID EXPUNGE in Trash. When the user opens a server draft, make a draft row that holds its Message-ID / gm_msgid, not a UID.
VERIFY: Mozilla bug 562748 (open for 16 years) confirms it: when a client deletes old draft revisions in [Gmail]/Drafts, Gmail moves them to [Gmail]/Trash. §7.3 says only 'delete the old server draft' and gives no Gmail-safe method. The APPENDed draft also comes back through the All Mail sync (Gmail) or the Drafts sync (Riseup) as a message row, so the Drafts view shows it next to the local draft row. That is a real duplicate. The proposed fixes are all small and correct: a stable Message-ID, hiding rows that match a local draft, MOVE to Trash then expunge in Trash, and APPEND with (\Draft \Seen). Point (b) depends on a 'edit server draft' feature that DESIGN does not define, which is a minor overreach.

## PS8 [major] [valid] §7.3 Actions (Gmail Move/Labels)
PROBLEM: Gmail 'Move' has no rule. The UI has 'Move' (multi-select) and 'Move/Labels', but §7.3 defines only delete, spam and not-spam. A generic move op would run UID MOVE from the source mailbox, and on Gmail that is always All Mail. All Mail is not a label. Gmail turns an expunge from All Mail into Trash, and MOVE out of All Mail is not documented. So the message either keeps \Inbox ('move' acts as 'label') or goes to Trash. The uidMove fallback (COPY + \Deleted + UID EXPUNGE) from All Mail sends the message to Trash.
FIX: On Gmail, 'Move to X' is one labels op: +X-GM-LABELS (X) and -X-GM-LABELS (the label of the current view; \Inbox for Inbox and the unified inbox). 'Move to Inbox' is +X-GM-LABELS (\Inbox). Use UID MOVE only to \Trash and \Junk, and from Trash/Spam to INBOX. Never expunge with All Mail as the source.
VERIFY: §13 offers 'Move' and 'Move/Labels', but §7.3 has no Gmail move rule. A generic 'move' op (§7.4) would run UID MOVE with All Mail as the source. Google does not document that case, and sources say an expunge from All Mail adds Trash. Google does document STORE ±X-GM-LABELS. Mapping 'Move to X' to +X / −current-view-label, and using MOVE only for Trash/Spam and their reverse, matches Gmail web semantics and adds no code.

## PS9 [major] [valid] §7.2 step 6 mass-delete guard
PROBLEM: The mass-delete guard fires on normal purges. Riseup deletes Spam after 7 days and Trash after 21 days. Gmail purges Trash and Spam after 30 days, and users click 'Empty Trash/Spam' in Gmail web. These normal events often remove more than 50 % of those folders. Then the banner comes back again and again, and the deleted mail stays visible in Plico (it looks restored) until the user taps Resync.
FIX: Do not apply the guard to folders with role trash or junk, and do not count deletions that Plico's own ops caused. Keep the guard for inbox, all, archive, sent and user folders.
VERIFY: §7.2 step 6 applies the guard to every mailbox. 'Empty Trash/Spam' in Gmail web or Roundcube removes 100 % of a folder. Auto-purges after a long offline period (Riseup 7 d/21 d per R20, Gmail 30 d per G18) do the same. So the banner appears for normal events, and deleted mail stays visible. The finding overstates the case of gradual daily purges, but exempting the trash/junk roles is the correct minimal fix. The 'own ops' exception adds nothing, because local rows are already deleted first.

## PS10 [major] [valid] §7.2 steps 2, 4, 5
PROBLEM: UID n:* returns the last message again, and steps 2 and 5 have gaps. Step 4 'UID FETCH <uidnext_local>:*' returns the last message when there is no new mail. If the upsert uses INSERT OR REPLACE, SQLite deletes the row and inserts it again. The cascade then deletes body, attachments, label rows and notified, so the body downloads again and a second notification is possible. On the first sync uidnext is 0, and '0:*' is invalid (Dovecot answers BAD). Step 5 (CHANGEDSINCE 1:*) also returns UIDs that are not local (below backfill_uid, or new), and it must not insert rows without headers. Step 2 skips a mailbox when UIDNEXT and MESSAGES are unchanged even when HIGHESTMODSEQ is not available (NOMODSEQ). Then flag changes are never synced.
FIX: Skip step 4 when server UIDNEXT <= local uidnext. Ignore returned UIDs below the requested start. Start the first sync at max(1, UIDNEXT − N). Upsert with UPDATE or INSERT OR IGNORE, never REPLACE. Let CHANGEDSINCE results update existing rows only. Allow the cheap-check skip only when HIGHESTMODSEQ is known and unchanged.
VERIFY: RFC 3501 §6.4.8 / RFC 9051: 'n:*' always includes the last message, so step 4 returns an old row when there is no new mail. That row needs an ignore-below-start rule, or it can cause re-insert or notification bugs. folder.uidnext defaults to 0, and '0:*' is invalid syntax (nz-number). The §7.2 first sync for Riseup has no start rule. Step 5 CHANGEDSINCE returns UIDs that have no local header row. Step 2 skips when UIDNEXT, MESSAGES and HIGHESTMODSEQ are unchanged. With NOMODSEQ (possible on TREES, per R4) that is null == null, so flag changes are never synced. All the fixes are one-line rules.

## PS11 [major] [partly] §7.2 step 3 UIDVALIDITY, 9 watermark
PROBLEM: A UIDVALIDITY change can make pending ops change the wrong mail. After a change, pending ops and draft.server_uid still hold UIDs from the old numbering. Ops run before sync sees the new UIDVALIDITY, so UID STORE/MOVE/EXPUNGE can change different messages. The notification 'watermark' is not defined. After a resync every row is new, which gives a storm or a miss. New UIDs with old dates come from 'not spam' or from a move into INBOX, and a Gmail un-archive adds \Inbox to a known row. On Gmail, a UIDVALIDITY change in All Mail deletes all bodies and labels and forces a full download again.
FIX: Each op stores the folder's uidvalidity with its UIDs. After SELECT, if the value is different, drop the op and undo its local change. Never run it. Notification rule: notify a row only when the new-UID fetch inserted it, notified = 0, it is unseen, and INTERNALDATE >= max(watermark − 10 min, now − 24 h). The watermark is the largest INTERNALDATE notified so far. Gmail: on an All Mail UIDVALIDITY change, map rows to the new UIDs by X-GM-MSGID ('UID FETCH 1:* (UID X-GM-MSGID)') and do not delete them.
VERIFY: The UID-reuse risk is real but rare. Ops run before sync, and nothing checks UIDVALIDITY, so a delete-forever after renumbering can expunge the wrong message. The 'notification watermark' in §9 is not defined anywhere, which is a real gap. But storing uidvalidity per op is not necessary, because the folder row already holds it. The Gmail msgid remap is over-engineering compared with priority 4.
BETTER FIX: Do not store uidvalidity in each op. The op runner already SELECTs the folder. Compare the SELECT UIDVALIDITY with folder.uidvalidity (and the Drafts folder value for draft.server_uid). If they differ, drop the op, undo its local change, and run the step-3 resync. Define the watermark as in the finding. Skip the X-GM-MSGID remap: UIDVALIDITY changes on Gmail are very rare, and that path adds code for an edge case.

## PS12 [major] [valid] §7.4 run_at, 7.5 send_at, 8.3 timers, 9 actions
PROBLEM: Queued work has no wake-up, so it can wait up to 28 min. Undo windows (op run_at = now + 4 s, send_at = now + 5 s) and op backoff need a timer. §8.3 forbids delay() for work that must run while the screen is off, but the due-time set of the alarm has only keepalive, backoff and OAuth. A notification action queues archive/delete with the 4 s run_at and calls kick() at t = 0. The op is not due yet, so IDLE starts again and the op waits for the next refresh (9–28 min). The same occurs when the user taps Send and then locks the phone.
FIX: Notification actions use run_at = now (there is no undo there). Add min(op.run_at, draft.send_at) to the due-time calculation of the alarm (the same exact, coalesced alarm). While the app is visible, a coroutine delay may also fire, but the alarm stays the backup.
VERIFY: §7.4 gives archive/delete a 4 s run_at, and only 'before every sync' runs ops. §9 ActionReceiver does local change + op + kick() at t=0, so the op is not due yet. IDLE starts again, and the op waits for the next refresh, up to 28 min in client mode. §8.3 forbids delay() while the screen is off, and lists op run_at and draft send_at nowhere as alarm due times. Even in the foreground, nothing fires when the undo window ends. The fix is small: run_at = now for notification actions, and min(op.run_at, send_at) added to the existing coalesced alarm.

## PS13 [major] [valid] §7.3 Mailboxes synced
PROBLEM: The design does not handle a Gmail account that hides All Mail, Trash or Spam from IMAP. The Gmail 'Show in IMAP' setting exists for All Mail, Spam and Trash, and many users turn All Mail off because other clients show each message two times. Without \All, the Gmail model has no source for any view. Without \Trash or \Junk, delete and spam fail. The 'Limit IMAP folders' setting (1,000–10,000) makes All Mail show only the newest N messages. Backfill then stops early, and each new mail pushes the oldest one out, so Plico deletes it locally as 'expunged'.
FIX: After LIST, if \All, \Trash or \Junk is missing, set account.state with the text 'Turn on Show in IMAP for All Mail / Trash / Spam (Gmail settings → Labels)' and do not sync. Add no fallback code. If SELECT All Mail gives EXISTS equal to 1000, 2000, 5000 or 10000 exactly, show a note about the folder size limit one time.
VERIFY: G27 confirms the 'Show in IMAP' setting for each label (All Mail, Spam and Trash included) and the folder size limit. The Gmail model in §7.3 has no source without \All, and Delete/Spam have no target without \Trash/\Junk. DESIGN has no rule for either case. A clear state message with no fallback code fits priority 4. Blocking all sync for a missing Trash or Spam is harsher than needed.
BETTER FIX: Stop sync only when \All is missing, with the 'Show in IMAP' hint. When only \Trash or \Junk is missing, show the same hint and turn off Delete/Spam for that account, but keep sync and push running.

## PS14 [major] [valid] §7.4 error handling, 4.3 literals
PROBLEM: Ops have no correct permanent-error rule. The rule 'Permanent error (NO for a missing UID)' never fires, because UID commands ignore UIDs that do not exist and return OK. So every NO counts as transient and retries for ever, with no limit: [TRYCREATE] (a label or folder was deleted elsewhere), [OVERQUOTA] (Riseup 1 GB), [TOOBIG]/[LIMIT] (a draft larger than Gmail APPENDLIMIT 35651584), [CANNOT], and BAD. Hidden rows stay hidden for hours. Also, a server can answer a synchronizing literal (Gmail LITERAL-, > 4096 bytes) with a tagged NO in place of '+'.
FIX: Transient: IOException, [UNAVAILABLE], [INUSE], [SERVERBUG], [THROTTLED], BYE. All other NO and BAD are permanent: drop the op, undo the local change, and show the server text (draft state 'failed'; a banner for OVERQUOTA). Limit transient retries (for example to 24 h), then do the same. Before APPEND, compare the message size with APPENDLIMIT. The literal writer accepts a tagged response while it waits for '+'.
VERIFY: RFC 9051 §6.4.9 says nonexistent UIDs are ignored and the command returns OK. So the only permanent case that §7.4 names ('NO for a missing UID') never occurs, and every other NO/BAD retries for ever at the 1 h cap. Examples are TRYCREATE for a label deleted elsewhere, OVERQUOTA on Riseup, and TOOBIG over APPENDLIMIT. RFC 3501 §7.5 lets a server answer a synchronizing literal with a tagged response in place of '+', so the literal writer must accept that. The proposed classification and retry limit are simple and correct.

## PS15 [major] [partly] §4.7 SmtpClient.send, 7.5
PROBLEM: A partial RCPT failure can duplicate mail or block a send for ever. 'RCPT TO each' has no rule for mixed replies. Riseup rejects an unknown domain at RCPT with 450 4.1.2, so a typo in one address gives a 4xx. If the client then sends DATA, the accepted recipients get the mail, and the 4xx retry sends it again to everyone. If the client stops, the 450 retries for ever and the user never sees the bad address. The design also has no rule for a 5xx on one recipient.
FIX: If any RCPT gets a non-2xx reply, send RSET and no DATA. Set the draft to 'failed' and show the rejected address and the server text (for 4xx and 5xx at RCPT, because 4.1.2 is a typo, not throttling). A 4xx at connect, MAIL or DATA stays transient, with a limit (for example 6 attempts or 24 h), then 'failed'.
VERIFY: The real part: R14 shows Riseup rejects an unknown domain at RCPT with 450 4.1.2. Under '4xx → retry with backoff' with no limit, a single typo keeps the draft queued for ever, and the user never sees the bad address. The duplicate-send branch is speculative, because nothing in DESIGN says DATA continues after a failed RCPT. The '5xx on one recipient' case is already covered by '5xx → failed'. The fix (RSET, no DATA, failed with the address, and a retry limit for other 4xx) is correct.

## PS16 [major] [valid] §7.6 Search, 4.3 Command.string()
PROBLEM: Server search with non-ASCII text fails on Gmail. Command.string() turns non-ASCII text into a literal, but the search command has no CHARSET. Gmail answers 'BAD Could not parse command' to a non-ASCII X-GM-RAW without CHARSET UTF-8, and IMAP's default charset is US-ASCII. So 'Search on server' fails on Gmail for every query with accents, and the Riseup result is not defined.
FIX: When the criteria contain non-ASCII bytes, send 'UID SEARCH CHARSET UTF-8 X-GM-RAW {n+}' (Gmail LITERAL-, n <= 4096) or 'UID SEARCH CHARSET UTF-8 TEXT {n+}' (Riseup LITERAL+). Add the transcript as a unit test.
VERIFY: Command.string() sends non-ASCII as a literal, but the search has no CHARSET. Field reports show Gmail answers 'BAD Could not parse command' to UTF-8 search criteria without CHARSET UTF-8: go-imap issue #19 for X-GM-RAW, and pimalaya/io-imap #3, fixed 2026-09-26, for a UTF-8 literal with charset None. With 'CHARSET UTF-8' plus a literal, the search works. This is a one-line fix plus a transcript test.

## PS17 [major] [partly] §7.3 label changes via CHANGEDSINCE
PROBLEM: Correct Gmail Inbox membership depends on one behaviour that nobody has checked: that a change to X-GM-LABELS alone raises the message MODSEQ in All Mail. Google does not document this, and RFC 7162 covers only flags. If it does not, an archive done in Gmail web or the Gmail app (which only removes \Inbox) never reaches Plico. The message then stays in Plico's Inbox and unified inbox for ever.
FIX: Test this first in the live tests. In addition, add a cheap check that does not depend on it. IDLE on INBOX already gets '* n EXPUNGE' for an archive. On each INBOX EXPUNGE (and on each full sync), send one 'UID SEARCH RETURN (ALL) X-GM-RAW "in:inbox"' in All Mail and make the \Inbox rows equal to that set. This is one command, and the reply is small because it covers the inbox only.
VERIFY: The dependency is real and not verified. gmail.md lists it as an open question, Google does not document it, and Thunderbird's plans only assume it. But no evidence shows that Gmail fails here either, so this is a test gap, not a confirmed bug. The proposed permanent fallback search on every EXPUNGE adds round trips and can return a large set for a big inbox.
BETTER FIX: Put 'label-only change raises MODSEQ in All Mail' as the first item of the live tests. Add the reconciliation only if the test fails, and make it cheap: on an INBOX EXPUNGE, compare SELECT INBOX EXISTS with the local \Inbox row count. Search 'X-GM-RAW "in:inbox"' only when they differ, because a large inbox gives a large reply.

## PS18 [major] [valid] §7.1 loop, 8.3 refresh, 9 folder.notify
PROBLEM: Folders with folder.notify = 1 get no sync in the background. §9 notifies for such folders, but IDLE watches only INBOX, and the keepalive refresh is only DONE + IDLE. So Riseup mail that server filters put into folders, and Gmail mail with a 'Skip the Inbox' label, is not fetched until the user opens the app or another INBOX event occurs. There is no notification, and unread counts stay old. The research decisions assumed a sweep on each wake (riseup A, gmail C).
FIX: On each refresh wake (it occurs anyway), after DONE: on Gmail, send 'STATUS "[Gmail]/All Mail" (UIDNEXT)'. If it changed, run the All Mail new-fetch, which covers all labels, and notify by folder.notify. On Riseup, send one 'LIST "" "*" RETURN (STATUS (MESSAGES UIDNEXT HIGHESTMODSEQ))' and sync only the folders that changed. Use the same LIST-STATUS as the step-2 cheap check, in place of N STATUS commands.
VERIFY: §9 notifies for folder.notify = 1, but §7.1 IDLE watches only INBOX, and the §8.3 refresh is only DONE + IDLE. So mail that a Riseup filter files elsewhere, or a Gmail skip-inbox label, is not fetched until an unrelated INBOX event or an app open occurs. gmail decision C ('one LIST-STATUS sweep on each wake') was lost from DESIGN. One STATUS (Gmail All Mail) or one LIST-STATUS (Riseup) on a wake that already happens costs almost nothing. Using LIST-STATUS for the step-2 cheap check also removes N STATUS round trips. Do the sweep only when the account has a notify folder outside the inbox.

## PS19 [major] [valid] §4.5 displayParts
PROBLEM: The message view can drop part of the body. displayParts keeps one best HTML part and one best plain part. Apple Mail sends inline images as multipart/mixed [text/html, image, text/html, ...], often inside an alternative. Mailing lists (Mailman) add the footer as a second inline text/plain part. Only one part is shown, so the rest of the body is missing without any warning.
FIX: In multipart/mixed, and in multipart/related without an HTML root, join all inline text/html and text/plain parts in order. Inline means no 'attachment' disposition and no filename. Escape plain parts as HTML when you join them with HTML. Show inline images that have no cid reference as attachments. Add Apple Mail, Mailman and message/rfc822 samples to the BODYSTRUCTURE tests.
VERIFY: §4.5 keeps one best HTML part and one best plain part and makes all other parts attachments. Apple Mail mixed bodies (text/html, image, text/html) and Mailman footers (a separate text/plain part when the post is multipart) then show only part of the body. The other text parts become anonymous attachment cards, so 'without warning' is overstated a little. Joining inline text parts in order is what K-9/Thunderbird and FairEmail do, and it is a small change to displayParts.

## PS20 [minor] [valid] §4.2 literal limit, 7.1 loadAttachment
PROBLEM: A large attachment is held in memory several times. ImapReader keeps all literals in memory before it returns. An attachment part of up to 35 MB (Gmail) or 25.6 MB (Riseup) then becomes one ByteArray, then a decoded copy, and maybe a growing buffer. The peak is near 100 MB on a heap of about 256 MB, so OutOfMemoryError is possible, mostly during parallel work.
FIX: In loadAttachment, fetch 'BODY.PEEK[sec]<offset.1048576>' chunks and add each to a temp file. Then decode file to file with Base64.getMimeDecoder().wrap() or a QP stream. The reader does not change, and the literal limit for normal responses can go down to about 4 MB.
VERIFY: ImapReader holds whole literals in memory (50 MB cap). An attachment part is held as the encoded literal, then as a decoded copy, then possibly as a growing buffer, so OOM is possible. Gmail also receives messages up to 50 MB, so a single part can reach the literal cap and fail to download at all. Chunked 'BODY.PEEK[sec]<off.len>' into a temp file, then a stream decode, is a standard and small fix that needs no reader change.

## PS21 [minor] [partly] §4.3 idle()/done(), Command literals, COMPRESS
PROBLEM: done() can send DONE before the server's '+'. This occurs when kick() comes just after IDLE is sent. DONE is the client's answer to the continuation, so a server can read it as a new command (BAD) while IDLE stays active. The refresh then times out and the client reconnects, which costs an argon2 login on Riseup. Also, with COMPRESS on, every wait for '+' (IDLE, synchronizing literals, AUTHENTICATE without SASL-IR) needs a SYNC_FLUSH first. If not, the server never gets the command.
FIX: done() sets a flag. The reader sends DONE immediately after the '+' arrives if the flag is set. The Command writer flushes before each wait for '+'. Add a fake-server test where kick comes before '+'.
VERIFY: done() before '+' technically breaks RFC 2177/9051. Setting a flag and sending DONE after '+' is a cheap and correct guard. But TCP order means most servers (Dovecot included) read DONE only after they enter IDLE, so the BAD-and-reconnect chain is not shown to occur. The COMPRESS part is not a real hole: §4.1 already does SYNC_FLUSH on every flush, and any writer must flush before it blocks for '+', with or without compression.

## PS22 [minor] [valid] §5 message.date, 7.2 body window
PROBLEM: The design does not say whether message.date (NOT NULL) is the Date header or INTERNALDATE. If it is the Date header: spam with a future Date stays at the top of the unified inbox, a missing or bad Date breaks NOT NULL, and the body window and notifications use wrong times.
FIX: Set date = INTERNALDATE (for sort, body window and watermark). Show the Date header only in the message view.
VERIFY: §5 has date NOT NULL, and §7.2 fetches both the DATE header and INTERNALDATE without saying which fills message.date. A missing or bad Date header breaks NOT NULL, and a forged future Date pins spam to the top. Using INTERNALDATE for sort, the body window and the watermark (the Date header only for display) is a one-line spec rule.

## PS23 [minor] [valid] §10 MessageBuilder headers
PROBLEM: MessageBuilder can write header lines longer than the hard limit. §10 gives the header order and 75-char encoded words, but no folding rule. To and Cc with many recipients, and References in long threads, can go over the 998-octet hard limit. Postfix (Riseup) or Gmail can then break or reject the header.
FIX: Fold structured headers at commas or spaces before 78 characters, and never go past 998. Keep References to the first ID and the last 10 IDs. Add a test for long recipient lists.
VERIFY: §10 gives the header order and encoded words but no folding rule. Long To/Cc or References lines can go past the RFC 5322 998-octet limit. §15 already tests 'line lengths', so the rule must be in the spec. Folding at commas/spaces and trimming References are standard and small.

## PS24 [minor] [valid] §10, 13 Compose (Forward)
PROBLEM: The design does not say how Forward includes the attachments of the original message. Users expect a forwarded PDF to go with the mail. The draft attachment model contains only picked URIs.
FIX: Forward adds the original attachments as draft entries with a source reference (message id + section). The Sender downloads them through loadAttachment into filesDir/outbox/<id>/ before it builds the MIME. Show them in compose as removable cards.
VERIFY: §13 has Forward, but the §5 draft model holds only picked URIs, so a forwarded mail loses its attachments. Users expect them. The gap is real. The proposed lazy download at send time adds a second attachment kind.
BETTER FIX: Use a simpler path: when the user taps Forward, download the original attachments with loadAttachment into filesDir/outbox/<draftId>/ and add them as normal draft entries. No new 'source reference' type and no send-time download in Sender are needed. If the download fails offline, show the error in compose.

## PS25 [minor] [partly] §7.3 Actions (star)
PROBLEM: On Gmail, '-FLAGS (\Flagged)' does not remove a star that was set in the web UI. Unstar then does nothing on the server, and the next sync shows the star again.
FIX: Gmail unstar is one op with '-FLAGS.SILENT (\Flagged)' and '-X-GM-LABELS.SILENT ("\\Starred")'.
VERIFY: FairEmail FAQ 153 confirms the quirk: a star set in the web UI cannot be removed with STORE -FLAGS (\Flagged). But no source shows that removing the \Starred label works either, and FairEmail's own code (Core.java) uses only \Flagged. The fix is a guess. Also, the result is a silent difference (the local row is unstarred while the server keeps the star), not 'the star comes back', because an unchanged modseq is not returned by CHANGEDSINCE.
BETTER FIX: Add 'unstar a web-set star' to the live tests. Send '-FLAGS.SILENT (\Flagged)' and, only if the test shows that it helps, '-X-GM-LABELS.SILENT (\Starred)' in the same op.

## PS26 [minor] [partly] §7.4 moves
PROBLEM: After a MOVE the moved message is missing from both folders for a time, and its body downloads again. 'Delete the row; the destination picks it up on its next sync' has this effect because non-INBOX mailboxes sync only on open or sweep. A Gmail delete does not show in Trash, a Riseup archive does not show in Archive, and the body and attachments download again, which costs data and battery.
FIX: Use the COPYUID from the MOVE reply to change folder_id and uid of the row (and its message_folder row). Keep the body and attachments. Delete the row only when the reply has no COPYUID.
VERIFY: The body re-download is real but small: text parts only, and attachments load on demand. Using COPYUID (RFC 6851, both servers have UIDPLUS) to update the row in place is a cheap improvement. But the 'missing from both folders' claim is overstated. syncNow flushes ops and then syncs every sync = 1 mailbox (Trash is kind 0 on Gmail), so the destination row appears in the same cycle, seconds later.

## PS27 [minor] [valid] §10 'Never: Bcc', 7.2 header fields
PROBLEM: Bcc recipients are lost in drafts and in the Riseup Sent copy. The rule 'never a Bcc header' applies to every MessageBuilder output, including the Drafts APPEND and the Riseup Sent APPEND. So a saved draft loses its Bcc recipients when it is opened on another device or after a reinstall. The Riseup Sent copy has no record of whom the user Bcc'd, while Gmail's own Sent copy keeps Bcc. The header fetch list has no BCC, so even Gmail Sent cannot show it.
FIX: Add a MessageBuilder flag forStorage. It includes Bcc for the Drafts APPEND and the Riseup Sent APPEND, and excludes it for SMTP DATA. Test both cases. Add BCC to HEADER.FIELDS.
VERIFY: §10 bans the Bcc header for all MessageBuilder output, and the Drafts APPEND and the Riseup Sent APPEND use the same builder. So server drafts lose Bcc, and the Riseup Sent copy keeps no record of Bcc recipients, while Gmail's own Sent copy keeps them. A forStorage flag (Bcc only in stored copies, never in SMTP DATA) does not leak Bcc to recipients. Adding BCC to HEADER.FIELDS is trivial.

## PS28 [minor] [valid] §4.3/4.4 simplification
PROBLEM: Some code is not needed, and one fallback is dangerous on Gmail. Both servers advertise MOVE, so the uidMove fallback (COPY + \Deleted + UID EXPUNGE) is dead code. On Gmail it would also send the message to Trash when the source is All Mail (see PS8). VANISHED handling (QRESYNC only) and '~{n}' binary literals (BINARY fetch only) have no use. The category filter sends one search for each category.
FIX: Make MOVE a required capability and show a clear error if it is missing. Remove VANISHED and '~{n}'. Send one search: 'UID SEARCH X-GM-RAW "category:primary OR category:updates" UID <new>'.
VERIFY: Both servers advertise MOVE (G15, R11), so the COPY+\Deleted+EXPUNGE fallback in §4.4 is dead code. On Gmail it is also unsafe from All Mail (see PS8). VANISHED arrives only after ENABLE QRESYNC, which DESIGN never sends, and '~{n}' arrives only for BINARY fetches, which DESIGN never sends. Removing them fits priority 4. Gmail search supports OR, so one X-GM-RAW search can replace one search per category.
Superseded 2026-10-17: Plico now supports every IMAP server, so the fallbacks are needed again: COPY + `\Deleted` + a guarded expunge when MOVE is missing (never on Gmail, which has MOVE), and a plain SEARCH when ESEARCH is missing. See DESIGN.md §4.4.
